# 事务

MySQL 中的事务是将一组 SQL 语句作为一个不可分割的逻辑单元执行，仅在 **InnoDB** 引擎中被完整支持。

## 1. ACID

- **原子性（Atomicity）**：一组操作要么全做，要么全不做。由 **Undo Log（回滚日志）** 实现，执行失败或发生回滚时，通过记录的反向操作恢复数据。
- **一致性（Consistency）**：事务执行前后，数据必须处于合法且业务规则一致的状态。这是事务的最终目标，依赖于其余三个特性共同保障。
- **隔离性（Isolation）**：并发事务之间互不干扰。主要通过 **锁机制（行锁、表锁）** 与 **MVCC（多版本并发控制）** 来实现。
- **持久性（Durability）**：事务一旦提交，修改永久生效。由 **Redo Log（重做日志）**和 WAL 机制保证，即使系统崩溃也能在重启时恢复。



```sql
-- 开启事务
START TRANSACTION; -- 或 BEGIN;

-- 执行业务操作
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 提交事务（持久化生效）
COMMIT;

-- 或发生异常时回滚
ROLLBACK;
```

> **提示**：MySQL 默认开启自动提交（`autocommit = 1`），单条 SQL 会被视作独立事务并自动提交。



## 2. 并发问题

在多事务并发访问同一数据时，若缺乏有效的隔离控制，会导致以下四类典型的数据不一致问题：

### 1. 脏读

- **定义**：一个事务读取了另一个事务**已修改但尚未提交**的数据。
- **场景**：事务 A 将余额从 100 改为 200（未提交）；事务 B 读取到 200 并据此结算；随后事务 A 发生异常回滚（余额恢复为 100）。
- **后果**：事务 B 基于实际上从未真正生效的“脏数据”完成了业务处理。

![image-20260820182004022](/covers/java--mysql-2--4-tk841l/image-20260820182004022.webp)



### 2. 不可重复读

- **定义**：同一事务内多次读取**同一个数据**，由于其他事务的**修改删除并提交**，导致前后读取的数据内容不一致。
- **场景**：事务 A 第一次查询商品库存为 100；事务 B 将库存修改为 200 并提交；事务 A 再次读取该商品库存，得到 200。
- **后果**：违背了事务内部的数据一致性预期，侧重于已有记录的 **UPDATE** 或 **DELETE**。

![image-20260820182155443](/covers/java--mysql-2--4-tk841l/image-20260820182155443.webp)



### 3. 幻读

- **定义**：同一事务内根据相同条件进行范围查询，由于其他事务**新增并提交了满足条件的数据**，导致前后查询到的**记录条数或数据集发生变化**。
- **场景**：事务 A 查询 `age > 18` 的用户共有 5 条；事务 B 插入了一条 `age = 20` 的新记录并提交；事务 A 再次查询（或执行批量更新），发现变成了 6 条记录。
- **后果**：前后产生如同“幻觉”般凭空出现的新行，侧重于范围内的 **INSERT**。

![image-20260820182310445](/covers/java--mysql-2--4-tk841l/image-20260820182310445.webp)



### 4. 丢失更新

- **第一类丢失更新（回滚丢失）**：事务 A 的回滚覆盖了事务 B 已提交的数据。（现代关系型数据库在底层排他锁机制下均已避免）。
- **第二类丢失更新（覆盖丢失）**：事务 A 与事务 B 同时读取数据进行计算后写回，后提交的事务覆盖了先提交的事务修改。例如两人同时对库存扣减 1，最终库存只减少了 1。



**核心问题对比**

| **并发问题**   | **触发操作**        | **影响范围** | **本质特征**                 |
| -------------- | ------------------- | ------------ | ---------------------------- |
| **脏读**       | 读取未提交数据      | 单行 / 多行  | 读到未提交数据               |
| **不可重复读** | `UPDATE` / `DELETE` | 单行记录     | 同一条数据内容前后不一致     |
| **幻读**       | `INSERT`            | 范围数据集   | 满足条件的记录行数前后不一致 |
| **丢失更新**   | 并发写冲突          | 单行记录     | 后提交覆盖先提交的更新结果   |



## 3. 四大隔离级别

SQL 标准定义了四种事务隔离级别，由低到高依次强化隔离程度，隔离级别越高，性能效率就越低

### 1. 读未提交（Read Uncommitted, RU）

- **特性**：事务可以读取其他事务**尚未提交**的修改数据。
  - 一个事务还未提交，它做的变更就能被其它事务看到

- **并发问题**：脏读、不可重复读、幻读均会出现。
- **底层机制**：读操作不加锁也不生成快照，写操作加排他锁，并发性能最高但数据完全无保障，生产环境极少采用。



### 2. 读已提交（Read Committed, RC）

- **特性**：事务只能读取其他事务**已经提交**的数据。
  - 一个事务提交后，它做的变更才能被其他事务看到

- **并发问题**：解决了脏读；但仍存在不可重复读和幻读。
- **底层机制**：基于 MVCC 实现快照读时，**每次执行 `SELECT` 都会生成一个新的 Read View**。此外，普通加锁只锁定记录本身（Record Lock），不锁间隙，锁冲突较少。Oracle、PostgreSQL 默认采用此级别。



#### 工作流程

读提交隔离级别是在每次读取数据时，都会⽣成⼀个新的 **Read View**。

也意味着，事务期间的多次读取同⼀条数据，前后两次读的数据可能会出现不⼀致，因为可能这期间另外⼀个事务修改了该记录，并提交了事务。

那读提交隔离级别是怎么⼯作呢？我们还是以前⾯的例⼦来聊聊。

假设事务 A（事务 id 为51）启动后，紧接着事务 B （事务 id 为52）也启动了，接着按顺序执⾏了以下操作：

- 事务 B 读取数据（创建 Read View），⼩林的账户余额为 100 万；
- 事务 A修改数据（还没提交事务），将⼩林的账户余额从 100 万修改成了 200 万；
- 事务 B 读取数据（创建 Read View），⼩林的账户余额为 100 万；
- 事务 A提交事务；
- 事务 B 读取数据（创建 Read View），⼩林的账户余额为 200 万；

那具体怎么做到的呢？我们重点看事务 B 每次读取数据时创建的  Read View。前两次事务 B 读取数据时创建的Read View 如下图：

我们来分析下为什么事务 B 第⼆次读数据时，读不到事务 A（还未提交事务）修改的数据？

事务 B 在找到⼩林这条记录时，会看这条记录的 trx_id 是 51，在事务 B 的 Read View 的 min_trx_id 和max_trx_id 之间，接下来需要判断 trx_id 值是否在  m_ids 范围内，判断的结果是在的，那么说明这条记录是被还未提交的事务修改的，这时事务 **B** 并不会读取这个版本的记录。⽽是，沿着 undo log 链条往下找旧版本的记录，

直到找到 trx_id 「⼩于」事务 B 的 Read View 中的 min_trx_id 值的第⼀条记录，所以事务 B 能读取到的是 trx_id 为 50 的记录，也就是⼩林余额是 100 万的这条记录。

我们来分析下为什么事务 A提交后，事务 B 就可以读到事务 A修改的数据？

在事务 A提交后，由于隔离级别是「读提交」，所以事务 **B** 在每次读数据的时候，会重新创建  **Read View**，此时事务 B 第三次读取数据时创建的  Read View 如下：

<img src="/covers/java--mysql-2--4-tk841l/image-20260820201723928.webp" alt="image-20260820201723928" style="zoom:67%;" />

事务 B 在找到⼩林这条记录时，会发现这条记录的 **trx_id** 是 **51**，⽐事务 **B** 的 **Read View** 中的 **min_trx_id** 值（**52**）还⼩，这意味着修改这条记录的事务早就在创建  **Read View** 前提交过了，所以该版本的记录对事务 **B** 是可见的。

正是因为在读提交隔离级别下，事务每次读数据时都重新创建 Read View，那么在事务期间的多次读取同⼀条数据，前后两次读的数据可能会出现不⼀致，因为可能这期间另外⼀个事务修改了该记录，并提交了事务。





### 3. 可重复读（Repeatable Read, RR）

- **特性**：同一事务内多次读取同一行数据，结果保持一致。
  - 一个事务执行过程中看到的数据，一直跟这个事务启动时看到的数据是一致的

- **并发问题**：解决了脏读、不可重复读；可以很大程度上避免幻读现象的发生（只是很大程度上避免，并不是彻底避免）
  - ***特例***：事务 A 查询不存在记录（快照读），事务 B 插入并提交，事务 A 执行 `UPDATE` 操作命中该记录，随后再次快照读会发现该记录（因为 UPDATE 属于当前读，更新了记录的 `trx_id`），属于极少数的幻读情况。

- **底层机制**：
  - **快照读**（普通 `SELECT`）：在事务**第一次执行查询时生成 Read View**，并在整个事务期间复用该视图，从而规避不可重复读和快照读下的幻读。
  - **当前读**（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）：通过 **Next-Key Locks（记录锁 + 间隙锁）** 锁定查询范围，防止其他事务插入新记录。
  - 除了普通查询时快照读，其他都是当前读
- 这是 **MySQL InnoDB 存储引擎的默认隔离级别**。



#### 工作流程

假设事务 A（事务 id 为51）启动后，紧接着事务 B （事务 id 为52）也启动了，那这两个事务创建的 Read View 如下：

<img src="/covers/java--mysql-2--4-tk841l/image-20260820200622742.webp" alt="image-20260820200622742" style="zoom: 80%;" />

事务 A和事务 B 的 Read View 具体内容如下：

- 在事务 A的 Read View 中，它的事务 id 是 51，由于它是第⼀个启动的事务，所以此时活跃事务的事务 id 列表就只有 51，活跃事务的事务 id 列表中最⼩的事务 id 是事务 A本⾝，下⼀个事务 id 则是 52。
- 在事务 B 的 Read View 中，它的事务 id 是 52，由于事务 A是活跃的，所以此时活跃事务的事务 id 列表是51 和 52，活跃的事务 **id** 中最⼩的事务 **id** 是事务 **A**，下⼀个事务 id 应该是 53。

接着，在可重复读隔离级别下，事务 A和事务 B 按顺序执⾏了以下操作：

- 事务 B 读取⼩林的账户余额记录，读到余额是 100 万；
- 事务 A将⼩林的账户余额记录修改成 200 万，并没有提交事务；
- 事务 B 读取⼩林的账户余额记录，读到余额还是 100 万；
- 事务 A提交事务；
- 事务 B 读取⼩林的账户余额记录，读到余额依然还是 100 万；



事务 B 第⼀次读⼩林的账户余额记录，在找到记录后，它会先看这条记录的 trx_id，此时发现 **trx_id** 为 **50**，⽐事务**B** 的 **Read View** 中的 **min_trx_id** 值（**51**）还⼩，这意味着修改这条记录的事务早就在事务 **B** 启动前提交过了，所以该版本的记录对事务 **B** 可见的，也就是事务 B 可以获取到这条记录。

接着，事务 A通过 update 语句将这条记录修改了（还未提交事务），将⼩林的余额改成 200 万，这时 MySQL 会记录相应的 undo log，并以链表的⽅式串联起来，形成版本链，如下图：

<img src="/covers/java--mysql-2--4-tk841l/image-20260820201034352.webp" alt="image-20260820201034352" style="zoom:67%;" />

由于事务 A修改了该记录，以前的记录就变成旧版本记录了，于是最新记录和旧版本记录通过链表的⽅式串起来，⽽且最新记录的 trx_id 是事务 A的事务 id（trx_id = 51）。

然后事务 B 第⼆次去读取该记录，发现这条记录的 **trx_id** 值为 **51**，在事务 **B** 的 **Read View** 的 **min_trx_id** 和**max_trx_id** 之间，则需要判断 **trx_id** 值是否在  **m_ids** 范围内，判断的结果是在的，那么说明这条记录是被还未提交的事务修改的，这时事务 **B** 并不会读取这个版本的记录。⽽是沿着 **undo log** 链条往下找旧版本的记录，直到找到 **trx_id** 「⼩于」事务 **B** 的 **Read View** 中的 **min_trx_id** 值的第⼀条记录，所以事务 B 能读取到的是 trx_id 为 50 的记录，也就是⼩林余额是 100 万的这条记录。

最后，当事物 A提交事务后，由于隔离级别时「可重复读」，所以事务 **B** 再次读取记录时，还是基于启动事务时创建的 **Read View** 来判断当前版本的记录是否可见。所以，即使事物 **A** 将⼩林余额修改为 **200** 万并提交了事务，事务 **B** 第三次读取记录时，读到的记录都是⼩林余额是 **100** 万的这条记录。

就是通过这样的⽅式实现了，「可重复读」隔离级别下在事务期间读到的记录都是事务启动前的记录。



#### 幻读发生的特殊情况

虽然 MySQL InnoDB 存储引擎在可重复读（RR）隔离级别下，通过 **MVCC 快照读** 和 **Next-Key Lock 当前读** 很大程度上解决了幻读问题，但**它并不是 100% 杜绝了所有场景下的幻读**。

当一个事务内部**混合使用「快照读」与「当前读 / 写操作」**时，依然会出现幻读现象。最典型的情况有以下三种：

**情况一：经典案例 —— 快照读后 `UPDATE` 命中了并发插入的行**

这是最经典、最纯粹的 RR 级别幻读复现场景（即：**同为普通 `SELECT` 快照读，第二次查到了第一次没有的记录**）。

**1. 复现执行时序**

假设表 `t(id INT PRIMARY KEY, name VARCHAR(20))` 初始为空：

```
时刻   事务 A (RR 级别)                             事务 B (并发事务)
─────────────────────────────────────────────────────────────────────────────
T1     BEGIN;
       SELECT * FROM t WHERE id > 0;
       -- 【快照读】结果：Empty set (0 条记录)
       -- 此时生成 Read View (creator_trx_id = A)

T2                                                  BEGIN;
                                                    INSERT INTO t VALUES (5, 'Tom');
                                                    COMMIT;
                                                    -- 物理行生成，此时该行的 trx_id = B

T3     -- 事务 A 执行当前读更新：
       UPDATE t SET name = 'Jerry' WHERE id = 5;
       -- 执行成功！受影响行数：1 行！
       -- 【关键底层机制】：UPDATE 是当前读，能看到已提交的 id=5。
       -- 更新后，该行的 trx_id 被修改为了 事务 A 的 trx_id！

T4     -- 事务 A 再次执行普通快照读：
       SELECT * FROM t WHERE id > 0;
       -- 💥 结果：查出了 (5, 'Jerry') 这一行！
       -- 产生了标准的幻读！
```

**2. 底层发生幻读的原因（MVCC 原理剖析）**

- 在 **T1** 时刻，事务 A 创建了 Read View。
- 在 **T2** 时刻，事务 B 插入了 `id = 5`（`trx_id = B`）。按 Read View 规则，事务 B 的修改对事务 A 是**不可见的**。
- 在 **T3** 时刻，`UPDATE` 属于**当前读**，直接基于物理存储读到了事务 B 提交的最新数据并完成了更新。更新后，该行记录的最新版本上记录的 **`trx_id` 变成了事务 A 自己的 `trx_id`**。
- 在 **T4** 时刻，事务 A 再次执行快照读，拿当前 Read View 判定时，命中了规则第一条：**`trx_id == creator_trx_id`（由我自己创建/修改的数据，无条件对自己可见）**。
- 因此，原本“不可见”的新插入记录，因为被事务 A 摸了一下（更新了 `trx_id`），直接“显形”出现在了快照读中。



**情况二：先执行「快照读」，后执行「加锁读 (当前读)」**

在同一个事务中，先后使用了不同读取机制：

```
时刻   事务 A (RR 级别)                             事务 B (并发事务)
─────────────────────────────────────────────────────────────────────────────
T1     BEGIN;
       SELECT * FROM t WHERE id > 10;
       -- 【普通快照读】：不加锁，返回空 (Empty)

T2                                                  BEGIN;
                                                    INSERT INTO t VALUES (15, 'Alice');
                                                    COMMIT;
                                                    -- 因为事务 A 没加 Gap Lock，事务 B 顺利插入并提交

T3     SELECT * FROM t WHERE id > 10 FOR UPDATE;
       -- 【加锁当前读】：强制读取底层物理最新数据
       -- 💥 结果：查出了 id = 15 这条记录！
```

- **原因分析**：T1 是快照读，没有在 `(10, +∞)` 上加间隙锁，给事务 B 留下了插入空间；而 T3 切换为 `FOR UPDATE`（当前读），绕过了 Read View 直接抓取最新提交物理行，导致两次查询结果集不一致。



**情况三：幽灵般的「主键冲突」（业务层面的幻读感知）**

虽然严格从查询语句上看没有查出新行，但在业务操作中能明确感知到新行的“幽灵存在”：

```
时刻   事务 A (RR 级别)                             事务 B (并发事务)
─────────────────────────────────────────────────────────────────────────────
T1     BEGIN;
       SELECT * FROM t WHERE id = 10;
       -- 返回 Empty (确认该 id 不存在)

T2                                                  BEGIN;
                                                    INSERT INTO t VALUES (10, 'Bob');
                                                    COMMIT;

T3     -- 事务 A 自信地去插入该 id：
       INSERT INTO t VALUES (10, 'Bob');
       -- 💥 报错: ERROR 1062 (23000): Duplicate entry '10' for key 'PRIMARY'

T4     SELECT * FROM t WHERE id = 10;
       -- 再次查询依然是 Empty（由于 Read View 保护）！
```

- **业务困境**：查的时候明明没有（快照读判定不存在），插的时候却报“已存在”（底层物理唯一性索引报错），再次查依然看不到。



**总结与工程防范**

1. **本质原因**：InnoDB 的 RR 隔离级别并不是完全等同于 Serializable（串行化）。快照读基于 MVCC（不阻塞并发写入），当前读基于 Lock（操作物理最新数据），**两者穿插就会打破快照隔离的一致性幻觉**。
2. **如何彻底避免幻读？**
   - **方案 1（严格串行化）**：若业务要求绝对严格的一致性，在事务开启的**第一步就使用加锁当前读**（如 `SELECT ... FOR UPDATE`），用 **Next-Key Lock** 从一开始就将目标间隙锁死，阻塞其他事务的并发插入。
   - **方案 2（隔离级别提升）**：将事务隔离级别直接升为 `SERIALIZABLE`（此时所有普通 `SELECT` 都会自动转为 `LOCK IN SHARE MODE` 加锁读）。



### 4. 串行化（Serializable）

- **特性**：所有事务排队依次串行执行，完全隔离。
  - 会对记录加上读写锁，在多个事务对这条记录进行读写操作时，如果发生了读写冲突的时候，后访问的事务必须等前一个事务执行完成，才能继续执行

- **并发问题**：解决所有并发事务问题（脏读、不可重复读、幻读）。
- **底层机制**：隐式地将所有普通读操作转化为加共享锁（S 锁）的当前读，读写完全互斥，系统吞吐量极低。



**隔离级别综合对比**

| **隔离级别**         | **脏读** | **不可重复读** | **幻读** | **MVCC / 锁行为**                            |
| -------------------- | -------- | -------------- | -------- | -------------------------------------------- |
| **Read Uncommitted** | 存在     | 存在           | 存在     | 无快照，几乎不加读锁                         |
| **Read Committed**   | 解决     | 存在           | 存在     | 每次 `SELECT` 新建 Read View；仅记录锁       |
| **Repeatable Read**  | 解决     | 解决           | 基本解决 | 首次 `SELECT` 复用 Read View；Next-Key Locks |
| **Serializable**     | 解决     | 解决           | 解决     | 读加 S 锁，写加 X 锁，读写互斥               |



### RC 与 RR 隔离级别的实现差异

MVCC 在 RC 和 RR 下的本质区别在于 **Read View 的生成时机**：

对于「读提交」和「可重复读」隔离级别的事务来说，它们是通过**Read View** 来实现的，它们的区别在于创建 Read View 的时机不同，可以把 Read View 理解成⼀个数据快照，就像相机拍照那样，定格某⼀时刻的风景。

「读提交」隔离级别是在「每个语句执⾏前」都会重新⽣成⼀个 **Read View**，⽽「可重复读」隔离级别是「启动事务时」⽣成⼀个 **Read View**，然后整个事务期间都在⽤这个 **Read View**。

| **隔离级别**       | **Read View 生成策略**                           | **并发表现与结果**                                           |
| ------------------ | ------------------------------------------------ | ------------------------------------------------------------ |
| **RC（读已提交）** | **每次执行 `SELECT` 均重新生成**独立的 Read View | 其他事务一旦提交，后续 `SELECT` 的新 Read View 就会将其剔除出 `m_ids`，从而读到最新数据（导致不可重复读）。 |
| **RR（可重复读）** | **仅在首次执行 `SELECT` 时生成**，事务内全程复用 | 事务执行期间活跃列表恒定，无论后续其他事务是否提交，读取到的始终是首次查询时的数据状态（保证可重复读）。 |

**快照读 vs 当前读**

- **快照读** ：单纯的 `SELECT` 语句（不加锁），依赖 MVCC 读取历史快照，无需加锁，性能最高。
- **当前读 **：`SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`、`INSERT`、`UPDATE`、`DELETE`。当前读不走 MVCC 快照，而是强制读取数据的**最新版本**并对相关记录加锁（Record Lock / Next-Key Lock）。



## 4. MVCC

**MVCC（Multi-Version Concurrency Control，多版本并发控制）** 是 MySQL InnoDB 引擎实现高效并发读写的核心机制。它通过保存数据的多个历史版本，使**普通的读操作（快照读）无需加锁即可执行**，实现“读-写”、“写-读”互不阻塞。

>**MVCC 就是通过给数据保留历史快照（多个版本），让查数据的人看“旧照片”，改数据的人写“新草稿”，从而实现读写互不阻塞、不用排队等锁。**

MVCC 仅在 **读已提交（RC）** 和 **可重复读（RR）** 隔离级别下生效。

**三大核心底层支撑**

### 1. 记录中的隐藏字段

InnoDB 为每行记录隐式添加了核心字段：

- `trx_id`（6 字节）：最后一次插入或修改该记录的**事务 ID**。
- `rool_ptr`（7 字节）：**回滚指针**，指向写入 Undo Log 的上一版本历史记录。



### 2. Undo Log 与版本链

每当数据被修改（`UPDATE` 或 `DELETE`）时，InnoDB 会将旧版本数据写入 Undo Log，并通过当前记录的 `rool_ptr` 指向该旧记录。随着多次修改，这些历史记录在 Undo Log 中按时间由新到旧串联成一条**版本链**（链表头为当前最新行记录）。



### 3. Read View（一致性视图）

事务在执行**快照读**时会生成一个 Read View，用于判断版本链中哪些数据对当前事务可见。Read View 包含 4 个核心属性：

<img src="/covers/java--mysql-2--4-tk841l/image-20260820192350172.webp" alt="image-20260820192350172" style="zoom:67%;" />

- `creator_trx_id`：创建该 Read View 的事务 ID。
- `m_ids`：生成视图瞬间，系统中所有**活跃（已开启但未提交）的事务 ID 列表**。
- `min_trx_id`：`m_ids` 中的最小值（最小活跃事务 ID）。
- `max_trx_id`：生成视图时系统准备分配给下一个事务的 ID（高水位线，即当前最大事务 ID + 1）。



知道了 Read View 的字段，我们还需要了解聚簇索引记录中的两个隐藏列。

假设在账户余额表插⼊⼀条⼩林余额为 100 万的记录，然后我把这两个隐藏列也画出来，该记录的整个⽰意图如下：

<img src="/covers/java--mysql-2--4-tk841l/image-20260820193519958.webp" alt="image-20260820193519958" style="zoom: 80%;" />

对于使⽤ InnoDB 存储引擎的数据库表，它的聚簇索引记录中都包含下⾯两个隐藏列：

- **trx_id**，当⼀个事务对某条聚簇索引记录进⾏改动时，就会把该事务的事务 **id** 记录在 **trx_id** 隐藏列⾥；
- **roll_pointer**，每次对某条聚簇索引记录进⾏改动时，都会把旧版本的记录写⼊到 undo ⽇志中，然后这个隐藏列是个指针，指向每⼀个旧版本记录，于是就可以通过它找到修改前的记录。

在创建  Read View 后，我们可以将记录中的 trx_id 划分这三种情况：

<img src="/covers/java--mysql-2--4-tk841l/image-20260820193717405.webp" alt="image-20260820193717405" style="zoom: 80%;" />

⼀个事务去访问记录的时候，除了⾃⼰的更新记录总是可见之外，还有这⼏种情况：

- 如果记录的 trx_id 值⼩于 Read View 中的min_trx_id值，表⽰这个版本的记录是在创建 Read View 前已经提交的事务⽣成的，所以该版本的记录对当前事务可见。
- 如果记录的 trx_id 值⼤于等于 Read View 中的max_trx_id值，表⽰这个版本的记录是在创建 Read View 后才启动的事务⽣成的，所以该版本的记录对当前事务不可见。
- 如果记录的 trx_id 值在 Read View 的min_trx_id和max_trx_id之间，需要判断 trx_id 是否在 m_ids 列表中：
  - 如果记录的 trx_id 在m_ids列表中，表⽰⽣成该版本记录的活跃事务依然活跃着（还没提交事务），所以该版本的记录对当前事务不可见。
  - 如果记录的 trx_id 不在m_ids列表中，表⽰⽣成该版本记录的活跃事务已经被提交，所以该版本的记录对当前事务可见。

>**`m_ids` 确实落在 `min_trx_id` 和 `max_trx_id` 之间，但这个区间内的事务并不全都在 `m_ids` 里，中间存在“空洞”（已提前提交的事务）。** 
>
>**为什么区间内会有“不在 `m_ids`”的事务？**
>
>事务 ID 是**单调递增连续分配**的，但**事务提交的先后顺序是随机的**（短事务先提交，长事务后提交），所以区间里可能夹着已提交的事务。
>
>**具体示例：**
>
>假设系统先后开启了 4 个写事务：
>
>1. **事务 100**（大事务，运行很慢）
>2. **事务 101**（只改了一条数据，**瞬间提交完毕**）
>3. **事务 102**（还在运行）
>4. **事务 103**（还在运行）
>
>此时，**事务 104** 开启并执行了一条 `SELECT` 查询，系统为它创建 Read View：
>
>- `m_ids`（当前活跃、未提交的事务列表）：`[100, 102, 103]`
>- `min_trx_id`（`m_ids` 最小值）：`100`
>- `max_trx_id`（系统准备分配的下一个 ID）：`105`
>
>**此时如果事务 104 去查记录：**
>
>- 某条记录由 **事务 101** 修改。
>- 事务 101 的 ID（`101`）严格介于 `min_trx_id(100)` 和 `max_trx_id(105)` 之间。
>- 检查 `m_ids` 列表 `[100, 102, 103]`，发现 **101 不在里面**。
>- **结论**：说明事务 101 虽然比 100 后启动，但在当前 Read View 创建之前**就已经执行完毕并提交了**，因此该版本数据对事务 104 **完全可见**。
>
>**一句话总结判断逻辑**
>
>在 `[min_trx_id, max_trx_id)` 这个区间内：
>
>- **在 `m_ids` 里** = 说明你查的时候它**还没提交**，不可见。
>- **不在 `m_ids` 里** = 说明它虽然晚于 `min_trx_id` 开启，但在你查之前**已经悄悄提交了**，可见。
