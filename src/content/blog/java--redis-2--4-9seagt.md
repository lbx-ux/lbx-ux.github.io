# 网络模型

## 1. 用户空间和内核态空间

在现代操作系统（如 Linux 和 Windows）中，用户空间（User Space）和内核态空间（Kernel Space）是内存隔离和权限保护的核心机制。

简单来说，操作系统为了保证自身的稳定和安全，将虚拟内存分成了两大块，并赋予了不同的 CPU 权限级别。



![image-20260816155309357](/covers/java--redis-2--4-9seagt/image-20260816155309357.png)

- **内核态空间 (Kernel Space - Ring 0)**
  - **这是操作系统的“VIP 核心区”。** 操作系统的内核代码和底层设备驱动程序运行在这里。
  - **权限极高：** 运行在内核态的代码可以无限制地访问所有硬件资源（如 CPU、内存、硬盘、网卡）。
  - **崩溃代价：** 如果内核态的代码发生异常或崩溃，通常会导致整个操作系统崩溃（比如 Windows 的蓝屏，Linux 的 Kernel Panic）。
- **用户空间 (User Space - Ring 3)**
  - **这是普通应用程序的“活动区”。** 你平时写的代码、运行的软件都在这里执行。
  - **权限受限：** 运行在用户空间的代码**不能**直接操作硬件，也不能越权访问其他程序的内存。
  - **崩溃代价：** 如果用户空间的程序崩溃了（比如报了个 `NullPointerException` 导致进程退出），操作系统本身依然能稳定运行。



### 1. 寻址空间

进程的寻址空间划分成两部分：**内核空间、用户空间**

什么是寻址空间呢？我们的应用程序也好，还是内核空间也好，都是没有办法直接去物理内存的，而是通过分配一些虚拟内存映射到物理内存中，我们的内核和应用程序去访问虚拟内存的时候，就需要一个虚拟地址，这个地址是一个无符号的整数，比如一个32位的操作系统，他的带宽就是32，他的虚拟地址就是2的32次方，也就是说他寻址的范围就是0~2的32次方， 这片寻址空间对应的就是2的32个字节，就是4GB，这个4GB，会有3个GB分给用户空间，会有1GB给内核系统

### 2. 系统调用

既然用户空间的程序没有权限直接操作硬件，那它需要读写文件或发送网络请求时该怎么办呢？这就需要用到**系统调用（System Call）**。

![image-20260816155735822](/covers/java--redis-2--4-9seagt/image-20260816155735822.png)

当你的程序需要执行特权操作时，它必须向内核“提出申请”。

1. 程序发起一个系统调用（比如 `read()`, `write()`, `open()`）。
2. CPU 暂停当前程序，将状态从**用户态切换到内核态**。
3. 内核接管控制权，代替程序去完成硬件操作（如从网卡读取数据）。
4. 内核把结果返回给程序，CPU 再从**内核态切换回用户态**。

这种状态的切换被称为**上下文切换（Context Switch）**，它是一个非常耗费 CPU 资源的过程。



Linux系统为了提高IO效率，会在用户空间和内核空间都加入缓冲区：

写数据时，要把用户缓冲数据拷贝到内核缓冲区，然后写入设备

读数据时，要从设备读取数据到内核缓冲区，然后拷贝到用户缓冲区

针对这个操作：我们的用户在写读数据时，会去向内核态申请，想要读取内核的数据，而内核数据要去等待驱动程序从硬件上读取数据，当从磁盘上加载到数据之后，内核会将数据写入到内核的缓冲区中，然后再将数据拷贝到用户态的buffer中，然后再返回给应用程序，整体而言，速度慢，就是这个原因，为了加速，我们希望read也好，还是wait for data也最好都不要等待，或者时间尽量的短。

## 2. 网络I/O模型

在理解 Linux 下的 5 种经典网络 I/O 模型之前，首先要明白一次完整的网络 I/O 操作（以读操作 `read` 为例）主要包含两个阶段：

1. **等待数据准备就绪（Wait for data）：** 数据从网络中到达网卡，然后被读取到内核的缓冲区（Kernel Buffer）。
2. **将数据从内核拷贝到用户空间（Copy data）：** 将数据从内核缓冲区拷贝到用户空间的应用程序缓冲区（User Buffer）。

<img src="/covers/java--redis-2--4-9seagt/image-20260816162909339.png" alt="image-20260816162909339" style="zoom:80%;" />

这五个经典模型的最大区别，就在于它们在这两个阶段的处理方式不同。



### 1. 阻塞 I/O (Blocking I/O - BIO)

**一句话理解：** 两个阶段都在干等，什么别的事也干不了。

![image-20260816164731092](/covers/java--redis-2--4-9seagt/image-20260816164731092.png)

当应用程序发起 `read` 系统调用时，如果内核中数据还没准备好，当前线程就会一直阻塞（挂起），直到数据准备好并完全拷贝到用户空间后，函数才返回。

- **实战背景：** 早期的 Java Sockets 编程（`java.io` 包）用的就是这种模式。每一个网络连接都需要分配一个独立的线程来处理。并发量一大，不仅耗费大量内存，线程切换的开销也极大。



### 2. 非阻塞 I/O (Non-blocking I/O - NIO)

**一句话理解：** 第一阶段不挂起，而是疯狂“查岗”；第二阶段依然阻塞。

<img src="/covers/java--redis-2--4-9seagt/image-20260816164840685.png" alt="image-20260816164840685" style="zoom:80%;" />

应用程序将 Socket 设置为非阻塞模式。发起 `read` 时，如果数据没好，内核会立刻返回一个错误（`EWOULDBLOCK`），线程不挂起，可以去干点别的事，过一会儿再来问。这叫做**轮询（Polling）**。但当数据准备好后，在“拷贝数据”的第二阶段，线程依然会阻塞，直到拷贝完成。

- **缺点：** 频繁的轮询会产生大量的系统调用，极大浪费 CPU 资源。纯粹的非阻塞 I/O 在实际中很少直接使用。



### 3. I/O 多路复用 (I/O Multiplexing)

![image-20260816165033671](/covers/java--redis-2--4-9seagt/image-20260816165033671.png)

**一句话理解：** 找个“大堂经理”帮忙盯着所有连接，谁有数据就去处理谁。

这是目前**最主流、最重要**的高并发 I/O 模型。它通过 `select`、`poll` 或 `epoll` 这类系统调用，让一个或几个线程可以同时监听成千上万个 Socket 的状态。如果没有任何 Socket 有数据，线程就在 `epoll` 处阻塞；一旦有 Socket 可读或可写，内核会通知应用程序，应用程序再去发起真实的 `read` 调用（此时第二阶段拷贝数据依然是阻塞的）。

- **实战背景：**
  
  - **Redis** 之所以能用单线程扛住十万级以上的并发，核心靠的就是基于 `epoll` 的 I/O 多路复用机制。
  - **Nginx** 作为高性能 Web 服务器，高并发的基础同样是它。
  - Java 里的 `java.nio` 包中的 `Selector`，底层在 Linux 上也就是封装了 `epoll`。构建复杂业务后端时，几乎所有的高性能通信框架（比如 Netty）都离不开它。
  
  

### 4. 信号驱动 I/O (Signal-driven I/O)

**一句话理解：** 留个电话，数据好了内核发短信通知。

![image-20260816170314717](/covers/java--redis-2--4-9seagt/image-20260816170314717.png)

应用程序告诉内核：“等数据准备好了，你给我发个 `SIGIO` 信号”。然后线程就去干别的了。收到信号后，应用程序再发起 `read` 把数据从内核拷贝出来（注意，第二阶段依然阻塞）。

- **现状：** 相比于多路复用，信号驱动 I/O 在实际的后端开发和网络应用中用得相对较少。



### 5. 异步 I/O (Asynchronous I/O - AIO)

**一句话理解：** 把活儿全包给内核，连拷贝数据都不用自己操心。

<img src="/covers/java--redis-2--4-9seagt/image-20260816165155155.png" alt="image-20260816165155155" style="zoom:80%;" />

应用程序发起 `read` 操作后立刻返回，去干别的事情。内核负责等待数据准备，**并且**负责把数据拷贝到用户空间。等一切都彻底完成后，内核再给应用程序发个通知（或者执行应用预设的回调函数）。在这个模型里，第一和第二阶段**全都不阻塞**线程。

- **实战背景：** Java 7 引入的 NIO.2 提供了真正的 AIO 支持（`AsynchronousSocketChannel`）。不过在 Linux 系统下，AIO 的底层实现由于历史包袱一直不够完美，目前主流的高并发网络通信（包括 Netty 的最佳实践）依然首选基于 `epoll` 的 I/O 多路复用。



### 核心区别总结

| **I/O 模型**         | **第一阶段：等待数据**     | **第二阶段：数据拷贝** | **同步/异步** |
| -------------------- | -------------------------- | ---------------------- | ------------- |
| **阻塞 I/O (BIO)**   | 阻塞                       | 阻塞                   | 同步          |
| **非阻塞 I/O (NIO)** | 非阻塞（轮询）             | 阻塞                   | 同步          |
| **I/O 多路复用**     | 阻塞（在 select/epoll 上） | 阻塞                   | 同步          |
| **信号驱动 I/O**     | 非阻塞（内核发信号）       | 阻塞                   | 同步          |
| **异步 I/O (AIO)**   | 非阻塞                     | 非阻塞                 | 异步          |

> **关键认知：** 很多人容易混淆，但其实前四种模型（BIO、NIO、多路复用、信号驱动）本质上都属于**同步 I/O**。因为在关键的第二阶段（数据从内核拷贝到用户进程）时，它们都会阻塞当前应用的线程。只有真正的 **AIO** 才能做到全过程非阻塞
