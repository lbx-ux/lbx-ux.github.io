在 Redis 7.0 及之后版本中，最核心的底层变革是 **彻底废除了 `ziplist`（压缩列表），全面由 `listpack`（紧凑列表）替代**，以彻底解决连锁更新（Cascading Updates）问题。

| 类型   | Redis 3.2 之前                                  | Redis 3.2 ~ 6.2                                     | Redis 7.0                                 |
| :----- | :---------------------------------------------- | :-------------------------------------------------- | :---------------------------------------- |
| String | `int` / `embstr` / `raw`，embstr 阈值为 39 字节 | `int` / `embstr` / `raw`，embstr 阈值提升为 44 字节 | 同 3.2~6.2，仍为 `int` / `embstr` / `raw` |
| List   | 小：`ziplist` 大：`linkedlist`                  | `quicklist`，节点内部是 `ziplist`                   | `quicklist`，节点内部改为 `listpack`      |
| Hash   | 小：`ziplist` 大：`hashtable`                   | 小：`ziplist` 大：`hashtable`                       | 小：`listpack` 大：`hashtable`            |
| Set    | 全整数小集合：`intset` 其他：`hashtable`        | 同左                                                | 同左，仍是 `intset` / `hashtable`         |
| ZSet   | 小：`ziplist` 大：`skiplist`                    | 小：`ziplist` 大：`skiplist `                       | 小：`listpack` 大：`skiplist`             |



## 1. SDS

**SDS（Simple Dynamic String，简单动态字符串）** 是 Redis 专为高性能与安全性定制的底层字符串实现。C 语言传统的字符数组以 `\0` 结尾，在长度计算、二进制存储和内存安全方面存在固有缺陷，Redis 使用 SDS 完全替代了传统 `char*`。

### SDS 优势

1. **获取字符串长度的时间复杂度是 (O(1))**：SDS通过`len`属性记录长度，获取长度只需读取该属性，复杂度为O(1)。
2. **杜绝缓冲区溢出**：所有修改操作前，SDS的API都会检查空间是否足够，不足则自动扩容，从根本上杜绝溢出。
3. **减少内存重分配次数**：通过**空间预分配**和**惰性空间释放**两种策略优化。
   - **空间预分配**：扩容时，会额外分配一些未使用的空间（`free`属性），减少未来连续增长所需的重分配次数。
   - **惰性空间释放**：字符串缩短时，不会立即回收多余内存，而是用`free`属性记录下来以备后用，避免频繁释放。
4. **二进制安全**：SDS不依赖`\0`判断结束，而是通过`len`属性，因此可以存储任何二进制数据。
5. **兼容部分C字符串函数**：SDS遵循在末尾添加空字符`\0`的惯例，使得可以直接使用部分C标准库的字符串处理函数。





### SDS 内部数据结构

自 Redis 3.2 起，为了最大限度节省内存，SDS 根据字符串长度划分为 5 种头部类型（`sdshdr5`、`sdshdr8`、`sdshdr16`、`sdshdr32`、`sdshdr64`），结构定义如下：

```c
struct __attribute__ ((__packed__)) sdshdr8 {
    uint8_t len;         /* 已使用长度（不包含结尾的 '\0'） */
    uint8_t alloc;       /* 分配的总长度（不包含头和结尾 '\0'） */
    unsigned char flags; /* 低 3 位表示类型（sdshdr8/16/32/64 等），高 5 位预留 */
    char buf[];          /* 字节数组，存储实际数据 */
};
```

- **`__attribute__ ((__packed__))`**：告知编译器取消内存结构对齐优化，紧凑排列字段，使指针可以直接通过 `buf - 1` 找到 `flags`，进而根据类型推导出 `len` 和 `alloc`。
- **`len`**：记录字符串**当前实际长度**
- **`alloc`**：分配给字符串的**总空间大小**（不含头部和结束符）。
- **`flags`**：标识**SDS的类型**。
- **`buf[]`**：**字节数组，用来保存实际数据**。不仅可以保存字符串，还可以保存二进制数据。





### 内存管理策略

**1. 空间预分配（Space Preallocation）**

**当判断出缓冲区大小不够同时，Redis会自动将扩大SDS的空间大小**

```c
hisds hi_sdsMakeRoomFor(hisds s， size_t addlen)
{
    ...
    //s目前的剩余空间已足够，无需扩展，直接返回
        if (avail >= addlen)
            return s;
    //获取目前s的长度
    len = hi_sdslen(s);
    sh = (char *)s - hi_sdsHdrSize(oldtype);
    //扩展之后s至少需要的长度
    newlen = (len + addlen);
    //根据新长度，为s分配新空间所需要的大小
    if (newlen < HI_SDS_MAX_PREALLOC)
    //新长度<HI_SDS_MAX_PREALLOC则分配所需空间*2的空间
        newlen *= 2;
    else
        //否则，分配长度为目前长度+1MB
        newlen += HI_SDS_MAX_PREALLOC;
    newsh = s_realloc(sh, hdrlen + newlen + 1);
}
```

- 若修改后 SDS 长度 $< 1\text{ MB}$：Redis 会分配与 `len` 相同大小的未用空间（即 `alloc = 2 * len`）。
- 若修改后 SDS 长度 $\ge 1\text{ MB}$：Redis 会额外分配固定 $1\text{ MB}$ 的未使用空间（即 `alloc = len + 1MB`）。
- 结尾均额外分配 1 字节用于写入 `\0`。

**2. 惰性空间释放（Lazy Freeing）**

当缩短字符串（如裁剪操作）时，SDS 不会立即调用 `free` 或 `realloc` 释放内存，而是仅减少 `len`，增加可用空间（`alloc - len`），为后续可能的增长留出缓冲。若需彻底释放，可显式调用特定函数完成内存收缩。





### 内部编码

Redis 的 String 对象在底层封装为 `redisObject` 结构体，根据存储内容的数据类型及长度大小，采用 **`int`**、**`embstr`** 和 **`raw`** 三种内部编码。

| **编码类型** | **底层数据结构**               | **触发条件 / 阈值**                           | **内存分配次数**               |
| ------------ | ------------------------------ | --------------------------------------------- | ------------------------------ |
| **`int`**    | `long` 整数（直接复用指针）    | 纯数字且可用 64 位有符号整数（`long`）表示    | **0 次**（直接写在指针字段中） |
| **`embstr`** | 紧凑型 SDS（`sdshdr8`）        | 字符串且长度 $\le 44$ 字节                    | **1 次**（连续内存块）         |
| **`raw`**    | 常规 SDS（`sdshdr8/16/32/64`） | 字符串且长度 $> 44$ 字节，或修改过的 `embstr` | **2 次**（分离内存块）         |

**1. `int` 编码**

当存储的值为整数，并且这个整数值可以用long类型来表示，Redis 会使用 `int` 编码。

<img src="/covers/java--redis-1--3-gzct2l/image-20260823180142665.png" alt="image-20260823180142665" style="zoom:67%;" />

- **实现原理**：`redisObject` 中的 `ptr` 原本是指向具体底层结构的指针（占 8 字节）。对于整数值，Redis 直接将 `void*` 指针强转**直接存储该整数值**，**无需额外分配任何 SDS 内存**。
- **共享对象池**：Redis 启动时会预先初始化 `0` 到 `9999` 的共享整数对象，当存储这些区间内的数字时，多个 Key 直接复用相同的 `redisObject`，进一步节省内存（注：若开启 LRU/LFU 淘汰策略，共享对象会失效）。



**2. `embstr` 编码（Embedded String）**

专为短字符串设计的紧凑型只读编码。

<img src="/covers/java--redis-1--3-gzct2l/image-20260823180527132.png" alt="image-20260823180527132" style="zoom:80%;" />

- **实现原理**：将元数据结构 `redisObject` 和底层字符串 `sdshdr8` 分配在**同一块连续的内存区域**中。

- **核心优势**：

  - **分配效率高**：创建时只需调用 1 次 `malloc`内存分配，销毁时只需 1 次 `free`。
  - **缓存命中率高**：数据连续分布，具备更好的 CPU 缓存局部性（Cache Locality）。

- **44 字节分界线由来**：

  Redis 默认采用 Jemalloc 内存分配器，其最小分配内存梯度为 8、16、32、**64** 字节等。

  - `redisObject` 固定占用 **16 字节**。

  - `sdshdr8` 头部（`len`、`alloc`、`flags`）占用 **3 字节**。

  - 字符串末尾保留的 `\0` 占用 **1 字节**。

    $$64\text{ 字节} - 16\text{ 字节} - 3\text{ 字节} - 1\text{ 字节} = 44\text{ 字节}$$

    为保证总内存恰好落在 64 字节的分配梯度内不产生内部碎片，有效字符串长度上限设定为 44 字节。



**3. `raw` 编码**

适用于长字符串或需要频繁追加、动态扩展的场景。

<img src="/covers/java--redis-1--3-gzct2l/image-20260823180620112.png" alt="image-20260823180620112" style="zoom: 67%;" />

- **实现原理**：`redisObject` 与 `SDS` 分别独立分配在两块不连续的内存空间中，`redisObject.ptr` 存储指向该 `SDS` 的内存地址，需要调用 **2 次 `malloc`** 分别创建 `redisObject` 与独立的大块 `SDS`。
- **适用场景**：字符串长度超过 44 字节，或者频繁进行修改、追加操作的字符串。



**编码的自动流转机制**

Redis 中的字符串编码转换通常是**单向不可逆**的：

```
           [ 写入纯整数 ]
              │
              ▼
            [ int ] ────( 执行 APPEND / 浮点计算 / 溢出 long )───┐
                                                                 │
           [ 写入短字符串 (≤ 44B) ]                               │
              │                                                  │
              ▼                                                  │
          [ embstr ] ───( 执行任意修改操作，如 APPEND )────────────┼──► [ raw ]
                                                                 │
           [ 写入长字符串 (> 44B) ]                              │
              │                                                  │
              ▼                                                  │
            [ raw ] ◄────────────────────────────────────────────┘
```

1. **`embstr` 是只读的**：Redis 底层并未为 `embstr` 提供任何就地修改的 API。一旦对其执行修改操作（如 `APPEND`、`SETRANGE`），Redis 会**先将其强制转为 `raw` 编码**，然后再执行修改（即使修改后的总长度依然 $\le 44$ 字节，编码也不会降回 `embstr`）。
2. **`int` 的退化**：如果对 `int` 编码的值执行了追加非数字字符的操作（`APPEND key abc`），或者对其进行递增/递减导致数值溢出 64 位整数范围，它会被转换为 `raw` 编码。





## 2. 双向列表（linkedlist）

在 Redis 中，**双向链表（Doubly Linked List，源码中称为 `adlist`）** 是 C 语言层面实现的基础通用数据结构。

它既是早期 Redis List 对象的底层实现之一，也广泛应用于 Redis 服务端自身的系统管理中（如客户端连接列表、慢查询日志等）。

### 结构设计

Redis 的双向链表由节点结构 `listNode` 和链表管理结构 `list` 组成：

```c
/* 链表节点 */
typedef struct listNode {
    struct listNode *prev; // 前驱节点指针
    struct listNode *next; // 后继节点指针
    void *value;           // 节点存储的值（通用泛型指针）
} listNode;
```

<img src="/covers/java--redis-1--3-gzct2l/image-20260823181523333.png" alt="image-20260823181523333" style="zoom:67%;" />

```c
/* 双向链表控制器 */
typedef struct list {
    listNode *head;        // 表头指针
    listNode *tail;        // 表尾指针
    unsigned long len;     // 链表长度计数器
    void *(*dup)(void *ptr);            // 节点值复制函数
    void (*free)(void *ptr);            // 节点值析构/释放函数
    int (*match)(void *ptr, void *key); // 节点值匹配/比较函数
} list;
```

list 结构为链表提供了链表头指针 head、链表尾节点 tail、链表节点数量 len、以及可以⾃定义实现的 dup、free、match 函数。

<img src="/covers/java--redis-1--3-gzct2l/image-20260823181626055.png" alt="image-20260823181626055" style="zoom:67%;" />





### 优缺点

**优势**

1. **双端访问与无环设计**：
   - 记录了 `head` 与 `tail`，头尾插入/弹出（`LPUSH`/`RPOP`）的时间复杂度均为 **$O(1)$**。
   - 表头的 `prev` 与表尾的 `next` 均指向 `NULL`，属于无环链表。
2. **$O(1)$ 获取元素总数**：
   - 维护了 `len` 字段，无需像传统 C 链表那样遍历整表统计长度。
3. **多态与通用性（Polymorphism）**：
   - 节点值采用 `void *value` 泛型指针。
   - 结合 `list` 中的 `dup`、`free`、`match` 函数指针，可以自定义任意数据类型的复制、释放和查找比较逻辑。



**缺陷**

1. **内存开销过大（指针膨胀）**：
   - 64 位系统下，一个 `listNode` 包含 2 个链表指针（16B）和 1 个 `void *value` 指针（8B），**光是节点结构自身就占 24 字节**。
   - 加上 Jemalloc 分配元数据与内存对齐，存储一个 1 字节字符可能要消耗 32 字节甚至更多内存，内存利用率极低。
2. **严重的内存碎片**：
   - 每个节点都是一次独立的 `malloc` 堆内存分配，频繁增删会导致大量内存碎片。
3. **CPU 缓存不友好（Cache Miss）**：
   - 各节点在物理内存中离散分布，无法利用 CPU Cache 的预读优化，遍历时频繁触发缓存缺失。





### 演进历程

从 `adlist` 到 `quicklist`，为了保留链表灵活增删的特性，同时解决内存离散与碎片问题，Redis 逐步完成了对 List 底层的改造：

```
+-------------------------------------------------------------------------+
| Redis 3.2 之前: ziplist (元素少且小时) ────(数量超限/长度超标)───► adlist   |
+-------------------------------------------------------------------------+
                                    │
                                    ▼
+-------------------------------------------------------------------------+
| Redis 3.2 - 6.2: 统一使用 quicklist (双向链表 + 节点内嵌 ziplist)          |
+-------------------------------------------------------------------------+
                                    │
                                    ▼
+-------------------------------------------------------------------------+
| Redis 7.0+: 统一使用 quicklist (双向链表 + 节点内嵌 listpack)              |
+-------------------------------------------------------------------------+
```

- **`quicklist` 的折中方案**：外层依然是双向无环链表，但每个链表节点内部存储的是一整块连续内存的 `listpack`（早期为 `ziplist`）。既支持从两端高效伸缩，又大幅削减了指针开销与内存碎片。





### 当前用途

尽管面向用户的 List 对象不再直接由 `adlist` 充当主容器，但在 Redis 核心服务的管理层面，`adlist` 仍然扮演着关键角色：

- **客户端连接列表**：`server.clients` 使用 `adlist` 记录当前连接到 Redis 的所有客户端。
- **慢查询日志**：`server.slowlog` 记录最近执行的慢命令。
- **发布/订阅（Pub/Sub）**：记录某个频道（Channel）的所有订阅客户端列表。
- **从节点同步列表**：`server.slaves` 维护所有的从库连接。



## 3. 压缩列表（ziplist）

**压缩列表（Ziplist）** 是 Redis 为了极度节约内存而设计的**连续内存块顺序型数据结构**。它可以在 $O(1)$ 时间复杂度内完成首尾元素的压入与弹出，常用于早期 Redis 的 List、Hash 以及 ZSet 的小规模数据存储。

### 结构设计

Ziplist 将所有元数据和节点内容紧凑地存放在一块连续分配的内存空间中，没有任何指针开销：

![image-20260823183530079](/covers/java--redis-1--3-gzct2l/image-20260823183530079.png)

| **字段**      | **字节大小**         | **作用与含义**                                               |
| ------------- | -------------------- | ------------------------------------------------------------ |
| **`zlbytes`** | 4 字节（`uint32_t`） | 记录整个压缩列表占用的总内存字节数（在内存重分配 `realloc` 时使用）。 |
| **`zltail`**  | 4 字节（`uint32_t`） | 记录压缩列表「尾部」节点距离起始地址有多少字节，列表尾的偏移量； |
| **`zllen`**   | 2 字节（`uint16_t`） | 记录节点总数。                                               |
| **`entry`**   | 不定长               | 实际存储的数据节点（包含整数或字节数组）。                   |
| **`zlend`**   | 1 字节（`uint8_t`）  | 标记压缩列表的结束点，固定值 0xFF（⼗进制255）。             |

在压缩列表中，如果我们要查找定位第⼀个元素和最后⼀个元素，可以通过表头三个字段（zllen）的长度直接定位，**复杂度是 O(1)**。⽽查找其他元素时，就没有这么⾼效了，只能逐个查找，此时的复杂度就是 **O(N)** 了，因此压缩列表不适合保存过多的元素。



**节点 `entry` 的内部结构**

每个 `entry` 节点包含三部分，专门通过可变长度编码（Variable-length Encoding）压缩空间：

![image-20260823184135674](/covers/java--redis-1--3-gzct2l/image-20260823184135674.png)

1. **`prevlen`（前置节点长度）**：
   - **作用**：记录前一个节点的字节长度，用于**从后往前遍历**
   - **动态占位**：
     - 若前一节点长度 $< 254$ 字节：占 **1 字节**。
     - 若前一节点长度 $\ge 254$ 字节：占 **5 字节**（第 1 字节固定为 `0xFE` 作为标记，后 4 字节存储实际长度值）。
2. **`encoding`（编码与长度）**：
   - 记录 `data` 存储的数据类型（字符串还是整数）以及数据的字节长度。
   - 前 2 位为 `00`、`01`、`10` 时代表不同长度的字节数组；以 `11` 开头代表整数编码（支持 `int16`、`int32`、`int64` 及 0~12 的即时小整数）。
3. **`data`（实际数据）**：
   - 存储具体数据，数值类型会直接按紧凑的二进制存储，不再转换为字符串。



### 优缺点

- **优势**：
  - **零指针开销**：普通双向链表每个节点需要 16~24 字节指针，Ziplist 仅通过偏移量跳转，省去全部指针内存。
  - **内存碎片极低**：整张表为单一连续内存块，一次性分配/释放。
  - **高缓存命中率**：数据连续分布在物理内存，对 CPU 缓存极为友好。
- **缺陷（致命硬伤）**：
  - **内存拷贝开销**：每次新增、删除节点都需要调用 `realloc` 重新分配内存并可能触发整段数据搬迁。
  - **连锁更新（Cascade Update）** 隐患。





###  连锁更新问题

连锁更新是导致 Ziplist 在最坏情况下增删时间复杂度退化至 **$O(N^2)$** 的核心原因：

- **触发机制**：当有一串连续节点的长度介于 250~253 字节之间时，它们的 `prev_entry_len` 均占用 1 字节。此时在表头插入一个 $\ge 254$ 字节的新节点，后继节点的 `prev_entry_len` 必须扩展为 5 字节。
- **连锁扩散**：后继节点因为多了 4 字节空间，自身总长度随之超过 254 字节，导致再下一个节点的 `prev_entry_len` 也必须从 1 字节扩至 5 字节，引发连续的内存重新分配。



现在假设⼀个压缩列表中有多个连续的、长度在 250～253 之间的节点，如下图：

![image-20260823191311457](/covers/java--redis-1--3-gzct2l/image-20260823191311457.png)

因为这些节点长度值⼩于 254 字节，所以 prevlen 属性需要⽤ 1 字节的空间来保存这个长度值。

这时，如果将⼀个长度⼤于等于 254 字节的新节点加⼊到压缩列表的表头节点，即新节点将成为 e1 的前置节点，如下图：

![image-20260823191409086](/covers/java--redis-1--3-gzct2l/image-20260823191409086.png)

因为 e1 节点的 prevlen 属性只有 1 个字节⼤⼩，⽆法保存新节点的长度，此时就需要对压缩列表的空间重分配操作，并将 e1 节点的 prevlen 属性从原来的 1 字节⼤⼩扩展为 5 字节⼤⼩。

多⽶诺牌的效应就此开始。

![image-20260823191514621](/covers/java--redis-1--3-gzct2l/image-20260823191514621.png)

e1 原本的长度在 250～253 之间，因为刚才的扩展空间，此时 e1 的长度就⼤于等于 254 了，因此原本 e2 保存 e1 的prevlen 属性也必须从 1 字节扩展⾄ 5 字节⼤⼩。

正如扩展 e1 引发了对 e2 扩展⼀样，扩展 e2 也会引发对 e3 的扩展，⽽扩展 e3 又会引发对 e4 的扩展.... ⼀直持续到结尾。

这种在特殊情况下产⽣的连续多次空间扩展操作就叫做「连锁更新」，就像多⽶诺牌的效应⼀样，第⼀张牌倒下了，推动了第⼆张牌倒下；第⼆张牌倒下，又推动了第三张牌倒下....





### 演进历程

为规避 Ziplist 的缺陷，Redis 经历了两次关键演进：

1. **Redis 3.2 引入 `quicklist`**：将一个大的 Ziplist 拆分成多个小 Ziplist 并用双向链表串联，限制单个 Ziplist 节点大小与长度，降低单次连锁更新影响范围。
2. **Redis 7.0 全面引入 `listpack`（紧凑列表）**：彻底放弃 Ziplist。`listpack` 节点**不再记录前一个节点的长度**，改在节点末尾记录**当前节点自身的总长度**（`element-tot-len`），既保留了从后往前遍历的能力，又从数据结构设计上**彻底消除了连锁更新**。





## 4. listpack

**Listpack（紧凑列表）** 是 Redis 5.0 引入、并在 Redis 7.0 全面替代 Ziplist 的连续内存顺序型数据结构。它在保留了内存极度紧凑、无指针碎片优势的同时，**从结构设计上彻底消除了 Ziplist 的“连锁更新”隐患**。

### 结构设计

listpack 采⽤了压缩列表的很多优秀的设计，⽐如还是⽤⼀块连续的内存空间来紧凑地保存数据，并且为了节省内存的开销，listpack 节点会采⽤不同的编码⽅式保存不同⼤⼩的数据。

![image-20260823192921148](/covers/java--redis-1--3-gzct2l/image-20260823192921148.png)



**节点 `entry` 的内部结构**

与 Ziplist 最大不同的是：**Listpack 节点不再记录前一个节点的长度，而是记录自身长度**。

![image-20260823193013415](/covers/java--redis-1--3-gzct2l/image-20260823193013415.png)

1. **`encoding`（编码字段）**：
   - 记录数据的类型（整数还是字符串）以及 `data` 部分的长度。
   - 支持小整数即时编码（6 位直接存数值）、`int16`、`int24`、`int32`、`int64` 以及不同长度梯度的字符串。
2. **`data`（数据内容）**：
   - 存储具体内容。纯数字直接以紧凑的补码二进制存储，非数字以原始字节数组存储。
3. **`len`（反向遍历长度，也称 `backlen`）**：
   - **记录当前节点（包括 `encoding` + `data` ）的总字节数**。
   - 放置在节点最末尾，专门用于支持**从后往前反向遍历**。

可以看到，**listpack** 没有压缩列表中记录前⼀个节点长度的字段了，**listpack** 只记录当前节点的长度，当我们向**listpack** 加⼊⼀个新元素的时候，不会影响其他节点的长度字段的变化，从⽽避免了压缩列表的连锁更新问题。



### 反向遍历与变长编码机制

为了用极少字节存储自身长度并支持从右向左解析，`len` 采用了**特殊的变长编码（7 位有效位 + 1 位标记位）**：

```
最高位 (Bit 7): 
  0 -> 表示已到达该 length 字段的最左端字节（起始字节）
  1 -> 表示左侧还有更多属于 length 的字节
低 7 位 (Bit 0~6): 
  实际承载长度的数值部分
```

**反向定位前一个节点的执行过程：**

1. 从当前节点末尾向左读取字节。
2. 如果读到的字节最高位是 `1`，说明长度值还没读完，继续向左移动 1 个字节；直到读到最高位为 `0` 的字节，完成整个 `len` 的数值还原（最多扫描 5 个字节）。
3. 用当前位置指针减去算出的 `len`，即可**精准跳到当前节点的起始位置**。
4. 再向左移动 1 字节，即可直接获取**前一个节点的 `len` 尾部**，从而递归完成全表反向遍历。



### Ziplist 与 Listpack 对比

| **对比维度**       | **Ziplist（压缩列表）**                  | **Listpack（紧凑列表）**                  |
| ------------------ | ---------------------------------------- | ----------------------------------------- |
| **首尾元数据**     | `zlbytes` + `zltail` + `zllen` + `zlend` | `total_bytes` + `num_elements` + `0xFF`   |
| **尾部快速定位**   | 表头显式保存 `zltail` 偏移量             | 从末尾 `0xFF` 向左解析最后一个 `len`      |
| **节点存储内容**   | `prevlen` + `encoding` + `data`          | `encoding` + `data` + `len`               |
| **反向遍历依据**   | 读取当前节点的 `prevlen` 找前驱          | 解析自身末尾 `len` 反推节点头             |
| **连锁更新风险**   | **存在**（最坏复杂度 $O(N^2)$）          | **完全消除**（稳定 $O(N)$）               |
| **Redis 应用现状** | Redis 7.0 中已被全面废弃                 | 成为 Hash、ZSet、Quicklist 的标准底层编码 |





## 5. quicklist

**Quicklist（快速列表）** 是 Redis 专为 List 对象设计的核心底层数据结构，本质上是一个**以紧凑列表（Redis 7.0+ 为 Listpack，早期为 Ziplist）作为节点的双向无环链表**。

它在双向链表和紧凑内存结构之间取得了极致的性能与空间平衡。

| **方案**                              | **优点**                                                     | **缺点**                                                     |
| ------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **纯双向链表 (`adlist`)**             | 头尾及中间插入删除极快，节点独立无需大片连续内存。           | 每个节点附带两个指针（16B）和值指针（8B），**指针开销远超数据本身**，且内存碎片多、CPU 缓存命中率低。 |
| **纯紧凑列表 (`listpack`/`ziplist`)** | 零指针开销，物理内存连续，极度节省空间且 CPU 缓存友好。      | 存储大量数据时，每次增删都需 `realloc` 申请大块连续内存并拷贝数据，性能急剧下降。 |
| **Quicklist（折中方案）**             | **外层用双向链表串联，内层节点存放紧凑列表**。既保证了两端高效伸缩，又将内存分配限制在极小的固定块内。 |                                                              |



### 结构设计

![image-20260823194905008](/covers/java--redis-1--3-gzct2l/image-20260823194905008.png)



**控制器结构 `quicklist`**

- **`head` / `tail`**：分别指向头节点和尾节点。
- **`count`**：记录所有 `listpack` 节点中包含的**元素总数量**。
- **`len`**：记录 `quicklistNode` **链表节点的个数**。
- **`compress`**：压缩深度（即两端各有多少个节点不执行压缩）。

**节点结构 `quicklistNode`**

- **`prev` / `next`**：双向链表的前驱和后继指针。
- **`entry`**：指向实际存储数据的内存块（`listpack` 或压缩后的 `quicklistLZF` 结构体）。
- **`sz`**：当前 `listpack` 占用的总字节大小。
- **`count`**：当前 `listpack` 内部包含的元素项数量。
- **`encoding`**：编码模式，`1` 表示原生未压缩数据（RAW），`2` 表示经过 LZF 压缩的数据（LZF）。



### LZF 内存深度压缩机制

在大多数 List 业务场景中（如消息队列、最新时间线），程序主要访问的是列表**两端的元素**（`LPUSH`、`RPOP`、`LRANGE 0 10` 等），中间大量的历史数据极少被读写。

Quicklist 引入了基于 **LZF 算法** 的中间节点透明压缩机制：

- **两端节点保持未压缩（RAW）**：确保高频的首尾读写操作零解压耗时。
- **中间节点深度压缩（LZF）**：根据配置将中间节点的大段文本/二进制数据就地压缩，换取高达 40%~80% 的内存节省。
- **按需解压**：当需要读取中间某个压缩节点的数据时，临时解压读取，使用完毕后再重新压缩。





## 6. 哈希表

**哈希表** 是 Redis 的核心支柱结构，不仅用于实现外层的全局键值数据库，也是底层 `Hash` 和 `Set` 对象在大数据量或非纯整数场景下的标准实现容器。

### 结构设计

Redis 字典底层由字典控制器 `dict`、哈希表 `dictht`（Redis 7.0 整合优化为单表结构，但逻辑结构一致）以及哈希节点 `dictEntry` 组成：

![image-20260823201554458](/covers/java--redis-1--3-gzct2l/image-20260823201554458.png)



```c
/* 哈希表节点 */
typedef struct dictEntry {
    void *key;                // 键指针
    union {
        void *val;            // 值指针
        uint64_t u64;         // 64 位无符号整型
        int64_t s64;          // 64 位有符号整型
        double d;             // 双精度浮点型
    } v;
    struct dictEntry *next;   // 指向下一个节点（单链表解决哈希冲突）
} dictEntry;
```



### 哈希算法与冲突解决

**哈希算法（SipHash）**：

- Redis 采用 **SipHash** 算法计算 Key 的哈希值。该算法在处理短字符串时兼顾了极高的计算速度与抗碰撞能力，能有效防御通过构造相同哈希值发起的 **Hash-DoS 攻击**。
- **索引定位**：计算出哈希值后，通过掩码与运算快速定位槽位：$$\text{index} = \text{hash} \ \& \ \text{sizemask}$$（`sizemask` 永远为 $2^n - 1$，等价于对数组长度取模，但位运算性能更高）。



**链式哈希与头插法**：

![image-20260823201827596](/covers/java--redis-1--3-gzct2l/image-20260823201827596.png)

- 当不同 Key 命中同一槽位时，通过 `dictEntry.next` 形成单向链表。
- **单链表头插**：新节点总是直接插入到链表头部（$O(1)$），避免了遍历链表至尾部的开销。



### rehash

Redis 通过 **负载因子（Load Factor）** 决定是否需要扩容或缩容：

$$\text{Load Factor} = \frac{\text{已存节点数 } (\text{used})}{\text{哈希表数组大小 } (\text{size})}$$

| **操作类型** | **触发条件**                                                 | **目标分配容量**                                  |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------- |
| **正常扩容** | $\text{Load Factor} \ge 1$（且当前无后台持久化进程）         | 第一个大于等于 $\text{used} \times 2$ 的 $2^n$    |
| **迫切扩容** | $\text{Load Factor} \ge 5$（即使有 `BGSAVE` 或 `BGREWRITEAOF` 也强制执行） | 第一个大于等于 $\text{used} \times 2$ 的 $2^n$    |
| **自动缩容** | $\text{Load Factor} < 0.1$                                   | 第一个大于等于 $\text{used}$ 的 $2^n$（最小为 4） |

> **写时复制（CoW, Copy-On-Write）保护机制**：
>
> 当执行后台快照（RDB/AOF 重写）时，操作系统会使用 CoW 机制与子进程共享物理内存。为了避免哈希表扩容修改内存指针导致大量物理内存页发生复制污染，Redis 会在持久化期间将扩容门槛从 $1$ 临时拔高到 $5$。



在正常服务请求阶段，插⼊的数据，都会写⼊到「哈希表 1」，此时的「哈希表 2 」并没有被分配空间。随着数据逐步增多，触发了 rehash 操作，这个过程分为三步：

1. 给「哈希表 2」分配空间，⼀般会⽐「哈希表 1」⼤⼀倍（两倍的意思）；
2. 将「哈希表 1 」的数据迁移到「哈希表 2」中；
3. 迁移完成后，「哈希表 1 」的空间会被释放，并把「哈希表 2」设置为「哈希表 1」，然后在「哈希表 2」新创建⼀个空⽩的哈希表，为下次 rehash 做准备。

<img src="/covers/java--redis-1--3-gzct2l/image-20260823202314632.png" alt="image-20260823202314632" style="zoom:67%;" />

这个过程看起来简单，但是其实第⼆步很有问题，如果「哈希表 **1** 」的数据量⾮常⼤，那么在迁移⾄「哈希表 **2** 」的时候，因为会涉及⼤量的数据拷贝，此时可能会对 **Redis** 造成阻塞，⽆法服务其他请求。



### 渐进式 Rehash

如果哈希表包含数百万个 Key，一次性将其全部重新哈希并迁移到新表会直接造成 Redis 主线程严重卡顿。因此 Redis 采用了**分步、渐进式迁移**策略：

- 给「哈希表 2」分配空间；
- 在 **rehash** 进⾏期间，每次哈希表元素进⾏新增、删除、查找或者更新操作时，**Redis** 除了会执⾏对应的操作之外，还会顺序将「哈希表 **1** 」中索引位置上的所有 **key-value** 迁移到「哈希表 **2**」上；
- 随着处理客户端发起的哈希表操作请求数量越多，最终在某个时间点会把「哈希表 1 」的所有 key-value 迁移到「哈希表 2」，从⽽完成 rehash 操作。

```
       [ 触发 Rehash ]
              │
              ▼ 为 ht[1] 分配空间，设置 rehashidx = 0
              │
    ┌─────────┴─────────┐
    ▼                   ▼
【被动迁移 (CRUD 顺带)】    【主动迁移 (定时任务)】
 每次对 dict 执行操作        serverCron 周期性执行
 顺带迁移当前 1 个槽位        每次最多占用 1ms 迁移槽位
    │                   │
    └─────────┬─────────┘
              │
              ▼
    [ 所有槽位迁移完毕 (rehashidx 遍历至末尾) ]
              │
              ▼ 释放 ht[0]，将 ht[1] 设为 ht[0]，重置 rehashidx = -1
```

**Rehash 期间的读写行为**

在 Rehash 进行的过程中，客户端的所有读写命令均会受到双表逻辑的管控：

- **新增（Insert）**：**一律直接写入 `ht[1]`**，确保 `ht[0]` 的数据只减不增，保证迁移能够顺利收敛结束。
- **查找（Find）/ 修改（Update）/ 删除（Delete）**：
  - 先在 `ht[0]` 中查找；
  - 如果 `ht[0]` 没找到，再到 `ht[1]` 中查找。



## 7. 整数集合（Intset）

**整数集合（Intset）** 是 Redis 专为集合对象（Set）设计的底层内存结构。当一个 Set 集合内的**所有元素都是整数**且**元素数量较少**时，Redis 会优先采用 Intset 存储，以获得极致的内存压缩率与高效的二分查找性能。

### 结构设计

Intset 本质上是一个有序、无重复、紧凑连续的内存数组：

```c
typedef struct intset {
    uint32_t encoding; // 编码方式：决定数组每个元素占用的字节宽度
    uint32_t length;   // 集合中包含的元素总个数
    int8_t contents[]; // 柔性数组，存储实际数据（连续内存）
} intset;
```

- **`encoding`（编码类型）**：
  - `INTSET_ENC_INT16`：每个元素占用 2 字节（$-2^{15} \sim 2^{15}-1$）。
  - `INTSET_ENC_INT32`：每个元素占用 4 字节（$-2^{31} \sim 2^{31}-1$）。
  - `INTSET_ENC_INT64`：每个元素占用 8 字节（$-2^{63} \sim 2^{63}-1$）。
- **`contents[]` 数组**：
  - 虽然声明为 `int8_t`，但实际每个元素的物理字节大小完全由 `encoding` 决定。
  - 数组内的所有元素**按从小到大的升序严格排列**，且**不存在任何重复元素**。



### 运行特性

- **$O(\log N)$ 检索性能**：由于底层数组连续且天然有序，判断元素是否存在（`SISMEMBER`）或定位插入位置时直接使用**二分查找（Binary Search）**。
- **零指针开销**：不需要像哈希表那样维护 `dictEntry`、哈希桶指针和单链表指针，整块数据是一整段紧凑的物理内存，CPU 缓存命中率极高。



### 自动升级机制

当尝试将一个超出当前编码范围的新整数插入集合时（例如当前为 `INT16`，新插入一个数值 `65535`），Intset 会自动触发升级（Upgrade）流程：

```
原始内存 (INT16, 2 字节/元素):
[ 10 ] [ 20 ] [ 30 ]

插入 70000 (需要 INT32) -> 触发升级:
1. 扩容内存：重新分配 4 * sizeof(int32) = 16 字节
2. 从后往前搬迁旧数据，将其扩展为 32 位宽：
   [ 30 扩为 4B ] -> [ 20 扩为 4B ] -> [ 10 扩为 4B ]
3. 写入新元素 70000：
   [ 10 (4B) ] [ 20 (4B) ] [ 30 (4B) ] [ 70000 (4B) ]
4. 修改 encoding 为 INTSET_ENC_INT32，length 更新为 4
```

**升级步骤详解**：

1. **重新分配内存**：根据新元素的编码类型，重新计算并申请扩容后的总内存大小：

   $$\text{新空间} = (\text{原元素个数} + 1) \times \text{新类型字节数}$$

2. **从后向前位移与类型转换**：为了避免数据覆盖，系统从现有数据的最末尾元素开始，依次将其转换为新的位宽并放置到对应的新下标槽位。

3. **定位并插入新元素**：由于新元素是因为“数值过大”或“绝对值过大的负数”才引发的升级，因此新元素要么大于所有现有元素（插在数组最末端），要么小于所有现有元素（插在数组最前端 0 号索引）。

4. **复杂度**：升级涉及全量数组的内存重构与搬迁，单次触发的时间复杂度为 $O(N)$。



**好处**

如果要让⼀个数组同时保存 int16_t、int32_t、int64_t 类型的元素，最简单做法就是直接使⽤ int64_t 类型的数组。不过这样的话，当如果元素都是 int16_t 类型的，就会造成内存浪费的情况。

整数集合升级就能避免这种情况，如果⼀直向整数集合添加 int16_t 类型的元素，那么整数集合的底层实现就⼀直是⽤ int16_t 类型的数组，只有在我们要将 int32_t 类型或 int64_t 类型的元素添加到集合时，才会对数组进⾏升级操作。

因此，整数集合升级的好处是**节省内存资源**。



 **为什么不支持降级**

当删除了集合中唯一的 64 位大整数后，即使剩余的所有整数均在 16 位范围内，Intset 也**不会执行降级操作**，编码格式将永久保留在 `INTSET_ENC_INT64`。

- **原因**：检查是否所有剩余元素都满足降级条件需要遍历全表计算最大/最小值，且降级同样需要重新申请内存与整段数据搬迁。为了防止频繁插入/删除临界值导致系统反复重构内存，Redis 放弃了降级支持，用少量内存空间换取执行性能的稳定性。



### Set转换触发条件

当集合遇到以下任意一种情况时，底层编码会自动从 `intset` 转换为 `hashtable`（字典）：

| **转换条件**     | **默认阈值 / 规则**                              | **对应配置项**                  |
| ---------------- | ------------------------------------------------ | ------------------------------- |
| **元素数量超标** | 集合元素个数超过 **512** 个                      | `set-max-intset-entries`        |
| **类型不匹配**   | 向集合中插入了**任何非整数元素**（如普通字符串） | 无法通过升级容纳，直接转为 Dict |





## 8. 跳表（Skiplist）

**跳跃表（Skiplist，简称跳表）** 是 Redis 有序集合（ZSet）的核心底层数据结构之一。它在普通有序双向链表之上增加了多层“前进指针”索引，以空间换时间，实现了平均 **$O(\log N)$** 的查找、插入、删除以及高效的范围检索。

### 结构设计

Redis 的跳表由表头管理结构 `zskiplist` 和节点结构 `zskiplistNode` 构成：

Zset 对象要同时保存「元素」和「元素的权重」，对应到跳表节点结构⾥就是 sds 类型的 ele 变量和 double 类型的score 变量。每个跳表节点都有⼀个后向指针，指向前⼀个节点，⽬的是为了⽅便从跳表的尾节点开始访问节点，这样倒序查找时很⽅便。

```c
/* 跳表节点 */
typedef struct zskiplistNode {
    sds ele;                                // 成员对象 (member，唯一字符串)
    double score;                           // 分值 (用于排序依据)
    struct zskiplistNode *backward;         // 后退指针 (仅在最底层 level 0 生效，用于从后向前遍历)、
    
    struct zskiplistLevel {
        struct zskiplistNode *forward;      // 前进指针 (跳跃访问后续节点)
        unsigned long span;                 // 跨度 (记录当前层该指针跨过了多少个底层节点)
    } level[];                              // 柔性数组，多层索引
} zskiplistNode;

/* 跳表控制器 */
typedef struct zskiplist {
    struct zskiplistNode *header, *tail;    // 头尾节点指针
    unsigned long length;                   // 节点总数 (不含头节点)
    int level;                              // 当前跳表中所有节点的最大层高
} zskiplist;
```

链表在查找元素的时候，因为需要逐⼀查找，所以查询效率⾮常低，时间复杂度是O(N)，于是就出现了跳表。跳表是在链表基础上改进过来的，实现了⼀种「多层」的有序链表，这样的好处是能快读定位数据。

那跳表长什么样呢？下图展⽰了⼀个层级为 3 的跳表。

![image-20260823205658642](/covers/java--redis-1--3-gzct2l/image-20260823205658642.png)

头节点有 L0~L2 三个头指针，分别指向了不同层级的节点，然后每个层级的节点都通过指针连接起来：

- L0 层级共有 5 个节点，分别是节点1、2、3、4、5；
- L1 层级共有 3 个节点，分别是节点 2、3、5；
- L2 层级只有 1 个节点，也就是节点 3 。

如果我们要在链表中查找节点 4 这个元素，只能从头开始遍历链表，需要查找 4 次，⽽使⽤了跳表后，只需要查找2 次就能定位到节点 4，因为可以在头节点直接从 L2 层级跳到节点 3，然后再往前遍历找到节点 4。



跳表是⼀个带有层级关系的链表，⽽且每⼀层级可以包含多个节点，每⼀个节点通过指针连接起来，实现这⼀特性就是靠跳表节点结构体中的**zskiplistLevel** 结构体类型的 **level** 数组。

level 数组中的每⼀个元素代表跳表的⼀层，也就是由 zskiplistLevel 结构体表⽰，⽐如 leve[0] 就表⽰第⼀层，leve[1] 就表⽰第⼆层。zskiplistLevel 结构体⾥定义了「指向下⼀个跳表节点的指针」和「跨度」，跨度时⽤来记录两个节点之间的距离。

下⾯这张图，展⽰了各个节点的跨度。

![image-20260823210437975](/covers/java--redis-1--3-gzct2l/image-20260823210437975.png)

跨度实际上是为了计算这个节点在跳表中的排位。具体怎么做的呢？因为跳表中的节点都是按序排列的，那么计算某个节点排位的时候，从头节点点到该结点的查询路径上，将沿途访问过的所有层的跨度累加起来，得到的结果就是⽬标节点在跳表中的排位。

查找图中节点 3 在跳表中的排位，从头节点开始查找节点 3，查找的过程只经过了⼀个层（L2），并且层的跨度是 3，所以节点 3 在跳表中的排位是 3。





###  核心机制

**跨度（`span`）与 $O(\log N)$ 排名计算**

Redis 在每个前进指针上记录了 `span`（跨度）。

- **作用**：表示从当前节点通过该指针到达下一个节点时，中间跳过了多少个最底层（Level 0）节点。
- **排名计算（`ZRANK`）**：查找某个元素时，沿着跳表路径将所有经过指针的 `span` 累加，即可在 **$O(\log N)$** 时间内精准算出当前元素的绝对排位（Rank），无需像普通链表那样线性逐个计数。



**随机层高生成算法（`zslRandomLevel`）**

跳表不使用平衡树复杂的旋转调整，而是通过**抛硬币式的概率算法**决定新节点的层高：

- **最大层高**：`ZSKIPLIST_MAXLEVEL = 32`（理论上可容纳 $2^{32}$ 个元素）。
- **概率因子**：$P = 0.25$（每次以 $25\%$ 的概率增加一层）。
- **平均指针数**：每个节点平均仅占用 $\frac{1}{1 - 0.25} \approx 1.33$ 个指针，内存开销极低。



**元素排序规则**

跳表中所有节点严格按照以下顺序升序排列：

1. **优先比较 `score`**：分值小的排在前面。
2. **分值相同时比较 `ele`（SDS）**：按字符串字典序（二进制字节比对）排列，确保节点有序且唯一。





**查找**

查找⼀个跳表节点的过程时，跳表会从头节点的最⾼层开始，逐⼀遍历每⼀层。在遍历某⼀层的跳表节点时，会⽤跳表节点中的 SDS 类型的元素和元素的权重来进⾏判断，共有两个判断条件：

- 如果当前节点的权重「⼩于」要查找的权重时，跳表就会访问该层上的下⼀个节点。
- 如果当前节点的权重「等于」要查找的权重时，并且当前节点的 SDS 类型数据「⼩于」要查找的数据时，跳表就会访问该层上的下⼀个节点。

如果上⾯两个条件都不满⾜，或者下⼀个节点为空时，跳表就会使⽤⽬前遍历到的节点的 level 数组⾥的下⼀层指针，然后沿着下⼀层指针继续查找，这就相当于跳到了下⼀层接着查找。

举个例⼦，下图有个 3 层级的跳表。

![image-20260823210713377](/covers/java--redis-1--3-gzct2l/image-20260823210713377.png)

如果要查找「元素：abcd，权重：4」的节点，查找的过程是这样的：

1. 先从头节点的最⾼层开始，L2 指向了「元素：abc，权重：3」节点，这个节点的权重⽐要查找节点的⼩，所以要访问该层上的下⼀个节点；
2. 但是该层的下⼀个节点是空节点（ leve[2]指向的是空节点），于是就会跳到「元素：abc，权重：3」节点的下⼀层去找，也就是 leve[1];
3. 「元素：abc，权重：3」节点的  leve[1] 的下⼀个指针指向了「元素：abcde，权重：4」的节点，然后将其和要查找的节点⽐较。虽然「元素：abcde，权重：4」的节点的权重和要查找的权重相同，但是当前节点的SDS 类型数据「⼤于」要查找的数据，所以会继续跳到「元素：abc，权重：3」节点的下⼀层去找，也就是leve[0]；
4. 「元素：abc，权重：3」节点的 leve[0] 的下⼀个指针指向了「元素：abcd，权重：4」的节点，该节点正是要查找的节点，查询结束。





 **为什么选跳表而不是红黑树或 B+ 树？**

| **对比维度**            | **跳跃表 (Skiplist)**                         | **红黑树 / 平衡二叉树**                              | **B+ 树**                        |
| ----------------------- | --------------------------------------------- | ---------------------------------------------------- | -------------------------------- |
| **范围查询 (`ZRANGE`)** | **极快**（定位边界后在 Level 0 顺序遍历即可） | 较差（需要通过中序遍历回溯父节点与子树）             | 快（底层叶子节点为链表）         |
| **排名计算 (`ZRANK`)**  | **$O(\log N)$**（通过 `span` 字段直接累加）   | 较难（需要在每个树节点维护子树大小字段并维护重平衡） | 较复杂                           |
| **并发与实现复杂度**    | **实现简单**，易于维护与调试，改动无连锁旋转  | 实现极其复杂，插入删除需要复杂的旋转变色             | 节点分裂与合并较复杂             |
| **内存开销调节**        | 可通过调节概率参数 $P$ 动态平衡内存与查询速度 | 树节点指针数量固定（2~3 个指针）                     | 适合磁盘块对齐，纯内存下碎片较多 |



### Dict + Skiplist

当 ZSet 不再满足 `listpack` 编码阈值（元素数 $\ge 128$ 或成员大小 $\ge 64$ 字节）时，底层会采用 `zset` 结构体，**同时维护一个字典和一个跳表**：

```c
typedef struct zset {
    dict *dict;         // 字典：key 是 member，value 是 score
    zskiplist *zsl;     // 跳表：按 score 升序组织 member
} zset;
               ┌──► dict:      member ──────► score  (支持 O(1) ZSCORE)
客户端命令 ────┤
               └──► zskiplist: [score, member] ──► ... (支持 O(log N) 范围与排名)
```

- **双重索引，零内存冗余**：`dict` 和 `zskiplist` 中的 `member`（SDS 字符串）均指向**同一块物理内存**，仅是指针引用，不会造成数据的双倍内存占用。
- **兼顾全场景性能**：
  - 执行 `ZSCORE key member`：直接查询 `dict`，时间复杂度为 **$O(1)$**。
  - 执行 `ZRANGE`、`ZRANK`、`ZREMRANGEBYSCORE`：走 `zskiplist`，时间复杂度为 **$O(\log N) + M$**。
