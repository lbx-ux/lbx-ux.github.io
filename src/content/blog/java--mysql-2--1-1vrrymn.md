# 一. MySQL体系结构

MySQL 采用了非常经典的**分层架构设计**。这种设计的核心理念是“各司其职，高度解耦”，尤其是它独创的“插件式存储引擎”架构，使得 MySQL 既能处理高并发的电商交易，也能应对数据仓库的分析查询。

MySQL 的体系结构可以自上而下划分为**四个核心层次**：

![image-20260818101130530](/covers/java--mysql-2--1-1vrrymn/image-20260818101130530.png)

## 1. 连接层

这是 MySQL 的“大门”，主要负责处理客户端（如你的代码、Navicat 或命令行）与 MySQL 服务器之间的网络通信。

- **连接池 (Connection Pool)：** 负责缓存和管理与客户端建立的连接。客户端断开后，连接不会立刻销毁，而是放回池中复用，以此减少频繁建立/销毁 TCP 连接的开销。
- **鉴权与安全：** 当你连接时，这一层会验证你的用户名、密码，以及你试图访问的库或表是否具有相应的权限。



## 2. 服务层

这是 MySQL 的“大脑”，绝大多数的核心功能（跨存储引擎的通用功能）都在这里完成。

- **SQL 接口 (SQL Interface)：** 接收你的 DML（增删改查）、DDL（建表等）语句，并返回查询结果。
- **解析器 (Parser)：** 将你写的 SQL 字符串拆解、校验。它会进行**词法分析**（识别出 `SELECT`、表明、列名）和**语法分析**（检查你的 SQL 语句是否符合规则）。如果写错了（比如拼错了关键字），报错就是在这里生成的。
- **优化器 (Optimizer)：** MySQL 会在这里决定你的 SQL “怎么执行最快”。它会评估各种执行计划，比如决定使用哪个索引，或者在多表 `JOIN` 时决定连接的先后顺序。
- **缓存与缓冲 (Caches & Buffers)：** 曾经这里包含“查询缓存”（Query Cache），但因为命中率低且维护成本高，**MySQL 8.0 版本已经彻底移除了查询缓存**。现在的缓存主要指表缓存、权限缓存等。



## 3. 引擎层

这是 MySQL 的“双手”，负责底层数据的**实际存储和提取**。

- **插件式架构：** 服务层通过 API 与引擎层通信，这些 API 屏蔽了不同存储引擎的差异。
- 正如之前提到的，你可以为不同的表选择不同的引擎（如 **InnoDB** 负责高并发事务，**MyISAM** 负责简单的历史数据查询）。
- 注意：索引的底层具体实现（如 B+ 树）是由存储引擎决定的，而不是服务层决定的。



## 4. 存储层

这是 MySQL 的“仓库”，数据最终落地的物理文件，直接依托于操作系统（如 Linux）的文件系统。

- **数据文件：** 例如 InnoDB 的 `.ibd` 文件，存储着实际的表数据和索引数据。
- **日志文件：** 包含 `redo log`（重做日志）、`undo log`（回滚日志）、`binlog`（归档/主从同步日志）以及错误日志、慢查询日志等。这些日志是 MySQL 保障数据安全和实现集群同步的基石。

> **一句话总结一条 `SELECT` 的旅程：**
>
> 客户端通过**连接层**进入系统 ➔ **服务层**的解析器看懂你的 SQL ➔ 优化器选定最优方案（用哪个索引） ➔ 调用**引擎层**的 API ➔ 引擎层去**存储层**的磁盘/内存中把数据捞出来，层层返回给你。



# 二. SQL执行流程

>**一句话总结一条 `SELECT` 的旅程：**
>
>客户端通过**连接层**进入系统 ➔ **服务层**解析并优化 SQL  ➔ 调用**引擎层**的 API ➔ 引擎层去**存储层**的磁盘/内存中把数据捞出来，层层返回给你。



>**一句话总结一条 `UPDATE` 的旅程：**
>
>客户端通过**连接层**进入系统 ➔ **服务层**解析并优化 SQL ➔ 执行器调用**引擎层**查找到待修改的旧数据 ➔ 引擎层记录旧值到 **undo log** 并更新内存数据（产生“脏页”） ➔ 引擎层将操作写入 **redo log**（标记为 `prepare` 状态） ➔ 服务层将逻辑操作写入 **binlog** ➔ 引擎层将 **redo log** 状态改为 `commit`（完成两阶段提交） ➔ 向客户端返回成功。
>
>### 核心记忆法：UPDATE 的“一找、一改、三日志”
>
>如果觉得上面的流程太长，可以把执行器接手后的核心更新动作提炼为以下 5 步：
>
>1. **一找：** 引擎层去内存或磁盘中把要更新的这行数据找出来。
>2. **写 Undo Log（防后悔）：** 先把修改前的“老数据”记下来，万一要回滚就靠它。
>3. **一改：** 直接在内存（Buffer Pool）中修改这行数据，此时磁盘上的数据还没变。
>4. **写 Redo Log - 准备（防断电）：** 把刚才做的物理修改记下来，状态设为 `prepare`。
>5. **写 Binlog 并最终提交（防不同步）：** 服务层写完归档逻辑日志 `binlog` 后，通知引擎把刚才的 `redo log` 状态改成 `commit`，彻底完成更新。



查询语句（SELECT）**和**更新语句（UPDATE/INSERT/DELETE）的执行流程有很大的区别。我们先来看所有语句都会经历的“前半段”：

1. **连接器（Connector）：** 建立网络连接，校验账号密码，查出你的权限。
2. **解析器（Parser）：**
   - *词法分析：* 识别出表名、列名、关键字。
   - *语法分析：* 检查你写的 SQL 是否符合 MySQL 语法（如果不符合，就会报 `You have an error in your SQL syntax`）。
3. **优化器（Optimizer）：** 决定这条 SQL 怎么执行最高效。如果有多个索引，选哪个？如果是多表 JOIN，先查哪张表？生成最终的**执行计划**。

过了这三步后，接下来就由执行器（Executor）接手，调用存储引擎的 API 来干活了



## A: 查询语句

查询的流程相对简单直接：

**1.权限复核:**

执行器在开始执行前，会再次判断你对这个表有没有查询权限。

**2.调用引擎读取:**

执行器根据优化器生成的执行计划，调用存储引擎的 API 接口（例如：“取满足条件的第一行”、“取下一行”）。

**3.数据过滤与返回:**

存储引擎去内存或磁盘中把数据找出来，返回给执行器。执行器如果发现有服务层需要处理的条件（比如 `LIMIT` 或没有走索引的 `WHERE` 条件），会在这一层进行过滤。最后将结果集返回给客户端。



## B: 更新语句

更新语句比查询语句复杂得多，因为它不仅要改数据，还要保证**数据不能丢（持久性）以及可以反悔（回滚）**。

在 InnoDB 引擎下，更新操作引入了著名的“两阶段提交”（Two-Phase Commit）和三大日志：`undo log`（回滚日志）、`redo log`（重做日志）和 `binlog`（归档日志）。

假设我们执行：`UPDATE users SET age = age + 1 WHERE id = 1;`

**1.查找并加载数据:**

执行器先找引擎取 `id=1` 这一行。如果这一行所在的数据页已经在内存（Buffer Pool）中，引擎直接返回；如果不在，引擎先从磁盘读入内存，再返回。

**2.写入 Undo Log（防后悔）:**

在修改内存数据之前，InnoDB 会先把原来的旧值（`age` 修改前的值）记录到 `undo log` 中。万一事务执行一半报错了，或者你手动 `ROLLBACK`，就可以用它来恢复。

**3.更新内存数据:**

执行器拿到数据后把 `age` 加 1，再调用引擎接口把新数据写回去。引擎将这个新数据更新到内存（Buffer Pool）中。**注意：此时数据并没有立刻写回磁盘，这叫“脏页”。**

**4.写入 Redo Log - 准备阶段 (Prepare):**

为了防止机器突然断电导致内存里的“脏页”丢失，引擎会把这次修改的操作（物理日志，例如“在某个数据页上做了什么修改”）记录到 `redo log` 中，并将状态标记为 `prepare`。

**5.写入 Binlog (记录逻辑):**

执行器生成这次操作的 `binlog`（逻辑日志，例如“把 id=1 的 age 改成了某某值”），并把 `binlog` 写入磁盘。这是为了以后的数据备份或主从同步。

**6.写入 Redo Log - 提交阶段 (Commit):**

执行器调用引擎的提交事务接口，引擎把刚刚写入的 `redo log` 状态改成 `commit`。至此，更新完成。

> **关键机制：为什么要“两阶段提交”？**
>
> 这是为了保证 `redo log`（本机崩溃恢复用）和 `binlog`（主从同步或备份恢复用）的一致性。如果只写一个就宕机，会导致主库和从库的数据不一致。只有两个日志都写成功，状态变成 `commit`，这次事务才算真正成功。



# 三. 存储引擎

MySQL 的存储引擎是其最核心的特性之一。与其他主流数据库（如 Oracle 或 SQL Server）不同，MySQL 采用了**插件式存储引擎架构（Pluggable Storage Engine Architecture）**。

这意味着 MySQL 将查询处理和其他系统任务与数据的存储/提取分离开来。你可以根据具体的业务需求，**为数据库中的每一张表指定不同的存储引擎**。



## 1. 核心存储引擎介绍

在 MySQL 中，最常用的存储引擎主要有以下几种：

### 1. InnoDB

自 MySQL 5.5 版本起，InnoDB 成为默认存储引擎。它专为处理高并发和保障数据完整性而设计，是绝大多数业务场景的首选。

- **支持事务（ACID）：** 保证了操作的原子性、一致性、隔离性和持久性。
- **行级锁（Row-Level Locking）：** 在执行写操作时只锁定被操作的行，极大提高了多用户并发性能。
- **外键（Foreign Keys）：** 强制保证数据库中表与表之间的引用完整性。
- **MVCC（多版本并发控制）：** 允许读写操作并发执行而互不阻塞。
- **崩溃恢复（Crash Recovery）：** 通过 Redo Log 和 Undo Log 机制，在数据库意外宕机后能够自动恢复未提交的事务，保证数据不丢失。



### 2. MyISAM

在 Web 2.0 早期非常流行，但随着应用对并发和事务要求的提高，逐渐被 InnoDB 取代。

- **不支持事务和外键：** 无法回滚，一旦发生错误可能导致数据不一致。
- **表级锁（Table-Level Locking）：** 每次更新数据都会锁住整张表，并发写性能较差。
- **优势：** 引擎设计简单，占用存储空间较小，且在纯读取场景下速度极快（内置了一个变量记录表的总行数，执行 `SELECT COUNT(*)` 瞬间完成）。



### 3. Memory

将所有数据存储在 RAM（内存）中，一旦数据库重启或崩溃，**数据会全部丢失**（但表结构会保留）。

- **极高的访问速度：** 适合用作临时表、缓存表或存储极少更新的静态字典数据。
- **限制：** 使用表级锁，且不支持 BLOB 和 TEXT 等大字段类型。



## 2. 对比

| **特性评估**                | **InnoDB**          | **MyISAM**      | **Memory**        |
| --------------------------- | ------------------- | --------------- | ----------------- |
| **事务安全 (Transaction)**  | **支持**            | 不支持          | 不支持            |
| **锁粒度 (Locking)**        | **行锁** (极佳并发) | 表锁 (并发差)   | 表锁              |
| **外键支持 (Foreign Keys)** | **支持**            | 不支持          | 不支持            |
| **并发控制 (MVCC)**         | **支持**            | 不支持          | 不支持            |
| **系统崩溃恢复**            | **支持** (安全)     | 不支持 (易损坏) | 不支持 (数据清空) |
| **数据存储位置**            | 磁盘                | 磁盘            | **内存**          |



## 3. 常用操作命令

如果你想在 MySQL 中查看或更改存储引擎，可以使用以下基础 SQL 命令：

- **查看当前 MySQL 支持的全部存储引擎：**

```sql
show engines;
```

- **建表时指定存储引擎：**

```sql
create table 表名(
	字段1 字段1类型 ,
)engine=存储引擎
存储引擎默认为innodb
```

- **修改已有表的存储引擎：**

```sql
alter rable 表名 engine=存储引擎
```
