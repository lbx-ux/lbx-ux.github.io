# 一. 介绍

索引（index）是帮助MySQL**高效获取数据**的**数据结构(有序)**。在数据之外，数据库系统还维护着满足特定查找算法的数据结构，这些数据结构以某种方式引用（指向）数据，这样就可以在这些数据结构上实现高级查找算法，这种数据结构就是索引

索引（Index）是一种**数据结构**，用于**快速查询和检索**表中的数据，类似于书的“目录”——通过目录快速找到对应的页面，而不需要逐页翻书。

|                            优势                             |                             劣势                             |
| :---------------------------------------------------------: | :----------------------------------------------------------: |
|           提高数据检索的效率，降低数据库的IO成本            |                    索引列也是要占用空间的                    |
| 通过索引列对数据进行排序，降低数据排序的成本，降低CPU的消耗 | 索引大大提高了查询效率，同时却也降低更新表的速度，如对表进行INSERT、UPDATE、DELETE时，效率降低 |



# 二. 底层数据结构

MySQL的索引是在存储引擎层实现的，不同的存储引擎有不同的索引结构，主要包含以下几种：

|      索引结构       |                             描述                             |
| :-----------------: | :----------------------------------------------------------: |
|     B+Tree索引      |         最常见的索引类型，大部分引擎都支持 B+ 树索引         |
|      Hash索引       | 底层数据结构是用哈希表实现的，只有**精确匹配索引列**的查询才有效，不支持范围查询 |
|  R-tree(空间索引)   | 空间索引是MyISAM引擎的一个特殊索引类型，主要用于**地理空间数据类型**，通常使用较少 |
| Full-text(全文索引) | 是一种通过建立倒排索引,快速匹配文档的方式。类似于Lucene,Solr,ES |

上述是MySQL中所支持的所有的索引结构，接下来，我们再来看看不同的存储引擎对于索引结构的支持情况。

|    索引     | InnoDB | MyISAM | Memory |
| :---------: | :----: | :----: | :----: |
| B+tree索引  |  支持  |  支持  |  支持  |
|  Hash 索引  | 不支持 | 不支持 |  支持  |
| R-tree 索引 | 不支持 |  支持  | 不支持 |
|  Full-text  |  支持  |  支持  | 不支持 |

注意：我们平常所说的索引，如果没有特别指明，都是指B+Tree结构组织的索引。

但是，即使如此，由于红黑树也是一颗二叉树，所以也会存在一个缺点：

- 大数据量情况下，层级较深，检索速度慢。

所以，在MySQL的索引结构中，并没xsa有选择二叉树或者红黑树，而选择的是B+Tree，那么什么是B+Tree呢？在详解B+Tree之前，先来介绍一个B-Tree。



## 2. B-Tree

B-Tree，B树是一种**多路平衡查找树**，相对于二叉树，B树每个节点可以有多个分支，即多叉。

以一颗最大度数（max-degree）为5(5阶)的b-tree为例，那这个B树每个节点最多存储4个key，5个指针：

![image-20260818165716817](/covers/java--mysql-2--2-tkettk/image-20260818165716817.webp)


知识小贴士：树的度数指的是一个节点的子节点个数。

- 5阶的B树，每一个节点最多存储4个key，对应5个指针。

- 一旦节点存储的key数量到达5，就会裂变，中间元素向上分裂。

- 在B树中，非叶子节点和叶子节点都会存放数据。

**插入溢出**：选中间值向上提，左右分为两个子节点；若根分裂则树高 + 1



## 3. B+Tree

B+Tree是B-Tree的变种，我们以一颗最大度数（max-degree）为4（4阶）的b+tree为例，来看一下其结构示意图：

![image-20260818170946044](/covers/java--mysql-2--2-tkettk/image-20260818170946044.webp)


我们可以看到，两部分：

- 绿色框框起来的部分，是索引部分，仅仅起到索引数据的作用，不存储数据。

- 红色框框起来的部分，是数据存储部分，在其叶子节点中要存储具体的数据。

最终我们看到，B+Tree 与 B-Tree 相比，主要有以下三点区别：

- 所有的数据都会出现在叶子节点。

- 叶子节点形成一个单向链表。

- 非叶子节点仅仅起到索引数据作用，具体的数据都是在叶子节点存放的。



上述我们所看到的结构是标准的B+Tree的数据结构，接下来，我们再来看看MySQL中优化之后的B+Tree。

MySQL索引数据结构对经典的B+Tree进行了优化。在原B+Tree的基础上，增加一个指向相邻叶子节点的链表指针，就形成了带有顺序指针（循环双向链表）的B+Tree，提高区间访问的性能，利于排序。

![image-20260818171516365](/covers/java--mysql-2--2-tkettk/image-20260818171516365.webp)

- **非叶子节点仅存索引与指针**：不包含任何行记录数据（Data），仅保存 `Key` 以及指向下级子节点的 `Pointer`。
- **数据全量沉淀在叶子节点**：所有记录（完整的行数据或主键 ID）全部保存在叶子节点中。非叶子节点出现的 Key 必然会再次出现在叶子节点中。
- **叶子节点双向链表相连**：所有叶子节点处于同一物理层级，且按 Key 大小顺序通过**双向链表**串联。
- **树高极低且查询路径恒定**：任何单点查询均需自顶向下走到叶子节点，查询时间复杂度严格稳定在 O(\log N)。





**InnoDB 中 3 层 B+ 树能存多少数据？**

以 MySQL InnoDB 默认页大小16KB为例进行容量推导：

1. **非叶子节点（索引页）**：
   - 假设主键为 `BIGINT`（占用 8Byte），指针占用 6Byte。
   - 单个索引项大小 8 + 6=14Byte。
   - 单页可容纳指针数 16KB / 14Byte = 1170 个。
2. **叶子节点（数据页）**：
   - 假设每行实际业务数据占用 1KB。
   - 单个叶子数据页可存储 16KB / 1KB=16 行记录。
3. **容量计算**：
   - **高度为 2**：1170 * 16 -18720 条记录。
   - **高度为 3**：1170 * 1170 * 16 = 2190 万条记录。

> 这意味着在千万级数据量下，InnoDB 仅需 **3 次 I/O**（其中根节点常驻内存，实际仅 1~2 次物理磁盘读取）即可精准定位任意单条记录。



| **维度**                  | **B+ Tree**                                    | **B-Tree**                                         | **为什么 B+ 树更优？**                                       |
| ------------------------- | ---------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------ |
| **单页 Key 容量（扇出）** | **极大**（非叶子节点不存 Data）                | 较小（每个节点都被 Data 占用空间）                 | 同样大小的内存页（如 16KB），B+ 树能存更多索引项，树高度更低。 |
| **树高度与磁盘 I/O**      | **极低（通常 2~4 层）**                        | 相对较高（4~6 层甚至更高）                         | 树每高一层，查询就多一次磁盘寻道与 I/O 读取。                |
| **范围查询能力**          | **极快**（只需定位左边界，沿链表顺序向后扫描） | 较慢（需通过复杂的中序遍历跨层递归回溯）           | 关系型数据库大量包含 `BETWEEN`、`>`、`<`、`ORDER BY` 等操作。 |
| **内存缓存利用率**        | **极高**（根节点与非叶子节点可全部常驻内存）   | 较低（数据混在节点中，内存放不下几层）             | 绝大多数查询前 2 次路由判断在内存中即可完成，仅最后一步访问磁盘。 |
| **查询稳定性**            | **绝对稳定**（所有查询固定遍历到叶子层）       | 不稳定（根节点命中为 1 次，叶子节点命中为 $H$ 次） | 业务响应时间（P99）波动极小。                                |

**节点分裂机制的差异（以插入为例）**

B+ 树与 B-Tree 在节点溢出时的分裂逻辑存在本质不同：

- **B-Tree 分裂**：将中位数 Key **移出并提升**到父节点，原节点一分为二（该 Key 在子节点中消失）。
- **B+ Tree 分裂**：
  - **叶子节点分裂**：将中位数 Key **复制一份提升**到父节点，同时该 Key 仍保留在右侧新叶子节点中，并通过指针维持叶子链表连续性。
  - **非叶子节点分裂**：与 B-Tree 一致，将中位数 Key 向上提升，作为纯路由索引。



## 4. Hash

哈希索引就是采用一定的hash算法，将键值换算成新的hash值，映射到对应的槽位上，然后存储在hash表中。

![image-20260818180109528](/covers/java--mysql-2--2-tkettk/image-20260818180109528.webp)


如果两个 (或多个) 键值，映射到一个相同的槽位上，他们就产生了hash冲突（也称为hash碰撞），可以通过链表来解决。

![image-20260818180150819](/covers/java--mysql-2--2-tkettk/image-20260818180150819.webp)

A. Hash索引只能用于对等比较 (=, in), 不支持范围查询 (between, >, <, <)

B. 无法利用索引完成排序操作

C. 查询效率高, 通常 (不存在hash冲突的情况) 只需要一次检索就可以了, 效率通常要高于B+tree索引



在MySQL中，支持hash索引的是Memory存储引擎，而InnoDB中具有自适应hash功能，不支持手动创建，hash索引是InnoDB存储引擎根据B+Tree索引在指定条件下自动构建的。

# 三. 索引分类

MySQL 的索引通常从**数据结构**、**物理存储**、**逻辑约束**和**字段列数**四个维度进行分类：

## 1. 数据结构

- **B+Tree 索引**：MySQL（InnoDB 与 MyISAM 引擎）默认且最核心的索引类型。非叶子节点仅存储键值和子节点指针，所有数据记录（或行指针）均保存在叶子节点，叶子节点之间通过双向链表相连，极其适合**等值查询、范围检索（BETWEEN、>、<）及 ORDER BY 排序**。
- **Hash 索引**：基于哈希表实现。仅支持精确等值匹配（`=`、`IN`、`<=>`），查询时间复杂度接近 $O(1)$。**不支持范围查询、模糊匹配与排序**。Memory 存储引擎原生支持；InnoDB 会根据访问频次自动在内存中构建**自适应哈希索引（AHI）**。
- **Full-Text 索引（全文索引）**：基于倒排索引（Inverted Index）机制，用于快速检索长文本中的关键字，替代效率低下的 `LIKE '%text%'` 查询。
- **R-Tree 索引（空间索引）**：专用于 `GEOMETRY`、`POINT` 等地理空间数据类型，支持多维空间对象的包含、相邻与相交判断。



## 2. 物理存储

- **聚簇索引**：

  - **数据与索引强绑定**：叶子节点直接存放完整的整行数据记录。

  - 一张 InnoDB 表**有且仅有一个**聚簇索引：默认使用主键；若无主键则取第一个非空唯一索引；若仍无则自动生成 6 字节的隐式 `row_id`。

    ```
    1. 显式主键 (PRIMARY KEY) ──> 若存在，直接作为聚簇索引
             │ (不存在)
             ▼
    2. 第一个非空唯一索引 (UNIQUE NOT NULL) ──> 若存在，作为聚簇索引
             │ (不存在)
             ▼
    3. 隐式行 ID (DB_ROW_ID) ──> 自动生成 6 字节自增隐藏列构建聚簇索引
    ```

- **非聚簇索引 / 二级索引**：

  - **数据与索引分离**：叶子节点不存储整行数据。
  - **InnoDB**：二级索引的叶子节点存储的是**主键值**。若查询包含非索引列，引擎先在二级索引树查到主键，再到聚簇索引树检索完整数据行，该过程称为**回表**。
  - **MyISAM**：所有索引均为非聚簇索引，叶子节点存储的是**指向数据物理磁盘地址的指针**。



![image-20260818190023888](/covers/java--mysql-2--2-tkettk/image-20260818190023888.webp)





当执行如下的SQL语句时，具体的查找过程是什么样子的

```sql
select * from user where name='Arm'；
```

具体过程如下：

(1) 由于是根据name字段进行查询, 所以先根据name='Arm'到name字段的二级索引中进行匹配查找。但是在二级索引中只能查找到 Arm 对应的主键值 10。

(2) 由于查询返回的数据是*, 所以此时, 还需要根据主键值10, 到聚集索引中查找10对应的记录, 最终找到10对应的行row。

(3) 最终拿到这一行的数据, 直接返回即可。

**回表查询：这种先到二级索引中查找数据，找到主键值，然后再到聚集索引中根据主键值，获取数据的方式，就称之为回表查询。**

![image-20260818190141225](/covers/java--mysql-2--2-tkettk/image-20260818190141225.webp)



## 3. 逻辑约束

| **索引类型** | **声明关键字**  | **约束与特征**                                               |
| ------------ | --------------- | ------------------------------------------------------------ |
| **主键索引** | `PRIMARY KEY`   | 唯一标识一行，不允许为 `NULL`，一张表只能有一个。            |
| **唯一索引** | `UNIQUE`        | 保证列值全局唯一，但**允许存在多个 `NULL` 值**。             |
| **普通索引** | `INDEX` / `KEY` | 最基础的单列/多列索引，无唯一性限制，仅加速查询。            |
| **全文索引** | `FULLTEXT`      | 针对文本字段分词索引，配合 `MATCH() AGAINST()` 使用。        |
| **前缀索引** | `INDEX(col(N))` | 仅针对大字符串字段的前 $N$ 个字符建索引，节省空间并降低 I/O 开销。 |



## 4. 字段列数

- **单列索引**：基于单个列创建的索引。
- **联合索引（复合索引 / 多列索引）**：由 2 个或更多字段组合构建的索引。遵循**最左前缀匹配原则**（查询条件必须从联合索引的最左列开始，遇到范围查询 `>`、`<` 会中断后续列的索引匹配）。

以联合索引 `INDEX idx_a_b_c (a, b, c)` 为例，InnoDB 会构建一棵独立的 B+ 树：

- **非叶子节点与叶子节点**：存放的数据均是复合键值 `[a, b, c]` 以及对应记录的 **主键 `id`**。
- **物理排序机制**：
  - 数据**首先严格按照第 1 列 `a` 进行全局升序排序**；
  - 只有在 **`a` 值完全相同**的前提下，才按照第 2 列 `b` 局部排序；
  - 只有在 **`a` 和 `b` 均相同**的前提下，才按照第 3 列 `c` 局部排序。

```
              ┌─────────────────────────────────────────┐
              │          联合索引 idx_a_b_c 数据页       │
              ├───────────┬───────────┬───────────┬─────┤
              │ 列 a      │ 列 b      │ 列 c      │ id  │
              ├───────────┼───────────┼───────────┼─────┤
              │ 1         │ 10        │ 'X'       │ 101 │
              │ 1         │ 20        │ 'Y'       │ 102 │  <-- a 相同，b 有序
              │ 1         │ 20        │ 'Z'       │ 103 │  <-- a、b 均相同，c 有序
              │ 2         │ 5         │ 'M'       │ 104 │  <-- a 变大，此时 b(5) 比上一行的 b(20) 小
              │ 3         │ 15        │ 'N'       │ 105 │      (全局视角下 b 是无序的)
              └───────────┴───────────┴───────────┴─────┘
```





**常见查询优化关联概念**

- **覆盖索引（Covering Index）**：一种查询优化现象。当 SQL 查询所需的所有字段（`SELECT` 与 `WHERE` 列）均包含在二级索引中时，无需执行回表操作，效率最高。
- **索引下推（Index Condition Pushdown, ICP）**：MySQL 5.6+ 引入的优化机制。在遍历二级索引时，优先过滤索引包含的 `WHERE` 条件，从而大幅减少回表次数。

# 四. 索引语法

## 1. 创建索引

### 1. 建表时定义索引

```sql
CREATE TABLE users (
    id INT AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    age INT,
    bio TEXT,
    created_at DATETIME,
    
    -- 1. 主键索引 (Primary Key)
    PRIMARY KEY (id),
    
    -- 2. 唯一索引 (Unique Index)
    UNIQUE KEY uk_email (email),
    
    -- 3. 普通单列索引 (Normal Index)
    INDEX idx_age (age),
    
    -- 排序索引
    INDEX desc-age (age DESC),
    
    -- 4. 联合索引 / 复合索引 (Composite Index)
    INDEX idx_user_age (username, age),
    
    -- 5. 前缀索引 (Prefix Index, 仅针对前 10 个字符建立索引)
    INDEX idx_bio_prefix (bio(10)),
    
    -- 6. 全文索引 (Fulltext Index)
    FULLTEXT KEY ft_idx_bio (bio)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```



### 2. 为已有表添加索引

**方式 A：使用 `ALTER TABLE`（推荐，功能最全）**

```sql
-- 添加普通索引
ALTER TABLE users ADD INDEX idx_created_at (created_at);

-- 添加唯一索引
ALTER TABLE users ADD UNIQUE INDEX uk_username (username);

-- 添加主键索引
ALTER TABLE users ADD PRIMARY KEY (id);

-- 添加联合索引
ALTER TABLE users ADD INDEX idx_name_time (username, created_at);

-- 生产环境推荐：显式声明 Online DDL（避免锁表）
ALTER TABLE users 
    ADD INDEX idx_age (age), 
    ALGORITHM = INPLACE, 
    LOCK = NONE;
```

**方式 B：使用 `CREATE INDEX` 语句**

```sql
-- 创建普通索引
CREATE INDEX idx_created_at ON users (created_at);

-- 创建唯一索引
CREATE UNIQUE INDEX uk_username ON users (username);

-- 创建前缀索引
CREATE INDEX idx_bio ON users (bio(20));
```



## 2. 查看索引

```sql
-- 查看表上所有索引的详细信息
SHOW INDEX FROM users;
-- 或
SHOW KEYS FROM users;

-- 查看格式化后的索引元数据（垂直展示，适合命令行）
SHOW INDEX FROM users \G;
```

> **输出核心字段说明**：
>
> - `Key_name`：索引名称（`PRIMARY` 表示主键）。
> - `Column_name`：索引包含的字段名。
> - `Seq_in_index`：该列在联合索引中的位置序号（从 1 开始）。
> - `Cardinality`：基数（索引中不重复值的预估数量，值越大索引选择性越好）。
> - `Index_type`：索引类型（如 `BTREE`、`FULLTEXT`）。



## 3. 删除索引

```sql
-- 方式 A：使用 DROP INDEX
DROP INDEX idx_age ON users;

-- 方式 B：使用 ALTER TABLE DROP INDEX
ALTER TABLE users DROP INDEX idx_user_age;

-- 特殊：删除主键索引（若存在自增 AUTO_INCREMENT 需先修改列属性移除自增）
ALTER TABLE users DROP PRIMARY KEY;
```



# 五. 索引法则

## 1. 最左前缀匹配原则

如果索引了多列（联合索引），要遵守最左前缀法则

最左前缀法则（Leftmost Prefix Rule）是 MySQL 联合索引（复合索引）的核心匹配规则：**在通过联合索引检索数据时，查询条件必须从索引的最左列开始，且不能跳过中间列；如果跳过某一列或遇到了范围查询，后续列将无法用于 B+ 树的快速二分检索。**

### 1. 底层原理

以联合索引 `INDEX(a, b, c)` 为例，InnoDB 会构建一棵复合 B+ 树，其物理排序逻辑为：

1. **全局维度**：仅按照第 1 列 `a` 进行绝对有序排列；
2. **局部维度**：只有在 **`a` 值相同**的前提下，第 2 列 `b` 才是局部有序的；
3. **更深层维度**：只有在 **`a` 和 `b` 同时相同**的前提下，第 3 列 `c` 才是局部有序的。

```
              ┌──────────────────────────────────────────────┐
              │           联合索引数据页 (a, b, c)            │
              ├────────────┬────────────┬────────────┬───────┤
              │ 列 a       │ 列 b       │ 列 c       │ id    │
              ├────────────┼────────────┼────────────┼───────┤
              │ 1          │ 10         │ 'X'        │ 101   │
              │ 1          │ 20         │ 'Y'        │ 102   │ <-- a 相等，b 有序
              │ 1          │ 20         │ 'Z'        │ 103   │ <-- a、b 均相等，c 有序
              │ 2          │ 5          │ 'M'        │ 104   │ <-- a 变化，全局看 b(5 < 20) 是无序的
              └────────────┴────────────┴────────────┴───────┘
```

> **结论**：若查询条件缺失最左列 `a`（例如只查 `WHERE b = 20`），由于在整棵树视角下 `b` 是无序离散的，B+ 树无法进行折半查找，索引直接失效。



### 2.  命中场景全景对比

| **查询 WHERE 条件**            | **索引命中情况**          | **实际执行行为与解释**                                       |
| ------------------------------ | ------------------------- | ------------------------------------------------------------ |
| `WHERE a=1 AND b=2 AND c=3`    | **全部命中 (a, b, c)**    | 完全匹配，走 3 列树查找，效率最高。                          |
| `WHERE b=2 AND c=3 AND a=1`    | **全部命中 (a, b, c)**    | **优化器会自动重排条件顺序**，与上一条等效。                 |
| `WHERE a=1 AND b=2`            | **部分命中 (a, b)**       | 连续匹配前两列。                                             |
| `WHERE a=1`                    | **部分命中 (a)**          | 仅使用最左列 `a`。                                           |
| `WHERE b=2 AND c=3`            | **完全不走索引 (ALL)**    | **缺失最左列 `a`**，索引直接失效。                           |
| `WHERE c=3`                    | **完全不走索引 (ALL)**    | **缺失最左列 `a`**，索引直接失效。                           |
| `WHERE a=1 AND c=3`            | **定位命中 `a`**          | `a` 用于树二分查找；`c` 无法用于树查找，但会触发 **ICP（索引下推）** 进行过滤。 |
| `WHERE a=1 AND b > 10 AND c=3` | **命中 `a, b`，`c` 失效** | **范围查询截断后续列**：`b > 10` 范围内的数据 `c` 是无序的，`c` 无法用于树查找。 |



### 3. 细节

**1. WHERE 条件的书写顺序不会破坏最左前缀**

MySQL 的 **CBO（查询优化器）** 会在执行前对 `WHERE` 中的 `AND` 条件进行自动重排以匹配索引：

```sql
-- 即使颠倒顺序，优化器会自动调整为 a -> b -> c，完整走索引
SELECT * FROM t WHERE c = 3 AND a = 1 AND b = 2;
```



**2. 范围查询的“截断效应”**

当联合索引的某一列使用了范围比较符（如 `>`、`<`、`BETWEEN`、`LIKE 'abc%'`）时，该列本身能用到索引，但**其右侧的所有列全部无法用于树查找**：

```sql
-- 索引 (a, b, c)
SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 3;
-- 实际仅 a 和 b 用到了索引（key_len 只包含 a 和 b 的长度），c 列失效
```

**优化方案**;

1. **业务允许时改用 `>=` / `<=` 或 `BETWEEN AND`**：

   - 例如查询“大于 30 岁”如果业务上等同于“大于等于 31 岁”，写成 `age >= 31` 即可让后续字段继续参与索引边界定位。

2. **调整联合索引的字段顺序（等值在前，范围在后）**：

   - 如果 `status` 是等值查询（`status = '0'`），而 `age` 是范围查询（`age > 30`），**建索引时应将等值列前置**：

     $$\text{建索引规则：} \text{INDEX}(profession, status, age)$$

   - 这样 `profession` 和 `status` 都能走等值二分查找，最后由 `age` 走范围扫描，三列均能充分发挥索引性能。

3. **离散范围改用 `IN (...)`**：

   - 如果范围是有限的几个离散值（如 `status` 或 `type`），优先使用 `IN ('A', 'B')` 代替范围查询，`IN` 在很多场景下会被优化器评估为多个等值匹配，不会截断后续索引列。



**3. 字符串模糊匹配（LIKE）也遵循最左前缀**

字符串在 B+ 树中是按字符编码从左往右排序的：

- `LIKE '张%'`：**遵循最左前缀**，能走索引。
- `LIKE '%张'` 或 `LIKE '%张%'`：**违反最左前缀**（左侧不确定，整体无序），导致索引失效走全表扫描。



**4. 排序（ORDER BY）与分组（GROUP BY）同样适用**

如果排序字段能与查询条件拼出最左前缀，可以消除额外的内存/文件排序（Using filesort）：

```sql
-- 索引 (a, b, c)
-- 场景 A：a 走等值过滤，b 局部有序，直接利用索引排序，效率极高
SELECT * FROM t WHERE a = 1 ORDER BY b, c;
 
SELECT * FROM t WHERE a = 1 ORDER BY c;
```



### 4. 优化

- **索引下推（ICP, MySQL 5.6+）**：

  若执行 `WHERE a = 1 AND c = 3`（跳过了 `b`），虽然 `c` 无法用于树查找，但引擎层会在遍历二级索引时直接比对 `c = 3`，仅把匹配的主键回表，大幅降低回表次数。

- **索引跳跃扫描（Index Skip Scan, MySQL 8.0+）**：

  当查询缺失最左列（如直接查 `WHERE b = 2`）时，如果最左列 `a` 的基数很小（例如性别只有 `M`/`F`），MySQL 8.0 优化器能自动将查询拆分为 `WHERE a='M' AND b=2 UNION ALL WHERE a='F' AND b=2` 走索引跳跃扫描。



## 2. 索引下推

索引下推（Index Condition Pushdown，简称 ICP）是 MySQL 5.6 引入的核心查询优化技术。

它的核心作用是：**把本应在 Server 层进行的索引字段条件过滤，“下推”到存储引擎（InnoDB / MyISAM）层提前完成，从而大幅减少回表（Table Lookup）次数，降低磁盘 I/O 消耗。**



假设有一张表 `users (id, name, age, address)`，并在 `(name, age)` 上建立了联合二级索引：

```sql
SELECT * FROM users WHERE name LIKE '张%' AND age = 20;
```

*假设数据中姓“张”的有 **10,000 条**，但其中 `age = 20` 的只有 **5 条**。*

```
【 传统无 ICP 流程 (MySQL 5.5 及以前) 】
 二级索引树 ──> 提取所有 10000 个姓张的主键 ──> 💥 强制回表 10000 次 ──> Server 层比对 age=20 ──> 丢弃 9995 行无效数据

【 开启索引下推 (MySQL 5.6+) 】
 二级索引树 ──> 在索引页内直接过滤 age=20 ──> ⚡ 仅对匹配的 5 个主键回表 ──> Server 层直接输出 5 行数据
```

| **阶段**           | **无 ICP（MySQL 5.5 及以前）**                               | **有 ICP（MySQL 5.6+ 默认开启）**                            |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **存储引擎层行为** | 仅根据 `name LIKE '张%'` 在二级索引中找出所有满足条件的主键 ID。 | 在二级索引页中定位 `name LIKE '张%'` 的同时，**直接读取索引页中附带的 `age` 列进行比对**。 |
| **回表操作**       | 每拿到一个主键就**立即回表**读取整行完整数据（共执行 **10,000 次** 随机 I/O）。 | 仅当 `age = 20` 条件满足时，**才去执行回表**（仅执行 **5 次** 回表）。 |
| **Server 层行为**  | 从引擎层接收 10,000 行完整数据，逐行判断 `age == 20`，丢弃 9,995 行。 | 接收引擎层已经过滤好的 5 行数据，直接返回客户端。            |
| **性能消耗**       | 产生大量无效的磁盘 I/O 与 Buffer Pool 内存页抖动。           | **回表 I/O 暴降 99.9%**，查询毫秒级响应。                    |



### 触发场景

1. **联合索引中出现模糊匹配（LIKE 'abc%'）**：
   - 联合索引 `(name, age)`，查询 `WHERE name LIKE '张%' AND age = 20`。`name` 范围扫描导致 `age` 无法用于树二分寻道，但 `age` 在二级索引页中存在，触发 ICP 过滤。
2. **联合索引跳过中间列（违反最左前缀）**：
   - 联合索引 `(a, b, c)`，查询 `WHERE a = 1 AND c = 100`。虽然跳过了 `b` 导致 `c` 无法参与树二分定位，但引擎层可以在扫描 `a = 1` 的索引节点时顺带比对 `c == 100`，只对符合条件的行回表。
3. **联合索引遇到范围截断（`>`、`<`）**：
   - 联合索引 `(profession, age, status)`，查询 `WHERE profession = '软件工程' AND age > 30 AND status = '0'`。`age > 30` 截断了 `status` 的树寻道，但引擎层会在扫描区间内直接比对 `status == '0'` 再决定是否回表。



### ICP 的使用限制与边界

- **仅对二级索引（Secondary Index）有效**：聚簇索引的叶子节点本身就保存了整行所有数据，直接在叶子页判断即可，不存在“回表”概念。
- **被下推的条件字段必须在索引中**：如果查询条件是 `WHERE name = '张' AND address LIKE '%北京%'`，因为 `address` 不在索引中，引擎层在索引树上看不到该字段，无法下推，只能回表后由 Server 层过滤。
- **包含子查询、存储函数的条件无法下推**。



## 3. 回表和覆盖索引

回表（Table Lookup）**与**覆盖索引（Covering Index）是 MySQL 查询优化中最核心的一对概念：**回表是产生大量随机 I/O、导致查询变慢的主要根源，而覆盖索引则是消除回表、提升吞吐量的关键手段。**

### 1. 回表

当通过**二级索引（辅助索引）\**查询数据，且 `SELECT` 列表中包含了\**二级索引树上没有的字段**时，MySQL 必须先在二级索引树上查到主键 ID，再拿着主键 ID 跑到**主键聚簇索引树**重新检索一遍整行完整记录，这个二次查找的过程就叫做**回表**。

**回表的性能代价**

- **双重树寻道**：原本 1 次树遍历即可完成的操作，变成了 2 次 B+ 树遍历。
- **离散随机 I/O**：二级索引中顺序排列的数据，其对应的主键在聚簇索引物理磁盘上的分布通常是离散的。查询 10,000 条记录可能触发数千次离散的磁盘随机 I/O，在大表和高并发场景下极易打满 I/O 瓶颈。



### 2. 覆盖索引

**覆盖索引并不是一种物理索引结构，而是一种高效的查询状态。**

当一条 SQL 查询所需的所有字段（包括 `SELECT` 投影列、`WHERE` 过滤列、`ORDER BY` 排序列、`GROUP BY` 分组列）全部包含在某一个二级索引的键值中（或属于主键）时，MySQL 只需要遍历二级索引树就能直接拿到所有需要的数据，**完全不需要发生回表**。

```
                                  【 二级索引树 (如: idx_user_age) 】
                                       叶子节点存: (username, age, id)
                                                      │
                                           (查询 username='Alice')
                                                      │
                             ┌────────────────────────┴────────────────────────┐
                             ▼                                                 ▼
                   【 场景 A：命中覆盖索引 】                                【 场景 B：触发回表 】
             SELECT age, id FROM users WHERE ...                     SELECT address FROM users WHERE ...
                             │                                                 │
                             ▼                                                 ▼
                     所需字段都在二级索引中                                缺少 address 字段
                   ⚡ 直接返回数据 (0 次回表)                            拿着 id 回到【 聚簇索引树 】
                                                                               │
                                                                               ▼
                                                                        读取整行获取 address (1次回表)
```



**核心特性与执行差异对比**

| **比较维度**             | **触发回表的查询**                                    | **命中覆盖索引的查询**            |
| ------------------------ | ----------------------------------------------------- | --------------------------------- |
| **检索树数量**           | 2 棵（二级索引树 + 聚簇索引树）                       | **1 棵**（仅二级索引树）          |
| **I/O 消耗**             | 大量离散随机 I/O，依赖聚簇索引缓存                    | **纯顺序/局部 I/O**，内存开销极小 |
| **`EXPLAIN` 中的 Extra** | 显示 `NULL`、`Using where` 或 `Using index condition` | **明确显示 `Using index`**        |
| **查询耗时**             | 随数据量与回表条数增加而急剧恶化                      | 毫秒级稳定响应                    |



### 3. 使用场景

**场景 1：严格禁止 `SELECT *`，按需取列**

```sql
-- ❌ 慢查询：引发整表回表
SELECT * FROM orders WHERE user_id = 1001;

-- ✅ 覆盖优化：只要 idx_user_status (user_id, status) 包含了所查字段，立即消除回表
SELECT id, user_id, status FROM orders WHERE user_id = 1001;
```



**场景 2：计数与存在性检查（COUNT / EXISTS）**

```sql
-- 统计满足条件的人数：覆盖索引直接在内存叶子节点统计，速度提升数十倍
SELECT COUNT(*) FROM users WHERE age > 18; -- 确保 age 字段有索引
```



**场景 3：拯救千万级深分页（延迟关联 / Deferred Join）**

当执行 `LIMIT 1000000, 10` 时，MySQL 默认会扫描 1,000,010 条记录并执行 1,000,010 次回表，最后抛弃前 100 万条，导致查询耗时数秒甚至超时。

- **优化前（超慢）**：

  ```sql
  SELECT * FROM orders WHERE status = 1 ORDER BY create_time LIMIT 1000000, 10;
  ```

- **利用覆盖索引做“延迟关联”优化（毫秒级）**：

  ```sql
  -- 索引为 idx_status_time (status, create_time)
  SELECT o.* 
  FROM orders o
  JOIN (
      -- 子查询只查 id，完全命中覆盖索引，在二级索引树上快速跳过 100 万行
      SELECT id 
      FROM orders 
      WHERE status = 1 
      ORDER BY create_time 
      LIMIT 1000000, 10
  ) tmp ON o.id = tmp.id;
  ```

  - **原理**：子查询仅通过覆盖索引扫描定位出目标 10 条记录的主键 `id`（0 次回表），最后主表根据这 10 个主键只做 **10 次精准回表**，性能通常提升数十倍到数百倍。





## 4. 索引使用情况

建立索引的核心原则是“以空间换时间、以写性能损耗换读性能提升”**。是否建索引取决于**数据规模、字段区分度、读写比例与查询模式。

### 1. 适合索引

- **数据量较大的表**：通常单表数据量达到数万行以上时，B+ 树能将 $O(N)$ 的全表扫描降为 $O(\log N)$ 的树寻道，性能收益显著。
- **高频出现在 `WHERE` 条件中的字段**：作为业务核心查询入口的字段（如 `user_id`、`order_sn`、`phone` 等）。
- **多表关联的 `JOIN ON` 字段**：主外键或关联字段建索引，可让多表连接从昂贵的 Nested-Loop 全表扫描转为 Index Lookup。
- **区分度高（Cardinality 大）的字段**：字段唯一值越多（例如手机号、UUID、自增 ID），索引过滤性越强，能以极小代价锁定少量目标行。
- **高频用于 `ORDER BY`、`GROUP BY`、`DISTINCT` 的字段**：利用 B+ 树叶子节点的天然有序性，可以直接按序输出结果，**消除昂贵的文件排序（`Using filesort`）与临时表（`Using temporary`）**。
- **能构成“覆盖索引”的高频查询组合**：将高频查询的查询条件与投影列合并为联合索引（如 `INDEX(user_id, status, create_time)`），实现**零回表**直接在内存中返回数据。
- **较长字符串的前缀部分**：对于长文本字段（如 `VARCHAR(255)`），提取前 10~20 个字符建立**前缀索引**，在保证高区分度的同时大幅削减索引体积。



### 2. 不适合索引

- **数据量很少的小表**：数据只有几百行时，整张表通常只需 1~2 个 16KB 数据页即可装下。优化器直接全表顺序 I/O 读取比遍历索引树再回表的代价更低。
- **区分度极低（基数小）的字段**：
  - 如性别（男/女）、状态位（0/1）、逻辑删除标记（is_deleted）等。
  - 若某个值占比超过 20%~30%，优化器计算发现二级索引扫描后需要天量回表，其随机 I/O 代价远超全表扫描，**最终会主动放弃索引走全表扫描**。
- **频繁更新的字段或写密集型表**：
  - 每当执行 `INSERT`、`DELETE` 或包含索引列的 `UPDATE` 时，InnoDB 必须同步维护每棵 B+ 树的节点顺序、页分裂与合并。
  - 索引越多，写入与事务锁竞争的开销呈线性暴增。
- **从不在 `WHERE`、`JOIN` 或排序分组中使用的列**：盲目建索引只会白白浪费磁盘与 Buffer Pool 内存空间。
- **未经前缀处理的大文本字段（`TEXT` / `BLOB`）**：字段体积过大会导致单个索引页能容纳的键值数骤降，使 B+ 树高度迅速增加，急剧消耗内存并拖慢检索。
- **单表索引总数过多（建议不超过 5 个）**：索引过多会严重稀释 Buffer Pool 内存，挤占真实数据页缓存，导致内存命中率下降。



**对比**

| **场景维度**     | **✅ 推荐建索引**                                    | **❌ 不建议建索引**                     |
| ---------------- | --------------------------------------------------- | -------------------------------------- |
| **数据量**       | 行数 $\ge 10,000$ 的中大表                          | 行数 $< 1,000$ 的配置表 / 字典表       |
| **字段区分度**   | 唯一值比例高（如手机号、订单号、邮箱）              | 唯一值比例极低（如性别、布尔状态位）   |
| **业务操作倾向** | 读多写少（高频查询、统计分析）                      | 写多读少（日志流水表、MQ 消费缓冲表）  |
| **字段参与环节** | 过滤（`WHERE`）、连接（`JOIN`）、排序（`ORDER BY`） | 仅在 `SELECT` 输出，从不用于过滤或排序 |
| **设计方式**     | 优先用联合索引覆盖多个查询场景                      | 针对每个字段盲目堆砌单列二级索引       |





## 5. 索引失效

在 MySQL 数据库中，索引失效通常不是索引“坏了”，而是**SQL 写法破坏了 B+ 树的有序检索结构，导致优化器（CBO）计算后发现走全表扫描的代价比走二级索引回表更低**。

**索引失效排查清单**

| **检查项**           | **关注排查点**                                  |
| -------------------- | ----------------------------------------------- |
| **列左侧是否有加工** | 检查是否有函数、计算、强制类型转换              |
| **模糊匹配前缀**     | 检查是否有 `%` 开头的 `LIKE`                    |
| **联合索引完整度**   | 检查是否命中最左字段、中间是否有 `>` / `<` 截断 |
| **字段字符集统一性** | 检查多表 `JOIN ON` 字段的字符集是否一致         |
| **过滤数据占比**     | 检查过滤出的数据量是否占整表过高                |



以下是日常开发中导致索引失效的 **十大典型写法与避坑方案**：

**1. 对索引列进行函数计算或表达式操作**

B+ 树的节点中保存的是字段的**原始值**，无法预知函数计算或数学运算后的结果，必须逐行执行计算，导致索引失效。

- ❌ **失效写法**：

  ```sql
  -- 函数包裹索引列
  SELECT * FROM users WHERE SUBSTR(phone, 1, 3) = '138';
  SELECT * FROM orders WHERE DATE(create_time) = '2026-01-01';
  
  -- 表达式运算
  SELECT * FROM users WHERE id + 1 = 100;
  ```
  
- ✅ **优化写法**：

  ```sql
  -- 将计算移到常量端 / 改写为范围查询
  SELECT * FROM users WHERE phone LIKE '138%';
  SELECT * FROM orders WHERE create_time >= '2026-01-01 00:00:00' AND create_time < '2026-01-02 00:00:00';
  SELECT * FROM users WHERE id = 99;
  
  -- 或使用 MySQL 8.0+ 函数索引：CREATE INDEX idx_func ON orders ((DATE(create_time)));
  ```



**2. 隐式类型转换（字符串与数值混用）**

当字段类型与传入参数类型不一致时，MySQL 会按照数据类型转换规则触发隐式转换。

- **规则**：字符串与数字比较时，MySQL 会**将字符串列转换为浮点数/整数**进行比对（相当于对索引列施加了 `CAST(col AS SIGNED)` 函数）。

- ❌ **失效写法**（假设 `phone` 为 `VARCHAR(20)`）：

  ```sql
  -- 传入数字，MySQL 会将每一行的 phone 转换为数字后再比对，导致全表扫描
  SELECT * FROM users WHERE phone = 13800000000;
  ```
  
- ✅ **优化写法**：

  ```sql
  -- 严格保持类型一致，加上引号
  SELECT * FROM users WHERE phone = '13800000000';
  ```



**3. 隐式字符集转换（多表关联字符集不一致）**

两张表关联时，若关联字段的字符集不同（例如 `t1.name` 为 `utf8mb4`，`t2.name` 为 `utf8`），MySQL 在做 `JOIN` 时会将低精度字符集转换为高精度字符集，底层等同于 `ON CONVERT(t2.name USING utf8mb4) = t1.name`，从而使 `t2` 上的索引失效。

- ❌ **失效场景**：

  ```sql
  -- t1 表字符集 utf8mb4，t2 表字符集 utf8
  SELECT * FROM t1 JOIN t2 ON t1.account = t2.account;
  ```
  
- ✅ **优化写法**：统一全库所有表的字符集为 `utf8mb4` 与相同的排序规则（如 `utf8mb4_general_ci` 或 `utf8mb4_0900_ai_ci`）。



**4. 头部模糊匹配（LIKE '%abc'）**

B+ 树的字符串索引是按照前缀字符的字典序从左往右排序的。

- `LIKE '张%'`：左前缀确定，可以利用 B+ 树快速定位边界。

- `LIKE '%张'` 或 `LIKE '%张%'`：首字符不确定，整棵树无法进行折半查找，只能走全表扫描。

- ❌ **失效写法**：

  ```sql
  SELECT * FROM users WHERE username LIKE '%张';
  SELECT * FROM users WHERE username LIKE '%张%';
  ```
  
- ✅ **优化方案**：

  - 仅后置通配符：`WHERE username LIKE '张%'`。
  - 必须全模糊匹配且数据量大时，使用全文索引（Full-Text Index）或引入专业检索组件（Elasticsearch）。



**5. 违背联合索引的“最左前缀法则”**

在联合索引 `INDEX(a, b, c)` 中，只有在 `a` 相等的前提下 `b` 才有序；在 `a`、`b` 均相等的前提下 `c` 才有序。

- ❌ **失效写法**：

  ```sql
  -- 缺失最左列 a，索引完全不生效（全表扫描）
  SELECT * FROM t WHERE b = 2 AND c = 3;
  SELECT * FROM t WHERE c = 3;
  ```
  
- ✅ **优化写法**：

  ```sql
  -- 必须带上最左列
  SELECT * FROM t WHERE a = 1 AND b = 2 AND c = 3;
  ```



**6. 范围查询导致联合索引右侧列失效**

联合索引中一旦某一列使用了范围比较（`>`、`<`），其右侧的所有列都无法再用于 B+ 树二分查找。

- ❌ **部分失效**（假设索引为 `idx_a_b_c (a, b, c)`）：

  ```sql
  -- a 和 b 走索引，但 b > 10 破坏了 c 的局部有序性，c 列索引失效
  SELECT * FROM t WHERE a = 1 AND b > 10 AND c = 3;
  ```
  
- ✅ **优化方案**：

  - 建索引时将等值列前置，范围列后置：改为 `INDEX(a, c, b)`。
  - 业务允许时改用带有等号的边界或枚举：`b >= 11` 或 `b IN (11, 12, 13)`。



**7. OR 查询两边存在未索引的字段**

使用 `OR` 连接条件时，如果其中一个字段有索引，而另一个字段没有索引，MySQL 为了找出两者的并集，仍必须全表扫描没有索引的列。此时优化器会判定直接全表扫描的总代价更低。

- ❌ **失效写法**（`age` 有索引，`address` 无索引）：

  ```sql
  -- 导致 age 上的索引也被迫放弃，走全表扫描
  SELECT * FROM users WHERE age = 20 OR address = '北京';
  ```
  
- ✅ **优化写法**：

  - 为 `address` 也建立索引，让优化器尝试触发 **Index Merge（索引合并）**。

  - 改写为 `UNION ALL`：

    ```sql
    SELECT * FROM users WHERE age = 20
    UNION
    SELECT * FROM users WHERE address = '北京';
    ```



**8. 使用否定条件（!=、<>、NOT IN、NOT LIKE）**

否定条件通常意味着匹配全表中的绝大多数数据，优化器计算后发现二级索引扫描后需要天量回表，其离散随机 I/O 代价远超顺序全表扫描。

- ❌ **常见失效写法**：

  ```sql
  SELECT * FROM users WHERE status != 0;
  SELECT * FROM users WHERE id NOT IN (1, 2, 3);
  ```
  
- ✅ **优化写法**：尽量转换为肯定条件查询（如 `status IN (1, 2)`），或通过覆盖索引避免回表。



**9. 索引列使用 `IS NULL` / `IS NOT NULL` 时过滤比例过大**

- 在 InnoDB 中，`IS NULL` 和 `IS NOT NULL` **本身是支持走索引的**。
- 但如果在实际数据表中 `NOT NULL` 的数据占了 90% 以上，查询 `WHERE col IS NOT NULL` 会匹配绝大多数行，优化器认为全表扫描更经济，因而主动放弃索引。



**10. 数据区分度低或检索范围过大（CBO 代价判定放弃）**

当某个字段区分度极低（例如性别只有男/女），或者范围查询（`age > 10`）命中的数据行数超过全表的 **20% ~ 30%** 时：

- 二级索引过滤出的海量主键会导致极其昂贵的**随机回表 I/O**。
- 优化器评估后会放弃走二级索引，直接选择全表顺序扫描（`type = ALL`）。
