登录状态管理有三种最为主流的实现方案：**纯 Session 方案**、**自研 Redis + Token 方案**、以及 **JWT 令牌（Json Web Token）方案**。



## 一. 三大技术原理及优缺点剖析

### 1. 传统单机 Session 方案
* **原理**：会话状态存在应用服务器（如 Tomcat）的 JVM 内存中，客户端通过 Cookie 自动携带的 `JSESSIONID` 来匹配并读取对应的内存会话。
* **好处**：
  1. **极其简单，开箱即用**：由 Web 容器内置，开发不需要写任何底层代码，也不需要部署外部中间件。
  2. **对前端透明**：依靠浏览器 Cookie 的原生传递机制，自动过期，自动携带，安全性（在防止 XSS 窃取方面）可以通过设置 `HttpOnly` 的 Cookie 轻易获得。
* **坏处**：
  1. **不支持分布式扩展**：无法直接满足多服务器集群或微服务架构，横向扩容时需要做代价极大的 Session 复制或粘性会话配置。
  2. **服务器内存压力大**：高并发下在线用户多时，Tomcat 内存很容易溢出（OOM）。
  3. **跨端/跨域极不友好**：在小程序、App 等没有 Cookie 自动携带机制的非浏览器平台，或者跨顶级域名的场景下极其繁琐。
* **典型场景**：中小型单体 Web 网站、传统的企业内部后台管理系统。



### 2. 自研 Redis + Token 方案

* **原理**：服务端充当“无状态”节点，将登录会话存储在外部统一的 Redis 极速内存数据库中。登录成功后生成一个随机 UUID 作为 Token 返回给前端，前端手动存入本地并通过请求头（如 `authorization`）发送。
* **好处**：
  1. **天然支持分布式扩展**：多台应用服务器共享同一个外部 Redis，服务器可以随意水平扩容。
  2. **控制力极强（可控性高）**：服务端可以**随时强制把某个用户踢下线**（直接在 Redis 中删除其 Token）、控制账号的单设备/多设备在线限制。
  3. **多端支持极佳**：基于请求头自定义传递，不受同源策略限制，天然对 App、小程序、前后端分离架构友好。
  4. **Tomcat 内存解脱**：会话数据全部转移到了具有高吞吐、高并发处理能力的外部 Redis 中，Tomcat 不承载状态。
* **坏处**：
  1. **增加系统复杂度**：需要引入并保证 Redis 缓存的高可用（若 Redis 挂了，全系统登录瘫痪）。
  2. **需要手动编写代码管理生命周期**：例如需要双拦截器进行 Token 过期时间的手动刷新与维护。
* **典型场景**：中大型互联网高并发系统、多客户端（PC+Web+小程序+App）协同的项目、有强制踢人或单账号多在线控制需求的业务。



### 3. JWT 令牌方案

* **原理**：**去中心化、完全无状态**。服务端将用户状态（如 ID、昵称、角色）及过期时间直接使用 Base64 编码，并配合密钥进行**数字签名**生成一长串加密字符串（即 JWT）返回给客户端。客户端将其通过请求头携带，后端服务**无需查询任何数据库或 Redis**，仅在 CPU 中使用本地密钥执行验签即可得知用户身份。
* **好处**：
  1. **极致的去中心化与性能**：后端服务器不需要查询任何 Session 或 Redis，仅在本地消耗极少的 CPU 完成签名验证，数据库和缓存数据库零压力。
  2. **微服务与网关天然适配**：网关只管验签，可以将解密后的用户信息直接往后传递给各个微服务，解耦性极强。
* **坏处**：
  1. **一旦颁发，无法中途收回**：这是 JWT **最致命的弱点**！JWT 的有效期全部写在 Token 内部。如果用户修改了密码、管理员禁用了其账号、或者 Token 被盗用，**服务端没有任何常规手段可以主动令其立即失效**（只能等待其自然过期）。
  2. **如果想主动失效，必须引入 Redis**：若为了踢人而使用 Redis 缓存拉黑 Token，那就**破坏了 JWT 纯无状态的核心初衷**，使其退化成了变相的 Redis+Token。
  3. **体积较大，数据敏感度低**：JWT 里面带有 Payload 数据，Base64 编码并不是加密，前端通过解码可以直接看到内容（所以不能放密码等敏感数据），且 JWT 较长会消耗额外的网络带宽。
* **典型场景**：纯 Stateless（无状态）的开放平台鉴权（API 授权）、跨系统的单点登录（SSO）令牌、不需要主动拉黑和控制会话的微服务系统。



## 二. 三种方案多维度指标对比

| 对比维度 | 纯 Session 方案 | 自研 Redis + Token 方案 | JWT 令牌方案 |
| :--- | :--- | :--- | :--- |
| **存储位置** | 应用服务器 JVM 内存 | 外部独立的 Redis NoSQL 数据库 | 客户端本地（服务端不存任何状态数据） |
| **数据读取开销** | 内存读写（极低） | 快速的 Redis 网络 IO 读写（极低） | 本地 CPU 解密验签（不需要网络和数据库查询） |
| **分布式支持度** | **极差**（需要会话同步/粘性 Session） | **极佳**（天生支持水平伸缩） | **极致**（天生支持水平伸缩与微服务跨服务鉴权） |
| **强制下线 / 单设备限制**| **容易**（直接销毁 Session） | **极佳**（随时删除/修改 Redis Key） | **极难**（服务端无法收回已颁发的 Token，除非用 Redis 做黑名单） |
| **防 CSRF 攻击** | **弱**（受 Cookie 原生机制拖累） | **高**（请求头 Header 自定义传递，天然防范） | **高**（请求头 Header 自定义传递，天然防范） |
| **防篡改与完整性校验** | 天然防篡改（数据在服务端） | 天然防篡改（数据在服务端） | 基于服务端安全密钥的** HMAC-SHA256 数字签名** |
| **系统依赖性** | 无，开箱即用 | 强依赖 Redis 缓存的高可用 | 无，仅依赖服务端的加密/解密签名密钥 |
| **多客户端跨平台** | 差，非浏览器兼容复杂 | 极佳 | 极佳 |



## 三. 技术选型建议总结

在面对新项目架构设计时，您可以参考以下法则进行快速决策：

1. **选择 纯 Session**：
   如果您是在写一个**给企业内部少数人用的管理后台**，或者只是学校里的**课设/单机练习小项目**，没有集群部署诉求，且希望用最快的速度上线，不需要搭建 Redis 中间件。
2. **选择 Redis + Token**：
   如果您是在做**面向大众的互联网高并发系统**（如电商、社交、点评系统等），有集群负载均衡部署，且**对于安全性、用户在线状态的控制非常严格**（例如用户修改密码需要立刻让所有设备全部重新登录、管理员可以随时拉黑封禁某个恶意账号）。这是目前中大型系统最推荐的黄金标准方案。
3. **选择 JWT 令牌**：
   如果您是在搭建一个**纯无状态的分布式微服务系统**，或者需要做**一次性临时权限校验的 Token**（如文件临时防盗链下载链接、第三方平台联合登录回调 Token），且在业务层面上**完全不需要对用户会话进行强制撤销和强制踢人操作**。
