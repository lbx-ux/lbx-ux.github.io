# 一. 全局锁

**全局锁（Global Lock）是对整个 MySQL 数据库实例加锁，使整个数据库处于只读状态**。加锁后，所有数据更新语句（DML：增删改）、数据定义语句（DDL：建表、改字段等）以及更新类事务的提交都会被完全阻塞。

**核心命令与生命周期**

- **加全局锁**：

  ```sql
  flush tables with read lock; -- 简称 FTWRL
  ```

- **释放全局锁**：

  ```sql
  unlock tables;
  ```

- **自动释放机制**：如果执行 FTWRL 的客户端会话（Session）异常断开连接，MySQL 会自动释放该全局锁，避免系统永久挂死。



**典型场景：全库逻辑备份（全库一致性视图）**

- **原理**：在没有 MVCC（多版本并发控制）的存储引擎（如 MyISAM）中，全库备份期间若有更新，备份出的数据表之间视图会不一致。通过 FTWRL 冻结全库写操作，保证视图时间点统一。

**现代方案对比（InnoDB 引擎）**

| **方案**                    | **命令 / 配置**                                              | **机制**                           | **业务影响**                   |
| --------------------------- | ------------------------------------------------------------ | ---------------------------------- | ------------------------------ |
| **FTWRL 全局锁**            | `flush tables with read lock;`                               | 阻塞所有写操作与 DDL               | 严重影响业务写入（高危操作）   |
| **单事务快照备份** *(推荐)* | `mysqldump --single-transaction -u root -p 数据库>数据库.sql` | 利用 InnoDB 的 MVCC 在快照读下备份 | **零阻塞**，不影响正常写入业务 |
| **只读参数配置**            | `set global read_only = on;`                                 | 设置实例为只读（Super 权限除外）   | 常用作主从同步中的从库保护     |



**FTWRL 的潜在风险与生产隐患**

- **主库执行 FTWRL**：业务端所有写请求瞬间被挂起，连接池可能迅速爆满，导致整个应用服务崩溃。
- **从库执行 FTWRL**：从库无法执行主从复制的 Relay Log，导致主从延迟（Replication Lag）不断增大。
- **长事务阻塞 FTWRL**：FTWRL 在生效前需要等待所有正在运行的事务完成并关闭打开的表。如果库中存在长查询，FTWRL 会被阻塞，并连带阻塞之后的所有写请求。



# 二. 表级锁

**MySQL 的表级锁（Table-level Lock）作用于整张数据表**，加锁开销小、速度快，但锁粒度最大、并发冲突概率最高。

MySQL 中的表级锁主要分为以下四种：

## 1. 表锁

由存储引擎或客户端显式控制，MyISAM 引擎默认采用此机制，InnoDB 极少主动使用。

一旦会话执行了 `LOCK TABLES`，MySQL 会将该会话置于严格的限制状态：**当前会话只能访问本次显式锁定的表，访问其他任何表都会直接报错。**

- **表共享读锁 (Table Read Lock)**：

  - ```sql
    lock tables 表名 read;
    ```

  - 当前会话和其他会话只能读取该表，无法写入；当前客户端的写操作会被报错，其他会话的写操作会被阻塞。

- **表独占写锁 (Table Write Lock)**：

  - ```sql
    lock tables 表名 write
    ```

  - 当前会话可以读写该表；其他会话的所有读写操作均被阻塞。

- **释放锁**：

  - ```sql
    unlock tables;   /  会话断开
    ```





## 2. 元数据锁

元数据锁（Metadata Lock，简称 MDL）是 MySQL Server 层自动维护的表级隐式锁（MySQL 5.5 引入）。其核心作用是**保证并发读写与表结构变更的一致性**，**防止一个事务在查询或修改数据时，另一个会话修改或删除了表结构。**（避免DDL与DML冲突）

MDL 不需要也不支持显式声明，所有 SQL 执行时均由系统自动申请与释放：

- **MDL 读锁**：执行 CRUD（DML/DQL）时自动添加，允许多个事务并发读写数据（读读兼容）。
- **MDL 写锁**：执行 `ALTER TABLE`、`DROP TABLE` 等表结构变更（DDL）时自动添加，与所有 MDL 读 写互斥。



> **MDL 的释放时机是当前事务提交（`COMMIT`）或回滚（`ROLLBACK`），而不是单条语句执行完毕。**

如果开启了事务（如 `begin; select * from t;`）但迟迟没有 `commit`，该连接将**一直持有该表的 MDL 读锁**，直到事务结束或连接断开。



**生产级陷阱：MDL 队列头阻塞**

由于 MySQL 为了防止 DDL 饿死，**MDL 写锁的排队优先级高于读锁**，这极易引发连锁雪崩：

```Plaintext
时间线：
1. 会话 A: BEGIN; SELECT * FROM t WHERE id=1; ───> 事务未提交，持续持有【MDL 读锁】
2. 会话 B: ALTER TABLE t ADD c INT;        ───> 申请【MDL 写锁】，被 A 阻塞，进入排队队列
3. 会话 C: SELECT * FROM t WHERE id=2;        ───> 申请【MDL 读锁】，被排在前面的 B 阻塞！
4. 会话 D, E, F... 所有后续 CRUD 语句全部被阻塞！
   ▼
结果：表不可用，应用端数据库连接池在几秒内迅速耗尽，整库业务瘫痪。
```

在对表结构变更时，先看看数据库中的长事务，是否有事务已经对表加上了MDL读锁，可以考虑kill掉这个长事务，然后再做表结构的变更。





## 3. 意向锁 

意向锁(Intention Lock - InnoDB 特有)是 InnoDB 自动加的**表级标记锁**，核心作用是**快速判断表中是否有行被锁定**，避免全表逐行扫描来检测行锁冲突。

- **意向共享锁 (IS)**：声明“本事务准备对表中某些行进行**读锁定**”、

  - ```sql
    select ... lock in share mode;
    ```
  - 事务在给某些行加行级 S 锁前，必须先获取该表的 IS 锁。

- **意向排他锁 (IX)**：声明“本事务准备对表中某些行进行**写锁定**”

  - ```sql
    insert , update , delete , select ... for update;
    ```
  - 事务在给某些行加行级 X 锁前，必须先获取该表的 IX 锁。

- *关键特性*：意向锁之间（IS 与 IX）、意向锁与行锁之间**完全互不排斥**，它们只与显式表级 S / X 锁冲突。

**表锁与意向锁兼容性矩阵**

| **当前持有的锁 \ 请求的锁** | **表级 S 锁** | **表级 X 锁** | **意向共享锁 (IS)** | **意向排他锁 (IX)** |
| --------------------------- | ------------- | ------------- | ------------------- | ------------------- |
| **表级 S 锁**               | **兼容**      | 互斥          | **兼容**            | 互斥                |
| **表级 X 锁**               | 互斥          | 互斥          | 互斥                | 互斥                |
| **意向共享锁 (IS)**         | **兼容**      | 互斥          | **兼容**            | **兼容**            |
| **意向排他锁 (IX)**         | 互斥          | 互斥          | **兼容**            | **兼容**            |



这个表格展示的是：**当一个事务已经对一张表加了某种锁时，另一个事务来申请加锁，是能直接执行（兼容）还是必须排队等待（互斥）。**

要彻底看懂这张表，先把这 4 种锁翻译成大白话：

- **表级 S 锁**：**“整表只读锁”**（`LOCK TABLES t READ`）。宣布整张表被冻结，谁都不许改，所有人只能读。
- **表级 X 锁**：**“整表独占锁”**（`LOCK TABLES t WRITE`）。宣布我要包场，别人既不能读也不能写。
- **意向共享锁 (IS)**：**“打个招呼：我想读表里的某几行”**（由 `SELECT ... FOR SHARE` 自动在表上挂个标记）。
- **意向排他锁 (IX)**：**“打个招呼：我想改表里的某几行”**（由 `UPDATE / DELETE / INSERT` 自动在表上挂个标记）。

**拆解矩阵核心规则**

**1. 意向锁之间完全兼容（右下角 4 格全是“兼容”）**

- **现象**：`IS` 与 `IS`、`IS` 与 `IX`、`IX` 与 `IX` 之间**绝不互斥**。
- **为什么**：
  - 事务 1 在修改 `id = 1` 的行（表上自动挂 `IX` 锁）；
  - 事务 2 在修改 `id = 2` 的行（表上同样自动挂 `IX` 锁）；
  - 它们改的是不同的行，在**表级别**不应该打架。因此表级意向锁之间完全兼容，行冲突交给具体的行锁去判断。

**2. 表级 X 锁与一切互斥（第二行、第二列全是“互斥”）**

- **现象**：只要有人想对整张表加独占锁（`LOCK TABLES t WRITE`），或者表上已经有了独占锁，其他任何锁都进不来。
- **为什么**：表级写锁要求**完全独占整张表**。哪怕别人只是在读单行（持有 `IS`）或在写单行（持有 `IX`），表级 X 锁都必须老老实实排队等待对方事务提交。

**3. 表级 S 锁与意向锁的逻辑**

- **表级 S 锁 + IS（兼容）**：
  - 当前有人锁定了整张表只读（表级 S 锁），另一个事务想读某几行（申请 `IS` 锁）。
  - *结果*：大家都是读操作，允许同时读取。
- **表级 S 锁 + IX（互斥）**：
  - 当前有人锁定了整张表只读（表级 S 锁），另一个事务想去修改某几行（申请 `IX` 锁）。
  - *结果*：整张表处于只读状态，禁止任何写操作，必须阻塞等待。

**一句话总结**

> **意向锁（IS / IX）只是行锁在表级别的“信号灯”，它存在的唯一目的就是为了阻挡显式的“整表锁（Table S / Table X）”，普通事务之间的增删改查彼此完全不受意向锁影响。**





## 4. AUTO-INC 锁（自增锁）

AUTO-INC 锁（自增锁）是 MySQL InnoDB 存储引擎在向包含 `AUTO_INCREMENT` 自增列的表插入数据时，使用的一种特殊的表级锁。

它的核心目标是：**保证在多个事务并发插入数据时，自增主键的值能够安全、唯一且有序地递增分配。**

**AUTO-INC 锁与普通表锁的区别**

- **普通表锁**：生命周期通常持续到**整个事务提交或回滚**。
- **AUTO-INC 锁**：生命周期通常只维持在**单条 `INSERT` 语句执行期间**（分配完自增 ID 即可释放，无需等待整个大事务提交）。



InnoDB 提供了参数 `innodb_autoinc_lock_mode`（取值 `0`、`1`、`2`），用于在**并发写入性能**与**自增 ID 连续性 / 主从复制安全**之间进行权衡。

在理解参数前，先区分两类插入语句：

- **简单插入（Simple Inserts）**：能预先确定插入行数的语句，例如单行/多行 `INSERT INTO t(name) VALUES ('a'), ('b');`。
- **批量插入（Bulk Inserts）**：无法预先确定插入行数的语句，例如 `INSERT INTO ... SELECT`、`LOAD DATA`、`REPLACE ... SELECT`。

**模式 0：传统模式（Traditional）**

- **机制**：所有 `INSERT` 语句（无论简单还是批量）都会申请**表级别的 AUTO-INC 锁**，直到该语句执行完毕才释放。
- **特点**：并发写入性能最低，多线程批量插入必须强行排队。



**模式 1：连续模式（Consecutive - MySQL 5.7 默认值）**

- **机制**：
  - **简单插入**：采用**轻量级互斥锁（Mutex）\**分配 ID，分配完毕后\**立即释放锁**，不需要等语句执行结束。
  - **批量插入**：仍然申请**表级别的 AUTO-INC 锁**，直到语句执行结束才释放。
- **特点**：提升了普通简单插入的并发性能，同时保证了单条批量插入语句内部生成的自增 ID 是连续的，兼容 Statement 格式的 Binlog 主从复制。



**模式 2：交叉模式（Interleaved - MySQL 8.0 默认值）**

- **机制**：所有插入语句（包括批量插入）**完全不再使用表级 AUTO-INC 锁**，一律采用轻量级的互斥锁分配自增 ID。
- **特点**：
  - **并发性能最高**，插入操作完全无锁阻塞。
  - **ID 交叉**：如果两个并发的批量插入同时运行，它们获取到的自增 ID 可能会相互穿插（例如事务 A 拿到 1, 3, 5，事务 B 拿到 2, 4, 6）。
  - **复制要求**：**必须搭配 Row 格式的 Binlog（`binlog_format=ROW`）**。如果使用 Statement 格式主从复制，会导致从库数据与主库 ID 不一致。



**三种模式对比表**

| **参数模式** | **模式名称** | **简单插入机制**      | **批量插入机制**      | **并发性能** | **默认版本**  | **Binlog 格式要求** |
| ------------ | ------------ | --------------------- | --------------------- | ------------ | ------------- | ------------------- |
| **0**        | Traditional  | 表级 AUTO-INC 锁      | 表级 AUTO-INC 锁      | 低           | 旧版本        | 任意格式            |
| **1**        | Consecutive  | 轻量 Mutex (快分即释) | 表级 AUTO-INC 锁      | 中等         | **MySQL 5.7** | 任意格式            |
| **2**        | Interleaved  | 轻量 Mutex (快分即释) | 轻量 Mutex (快分即释) | **极高**     | **MySQL 8.0** | **必须为 ROW**      |



**为什么自增 ID 会出现“断层 / 空洞”（不连续）？**

很多开发者疑惑为什么自增 ID 经常跳过某些数字（如从 1 跳到 5），这并非 Bug，而是由以下机制导致的正常现象：

1. **事务回滚（Rollback）**：事务 A 申请了自增 ID（如 `id=2`），随后执行失败或主动 `ROLLBACK`。出于并发性能考虑，**已分配的自增 ID 绝不会回滚退回**，导致该 ID 永久空缺。
2. **唯一键冲突（Duplicate Key）**：插入时如果因为唯一索引冲突而报错失败，此时自增 ID 计数器已经被消耗递增了一次。
3. **批量插入预分配（Batch Prefetching）**：对于未知行数的批量插入（如 `INSERT ... SELECT`），InnoDB 会按照指数级预先申请自增 ID 区间（如每次申请 1、2、4、8... 个 ID）。如果实际插入的行数没有用完预分配的配额，多余申请的 ID 就被直接废弃，形成空洞。



- **业务逻辑不要依赖“严格自增连续”**：自增主键只保证**唯一性与趋势递增**，绝不能用来做诸如“连续发票编号”、“无缝流水号”等对连续性有严苛要求的业务逻辑。
- **MySQL 8.0 默认配置无需调整**：MySQL 8.0 默认即为 `innodb_autoinc_lock_mode=2` 且 `binlog_format=ROW`，已经是并发吞吐最高的最佳组合。



#  三. 行锁

行级锁（Row-level Lock）是 MySQL InnoDB 存储引擎独有的核心特性。它的锁粒度最小、并发冲突率最低，但加锁开销最大。

> **核心底层原理**：InnoDB 的行锁**锁定的不是物理数据行，而是索引项（Index Record）**。如果一条 SQL 语句没有命中任何索引，InnoDB 必须通过全表扫描来定位数据，此时会把整张表的所有记录和间隙全部锁住。

| **锁类型**               | **触发方式**                                          | **读读** | **读写 / 写读** | **写写** |
| ------------------------ | ----------------------------------------------------- | -------- | --------------- | -------- |
| **共享锁 (S 锁 / 读锁)** | `SELECT ... FOR SHARE` (或 `LOCK IN SHARE MODE`)      | **兼容** | 互斥            | 互斥     |
| **排他锁 (X 锁 / 写锁)** | `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`、`INSERT` | 互斥     | 互斥            | 互斥     |

***快照读（普通 `SELECT`）基于 MVCC 实现，不加任何锁，与任何行锁都互不干扰。***



## 1. 行锁种类

### Record Lock（记录锁）

- **作用**：精准锁定单条存在的索引记录。
- **加锁区间**：仅仅锁定单条记录本身。
- **触发场景**：通过主键或唯一索引进行**等值查询**且记录存在（如 `WHERE id = 10 FOR UPDATE`）。



### Gap Lock（间隙锁）

- **作用**：锁定索引记录之间的开区间 $(a, b)$，**不包含记录本身**。它的唯一目的就是阻止其他事务向该区间插入（`INSERT`）新数据，从而杜绝幻读。
- **特性**：间隙锁之间互不排斥。两个不同的事务可以同时在一个间隙上持有 Gap Lock。



### Next-Key Lock（临键锁）

- **定义**：**Record Lock + Gap Lock 的组合**，锁定左开右闭区间 $(a, b]$。
- **地位**：InnoDB 在可重复读（RR）隔离级别下的**默认加锁单位**。



### Insert Intention Lock（插入意向锁）

- **机制**：事务在执行 `INSERT` 向某个间隙插入数据前，必须在该间隙上设置的一种特殊意向锁。
- **特性**：若多个事务向同一个间隙的不同位置插入数据，它们之间**互不阻塞**，能并发完成插入。
  - 在执行插入语句的时候，如果插入的记录在其他事务持有间隙锁的范围内，插入语句就会被阻塞，因为插入语句在碰到间隙锁的时候，会生成一个插入意向锁，然后插入意向锁和间隙锁之间是互斥的关系




## 2. 加锁规则

InnoDB 加锁的基本单元是 **Next-Key Lock**，在特定条件下（RR隔离级别）会自动降级（退化）：

### 唯一索引 / 主键等值查询

- 记录**存在**：Next-Key Lock 降级为 **Record Lock**（只锁该记录）。
- 记录**不存在**：Next-Key Lock 降级为 **Gap Lock**（只锁目标值所在的空隙）。



**问题一 : 为什么在唯一索引 / 主键等值查询记录不存在的时候，要加一个锁住目标值所在的间隙呢**

>加间隙锁的核心目的只有一个：**防止其他事务趁机“插入”这条数据，从而解决并发场景下的“幻读”和数据一致性问题。**
>
>虽然当前“没有这条数据”，但“现在没有”不代表“等会儿也没有”。
>
>**如果不加间隙锁，会发生什么严重问题？**
>
>假设表里只有 `id = 5` 和 `id = 10` 两条记录，不存在 `id = 7`：
>
>```
>时刻   事务 A (开启事务)                             事务 B (并发执行)
>─────────────────────────────────────────────────────────────────────────────
>T1     SELECT * FROM t WHERE id = 7 FOR UPDATE;
>  -- 查无此人。如果不加锁...
>
>T2                                                  INSERT INTO t (id) VALUES (7);
>                                               COMMIT;
>                                               -- 事务 B 成功把 id=7 插了进去！
>
>T3     -- 事务 A 再次执行当前读:
>  SELECT * FROM t WHERE id = 7 FOR UPDATE;
>  -- 凭空多出了一条 id=7 的数据！(产生幻读)
>
>  -- 或者事务 A 误以为 7 依然不存在，执行:
>  INSERT INTO t (id) VALUES (7);
>  -- 报错: 主键冲突 Duplicate entry '7' (明明刚查过没有，插入却报错！)
>```
>
>事务 A 显式执行了 `FOR UPDATE`，本质意图是：**“在我的事务结束前，我要独占 `id = 7` 的状态（不论它存不存在），谁都别想动它。”**
>
>
>
>**为什么不直接锁“7”，而要锁一个“间隙 $(5, 10)$”？**
>
>因为在底层 B+ 树的索引页中，**物理上根本不存在 `id = 7` 这条索引记录**。
>
>- InnoDB 的行锁本质是挂在**索引节点**上的。既然没有 `7` 这个节点，锁就无处可挂。
>- 为了彻底阻止别人插入 `id = 7`，InnoDB 只能退而求其次：**把 `7` 所在的那片空地 $(5, 10)$ 整个拦上警戒线（加间隙锁）**。
>- 一旦加了 $(5, 10)$ 的间隙锁，其他事务再想执行 `INSERT INTO t(id) VALUES (7)`，就会被锁拦截并排队等待。
>
>
>
>**典型业务场景：防并发重复插入**
>
>很多业务逻辑是典型的“先查后插”：
>
>1. 查某唯一流水号 / 邀请码是否存在（`SELECT ... WHERE code = 'ABC' FOR UPDATE`）。
>2. 如果不存在，则生成并插入数据（`INSERT INTO ... VALUES ('ABC')`）。
>
>如果查询不存在时**不加间隙锁**，两个并发请求会同时查出“不存在”，随后双双执行 `INSERT`，导致主键/唯一索引冲突报错。而有了间隙锁，后来的请求在查询或插入时就会被阻塞，从而保证了严格的串行化安全。
>
>> **一句话总结**：
>
>> 记录存在时，锁**记录本身**（防止别人改/删）；
>
>> 记录不存在时，锁**整片间隙**（防止别人凭空造出来）。





**问题二：通过唯一二级索引加锁时，是否会锁聚簇索引**


>**通过唯一二级索引加锁时，是否会锁聚簇索引取决于「记录是否存在」：**
>
>- **如果通过主键查询**：只给**聚簇索引**加锁。
>- **如果通过唯一二级索引查询**：
>  - **记录存在**：**二级索引和聚簇索引都会被加锁**（两个索引都加记录锁）。
>  - **记录不存在**：**只在二级索引上加间隙锁（Gap Lock）**，聚簇索引不会加锁。
>
>
>
> **唯一二级索引：记录存在时的加锁流程**
>
>假设表结构为 `t(id PRIMARY KEY, code UNIQUE, name)`，执行：
>
>```sql
>SELECT * FROM t WHERE code = 'A' FOR UPDATE;
>```
>
>若 `code = 'A'` 存在（对应的主键为 `id = 1`）：
>
>1. **第一步（查二级索引）**：InnoDB 在 `code` 的唯一索引树上找到 `'A'` 节点，对该**二级索引记录加 X 记录锁**。
>2. **第二步（回表查聚簇索引）**：根据对应的主键 `id = 1` 回到聚簇索引树，对主键 `id = 1` 的**聚簇索引记录也加上 X 记录锁**。
>
>> **为什么要两边都加锁？**
>>
>> 如果只锁二级索引，另一个并发事务执行 `UPDATE t SET name = 'xxx' WHERE id = 1`（走主键索引更新）就无法感知到锁定，会直接篡改数据，破坏事务隔离性。因此**只要发生了回表定位实体行，聚簇索引必须加锁**。
>
>
>
>**唯一二级索引：记录不存在时的加锁流程**
>
>执行：
>
>```sql
>SELECT * FROM t WHERE code = 'B' FOR UPDATE;
>```
>
>若 `code = 'B'` 不存在（在二级索引中处于 `'A'` 与 `'C'` 之间）：
>
>1. **查二级索引**：InnoDB 扫描 `code` 唯一索引树，未找到 `'B'`。
>2. **加间隙锁**：在二级索引树上给区间 `('A', 'C')` 加上 **Gap 锁**，防止别人插入 `code = 'B'`。
>3. **结束流程**：因为根本没有这行数据，**不需要也不会发生回表**，所以**聚簇索引上没有任何锁**。
>
>
>
>**锁分布对比一览**
>
>| **查询方式**             | **数据状态**   | **唯一二级索引上的锁** | **聚簇索引（主键）上的锁**  |
>| ------------------------ | -------------- | ---------------------- | --------------------------- |
>| **主键等值查询**         | 记录存在       | 无二级索引参与         | **Record Lock**（仅锁主键） |
>| **主键等值查询**         | 记录不存在     | 无二级索引参与         | **Gap Lock**（锁主键间隙）  |
>| **唯一二级索引等值查询** | **记录存在**   | **Record Lock**        | **Record Lock**（回表加锁） |
>| **唯一二级索引等值查询** | **记录不存在** | **Gap Lock**           | **无锁**（无需回表）        |





### 唯一索引 / 主键范围查询

在可重复读（RR）隔离级别下，**唯一索引 / 主键的范围查询**加锁规则与等值查询有显著不同：

> **核心原则**：范围查询为了彻底防止范围内的“幻读（新数据插入）”，**加锁的基本单位是 Next-Key Lock（左开右闭区间 $(a, b]$）**。范围查询通常**不会**像等值查询那样完全降级为单点记录锁（Record Lock），但在边界扫描处存在特定的优化退化规则。
>
> 这个Next-Key Lock虽然是一个左闭右开的区间，但是不能合并，有几个就是几个



当唯⼀索引进⾏范围查询时，会对每⼀个扫描到的索引加 **next-key** 锁，然后如果遇到下⾯这些情况，会退化成记录锁或者间隙锁：

- 情况⼀：针对「⼤于等于」的范围查询，因为存在等值查询的条件，那么如果等值查询的记录是存在于表中，那么该记录的索引中的 next-key 锁会退化成记录锁。
- 情况⼆：针对「⼩于或者⼩于等于」的范围查询，要看条件值的记录是否存在于表中：
  - 当条件值的记录不在表中，那么不管是「⼩于」还是「⼩于等于」条件的范围查询，扫描到终⽌范围查询的记录时，该记录的索引的 **next-key** 锁会退化成间隙锁，其他扫描到的记录，都是在这些记录的索引上加 next-key 锁。
  - 当条件值的记录在表中，如果是「⼩于」条件的范围查询，扫描到终⽌范围查询的记录时，该记录的索引的 **next-key** 锁会退化成间隙锁，其他扫描到的记录，都是在这些记录的索引上加 next-key 锁；
  - 如果「⼩于等于」条件的范围查询，扫描到终⽌范围查询的记录时，该记录的索引 next-key 锁不会退化成间隙锁。其他扫描到的记录，都是在这些记录的索引上加 next-key 锁。





为方便理解，假设表 `t(id INT PRIMARY KEY, val INT)` 中现有以下 4 条记录：

```
主键记录：5, 10, 15, 20
间隙分布：(-∞, 5], (5, 10], (10, 15], (15, 20], (20, +supremum]
```

*(注：`supremum` 是 InnoDB 在索引页最后维护的虚拟上限伪记录，代表 $+\infty$)*



**规则一：大于 / 大于等于范围查询（`>` 与 `>=`）**

**1. 大于等于查询：`WHERE id >= 10 FOR UPDATE`**

- **边界等值匹配**：首先定位到 `id = 10`。因为 `id` 是主键/唯一索引，且是精准等值命中，所以对 `id = 10` 的 Next-Key Lock $(5, 10]$ 会**降级为 Record Lock（仅锁记录 10）**。
- **向右范围扫描**：继续向右扫描所有记录并加 **Next-Key Lock**，直到最大伪记录：
  - $(10, 15]$
  - $(15, 20]$
  - $(20, +\text{supremum}]$
- **最终锁定区间**：记录 `10`（id = 10 记录本身加记录锁）以及开区间 $(10, +\infty)$。



**2. 大于查询：`WHERE id > 10 FOR UPDATE`**

- **定位起始点**：先定位到第一个不满足条件的记录 `id = 10`，由于是严格大于（`>`），不包含 10 本身，直接从 `10` 往右扫描。
- **向右范围扫描**：依次加 Next-Key Lock：
  - $(10, 15]$
  - $(15, 20]$
  - $(20, +\text{supremum}]$
- **最终锁定区间**：开区间 $(10, +\infty)$（`id = 10` 本身不加记录锁）。



**规则二：小于 / 小于等于范围查询（`<` 与 `<=`）**

**1. 小于等于查询：`WHERE id <= 10 FOR UPDATE`**

- **向左扫描范围**：从左往右依次扫描至 `id = 10`，逐个加上 Next-Key Lock：
  - $(-\infty, 5]$
  - $(5, 10]$
- **边界停止条件**：扫描到 `id = 10` 时发现条件满足，且因为是**唯一索引**，后续不可能再有符合条件的记录，**扫描直接停止，不会继续往右扫描**。
- **最终锁定区间**：$(-\infty, 10]$。



**2. 小于查询：`WHERE id < 10 FOR UPDATE`（经典退化场景）**

- **扫描命中**：依次扫描 `5`，加上 Next-Key Lock $(-\infty, 5]$。
- **扫描到第一个不符合条件的记录 `id = 10`**：
  - 按照通用 Next-Key Lock 规则，原本应对 10 加上 $(5, 10]$。
  - 但由于查询条件是严格小于（`id < 10`），不包含 10 本身，且 `id` 为唯一索引；
  - InnoDB 会对 `id = 10` 上的 Next-Key Lock 进行**优化降级，退化为 Gap Lock（间隙锁）$(5, 10)$**。
- **最终锁定区间**：$(-\infty, 5]$ 以及间隙 $(5, 10)$（即 $(-\infty, 10)$，`id = 10` 这条物理记录本身**未被加锁**）。



**规则三：唯一二级索引的范围查询**

若使用非主键的唯一二级索引（Unique Secondary Index）进行范围查询：

1. **二级索引树加锁**：完全遵循上述的 Next-Key Lock 及退化规则，在二级索引上锁定所有命中的记录区间。
2. **聚簇索引（主键）加锁**：
   - 仅对范围查询**实际匹配命中**的实体记录，回表对其主键加上 **Record Lock（记录锁）**。
   - **主键索引上的间隙不会被加锁**（防幻读的间隙锁已经在二级索引树上生效了）。



**加锁范围总结速查表（基于数据 5, 10, 15, 20）**

| **范围查询 SQL**             | **实际锁定的区间与类型**                        | **说明**                              |
| ---------------------------- | ----------------------------------------------- | ------------------------------------- |
| `WHERE id >= 10`             | 记录 `[10]` (Record) + `(10, +∞]` (Next-Key)    | 10 命中等值降级为记录锁，右侧全部锁定 |
| `WHERE id > 10`              | `(10, +∞]` (Next-Key)                           | 10 不锁，右侧全部 Next-Key 锁         |
| `WHERE id <= 10`             | `(-∞, 5]` (Next-Key) + `(5, 10]` (Next-Key)     | 唯一索引扫描至 10 即停止              |
| `WHERE id < 10`              | `(-∞, 5]` (Next-Key) + `(5, 10)` **(Gap Lock)** | 10 上的 Next-Key 锁退化为间隙锁       |
| `WHERE id BETWEEN 10 AND 15` | 记录 `[10]` + `(10, 15]` (Next-Key)             | 10 退化为记录锁，15 锁定 Next-Key     |





### 非唯一索引等值查询

在可重复读（RR）隔离级别下，**非唯一普通索引（二级索引）的等值查询**加锁规则比唯一索引更复杂。

**命中记录加临键锁，并继续向右遍历到第一个不满足条件的记录，退化为间隙锁。**

因为非唯一索引的值允许重复，InnoDB 不仅要锁住**已有相同值的记录**，还必须锁住**该值左侧和右侧的所有间隙**，彻底杜绝其他事务在任何可能的位置插入相同的数值（防止幻读）。

**示例数据假设**

假设表结构为 `t(id INT PRIMARY KEY, age INT, INDEX(age))`，包含以下数据：

```
主键 id:   1     5     10     15
索引 age:  10    20    20     30
```

> **注意**：二级索引 B+ 树叶子节点的底层排序是 **`(age, id)` 联合递增**：
>
> ```
> (10, 1) -> (20, 5) -> (20, 10) -> (30, 15)
> ```



**情况一：记录存在（如 `WHERE age = 20 FOR UPDATE`）**

当等值查询的记录在表中存在时，加锁分为 **二级索引** 和 **聚簇索引（主键）** 两部分：

**1. 二级索引（`age`）上的加锁过程：**

1. **向右扫描所有命中记录**：

   - 扫描到第一条 `age=20 (id=5)`，加 **Next-Key 锁**，锁定区间：

     $$(10, 20]$$

   - 扫描到第二条 `age=20 (id=10)`，加 **Next-Key 锁**，锁定区间：

     $$(20, 20]$$

2. **向右继续扫描到第一个不符合条件的记录**：

   - 扫描到 `age=30 (id=15)`，发现不满足 `age = 20`。

   - **触发退化**：由于该记录不符合查询条件，记录 `30` 本身不需要被锁定，因此该记录上的 Next-Key 锁**退化为间隙锁（Gap Lock）**，锁定区间：

     $$(20, 30)$$

   - 扫描停止。

> **二级索引最终锁定效果**：
>
> $$(10, 20] + (20, 30) \Longrightarrow \mathbf{(10, 30)}$$
>
> **效果**：不仅现有的两个 `20` 被锁住，任何试图在 `10` 到 `30` 之间插入 `age = 20` 的操作都会被彻底阻断。



**2. 聚簇索引（主键 `id`）上的加锁过程：**

- 只有**实际命中的数据行**回表时，会对对应的主键加上 **Record Lock（记录锁）**：
  - 主键 `id = 5` 加记录锁
  - 主键 `id = 10` 加记录锁
- **聚簇索引上不会加间隙锁**（因为间隙已由二级索引守住）。



**情况二：记录不存在（如 `WHERE age = 25 FOR UPDATE`）**

当查询的值不存在时：

**1. 二级索引（`age`）上的加锁过程：**

- 定位到第一个大于 25 的记录，即 `age = 30 (id = 15)`。

- 按照规则，对 `30` 加 Next-Key 锁 $(20, 30]$。

- **触发退化**：因为这是等值查询且该记录不匹配，Next-Key 锁**退化为间隙锁（Gap Lock）**，锁定区间：

  $$(20, 30)$$

- 扫描停止。



**2. 聚簇索引（主键 `id`）上的加锁过程：**

- 因为没有命中任何记录，**无需回表，聚簇索引完全不加锁**。



**为什么非唯一索引需要“向右多扫一条并退化为间隙锁”？**

- **唯一索引**：因为唯一性约束，只要找到一条记录，就能**百分之百确定后面绝不可能再有相同的值**，所以当场降级为记录锁并立即停止扫描。
- **非唯一索引**：找到了 `age = 20` 之后，InnoDB 无法确定后面还有没有其他的 `age = 20`，所以**必须一直往右扫描，直到撞见第一个不等于 20 的记录（即 `age=30`）才能停下来**。
- 既然扫描到了 `age=30`，为了封住 `(20, 30)` 这个右侧间隙（防止别人插入 `age=20`），就必须在这个记录上加锁；但又因为 `30` 本身不需要被修改锁定，所以退化为**间隙锁**。



**唯一索引 vs 非唯一索引【等值查询】加锁对比**

| **查询类型**        | **记录存在**                                                 | **记录不存在**                                               |
| ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **主键 / 唯一索引** | **仅 Record Lock**  （只锁该记录，无需锁前后间隙）           | **Gap Lock**  （锁定目标值所在的空隙）                       |
| **非唯一普通索引**  | **Next-Key Lock + 右侧 Gap Lock**  （二级索引锁住左右整个开区间；聚簇索引仅对命中行加 **Record Lock**） | **Gap Lock**  （二级索引锁住目标值所在空隙；聚簇索引**不加锁**） |



### 非唯一索引范围查询

按索引扫描范围依次添加 Next-Key Lock，不会发生降级。



## 3. RC vs RR

| **特性对比**          | **读已提交 (RC)**                                 | **可重复读 (RR)**                    |
| --------------------- | ------------------------------------------------- | ------------------------------------ |
| **默认行锁算法**      | **仅 Record Lock**                                | **Next-Key Lock**                    |
| **间隙锁 (Gap Lock)** | 默认关闭（仅在外键与唯一性检查时生效）            | 开启（用于彻底防止幻读）             |
| **锁持有与释放**      | 语句执行完后，不符合 `WHERE` 条件的行锁会立即释放 | 行锁持续持有至**整个事务提交或回滚** |
| **并发与死锁**        | 并发吞吐高，死锁发生率极低                        | 间隙锁易导致并发插入冲突与死锁       |





# 四. 危害

## 1. 无索引更新锁全表

“无索引更新锁全表”是 MySQL 生产环境中最危险、最常见的高危事故之一。

虽然直观上看起来是“锁住了整张表”，但在底层的实现机制、隔离级别差异以及排查治理上，有着非常严密的逻辑。



> **核心结论：它不是表级锁（Table Lock），而是对主键聚簇索引上的“所有记录”和“所有间隙”都加上了行级排他锁（Next-Key Lock）。**

1. **InnoDB 的锁是挂在索引上的**：当执行 `UPDATE user SET status = 1 WHERE name = 'Tom';` 时，如果 `name` 字段没有索引，MySQL Server 层无法直接定位数据，只能要求 InnoDB 存储引擎进行**全表扫描（Full Table Scan）**。
2. **扫描一行，加锁一行**：InnoDB 沿着主键聚簇索引树从头扫描到尾。每扫描到一条主键记录，就会先加上排他锁（X 锁）。



**隔离级别的决定性差异（RR vs RC）**

全表扫描时的加锁行为在不同的事务隔离级别下截然不同：

```
假设表中数据为：id = 1, 5, 10, 15。目标更新：WHERE name = 'Tom' (只有 id=5 匹配)
```

| **隔离级别**                      | **加锁算法**                         | **不符合条件的行何时释放锁？**                               | **最终结果**                                                 |
| --------------------------------- | ------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **可重复读 (RR)**  *(MySQL 默认)* | **Next-Key Lock**  (记录锁 + 间隙锁) | **不会释放**。  必须持有到**整个事务提交/回滚**。            | **彻底冻结整张表！**  所有区间的修改和并发插入全被阻塞：  $(-\infty, 1], (1, 5], (5, 10], (10, 15], (15, +\infty)$ |
| **读已提交 (RC)**                 | **仅 Record Lock**  (间隙锁默认关闭) | **立即释放**。  MySQL 评估 `name != 'Tom'` 后立刻释放行锁（半一致性读特性）。 | **仅锁定 `id = 5` 这一行**。  全表扫描期间会有短暂行锁争用，但语句结束后只保留匹配行的锁。 |



**生产环境的破坏性影响**

一旦在 **RR 隔离级别** 下触发了无索引的 `UPDATE` 或 `DELETE`，且处于一个未提交的事务中：

1. **写入与修改全线瘫痪**：其他任何事务试图对该表执行 `INSERT`、`UPDATE`、`DELETE` 或 `SELECT ... FOR UPDATE`，无论操作哪一行、插入什么数据，都会**全部陷入锁等待排队**。
2. **连接池瞬间打满**：上游业务线程全部被阻塞在数据库锁等待上，应用端连接池在数秒内耗尽，连带导致整个微服务集群不可用。
3. **连锁报错**：大量并发请求在等待一定时间后，触发 `ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction` 批量报错。



**生产防护与最佳实践**

- **强制开启安全更新模式（强制走索引）**：

  在数据库或会话层开启安全更新，没有走索引或没有 `WHERE` 条件的 `UPDATE/DELETE` 会直接报错拒绝执行：

  ```sql
  SET SQL_SAFE_UPDATES = 1;
  ```

- **研发规范与 SQL 审查**：

  - 所有 `UPDATE` / `DELETE` 语句必须先通过 `EXPLAIN` 确认 `type` 为 `ref`、`eq_ref` 或 `range`，严禁 `type = ALL`。

  - 大批量更新拆解为基于主键的分批循环更新（如每次更新 500 条）：

    ```sql
    UPDATE user SET status = 1 WHERE id >= 1 AND id <= 500;
    ```

- **架构层面考量隔离级别**：

  高并发互联网系统普遍建议将数据库隔离级别设为 **RC（Read Committed）** + **ROW 格式 Binlog**，不仅可以避免间隙锁死锁，还能大幅降低全表扫描更新带来的阻塞灾难。

- **控制锁等待超时时间**：

  适当调低 `innodb_lock_wait_timeout`（如从默认的 50 秒调为 5~10 秒），防止慢事务长时间占满连接池。



## 2. 当前读解决幻读

在 MySQL InnoDB 引擎的可重复读（RR）隔离级别下，防止幻读主要依靠两条路线：

1. **快照读（普通 `SELECT`）**：通过 **MVCC（多版本并发控制 + Read View）** 解决。
2. **当前读（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 等）**：通过 **记录锁（Record Lock）+ 间隙锁（Gap Lock）= 临键锁（Next-Key Lock）** 解决。



**为什么「单靠记录锁」无法防止幻读？**

- **幻读的定义**：在同一个事务内，多次执行相同的范围查询，后一次查询看到了前一次没有看到的“新插入的数据行”。
- **记录锁的局限**：InnoDB 的行锁本质是挂在 **B+ 树已有的索引记录** 上的。如果表里只有 `id = 5` 和 `id = 10`：
  - 如果事务 A 执行 `SELECT * FROM t WHERE id >= 5 FOR UPDATE`，若只对已有的记录 `5` 和 `10` 加记录锁；
  - 此时事务 B 执行 `INSERT INTO t (id) VALUES (7);`，由于物理上根本没有 `id = 7` 这条记录，事务 B 不会触发任何记录锁冲突，顺利插入并提交；
  - 事务 A 再次执行当前读时，就会发现凭空多出了一条 `id = 7` —— **幻读产生**。

> **结论**：记录锁只能锁住**“已经存在的旧数据（防修改/删除）”**，无法锁住**“未来可能被插入的新数据”**。



**间隙锁 + 插入意向锁的互斥**

为了封堵新数据的插入通道，InnoDB 引入了 **间隙锁（Gap Lock）** 和 **插入意向锁（Insert Intention Lock）**：

1. **加间隙锁（拉起警戒线）**：
   - 事务 A 执行范围查询时，InnoDB 不仅对已有记录加记录锁，还对记录与记录之间的空隙（如 `(5, 10)`、`(10, +∞)`）加 **间隙锁（Gap Lock）**。
   - 间隙锁向外界宣告：“这片区间正在被我保护，任何人不准在这里落户”。
2. **申请插入意向锁（试图落户）**：
   - 事务 B 执行 `INSERT INTO t (id) VALUES (7)` 时，在实际写入 B+ 树页之前，**必须先在该间隙 `(5, 10)` 上申请一个「插入意向锁」**。
3. **底层锁冲突（触发阻塞）**：
   - 在 InnoDB 的锁兼容矩阵中：**间隙锁（Gap Lock）与 插入意向锁（Insert Intention Lock）是绝对互斥的！**
   - 事务 B 发现该间隙已被事务 A 加了间隙锁，其插入意向锁申请会被**立刻挂起阻塞**，进入锁等待排队。
   - 事务 B 无法插入数据 $\rightarrow$ 事务 A 在提交前无论查多少次，范围内都不会多出新行 $\rightarrow$ **彻底杜绝幻读**。



**完整并发执行时序演练**

假设表 `t` 中现有主键数据：`5`、`10`。

```
时刻   事务 A (当前读事务)                           事务 B (并发插入事务)
─────────────────────────────────────────────────────────────────────────────
T1     BEGIN;
       SELECT * FROM t 
       WHERE id >= 5 
       FOR UPDATE;
       
       【加锁分析】:
       1. 记录 5 加 Record Lock
       2. 区间 (5, 10] 加 Next-Key Lock
       3. 区间 (10, +∞) 加 Next-Key Lock
       👉 锁定范围等价于：[5, +∞)

T2                                                  BEGIN;
                                                    INSERT INTO t (id) VALUES (7);
                                                    
                                                    【底层加锁判定】:
                                                    1. 插入 7 需要在间隙 (5, 10) 
                                                       申请「插入意向锁」
                                                    2. 发现事务 A 持有该区间的「间隙锁」
                                                    💥 锁冲突！事务 B 被强制挂起阻塞...

T3     SELECT * FROM t 
       WHERE id >= 5 
       FOR UPDATE;
       👉 依然只查到 5 和 10，没有幻读！

T4     COMMIT; 
       -- 事务 A 提交，释放所有记录锁和间隙锁

T5                                                  -- 事务 B 被唤醒，获取锁并完成插入
                                                    COMMIT;
```



**两者分工总结**

| **锁类型**                 | **负责锁定的目标**        | **核心使命**                                                 |
| -------------------------- | ------------------------- | ------------------------------------------------------------ |
| **记录锁 (Record Lock)**   | **已存在**的物理索引记录  | 防止并发事务 **修改（`UPDATE`）** 或 **删除（`DELETE`）** 已有数据 |
| **间隙锁 (Gap Lock)**      | 记录之间的**空白区间**    | 与插入意向锁互斥，防止并发事务 **插入（`INSERT`）** 新数据   |
| **临键锁 (Next-Key Lock)** | **记录本身 + 其左侧间隙** | **两者的结合体**，同时解决数据篡改和数据凭空新增，彻底实现串行化保护 |

> **一句话概括**：
>
> 记录锁守住“已有的房子”，间隙锁圈住“空闲的宅基地”；别人既拆不掉老房子，也盖不起新房子，自然就不会发生幻读。





## 3. 死锁

死锁（Deadlock）**是指两个或多个事务在执行过程中，因互相持有对方所需的排他资源（锁），且都在等待对方释放资源，从而陷入**无限循环等待（Cyclic Wait）的僵死状态。



**InnoDB 死锁的自动检测与处理机制**

InnoDB 存储引擎拥有完善的死锁自主防御机制：

**1. 死锁检测机制（Wait-for Graph 等待图）**

- 参数：`innodb_deadlock_detect = ON`（默认开启）。

- **原理**：InnoDB 会在内存中实时维护事务之间的锁等待依赖图（有向图）。一旦发现图结构中出现了**环路（Cycle）**，判定发生死锁。

- **处理策略（回滚代价最小的事务）**：

  - InnoDB 会选择一个回滚代价最小的事务作为“受害者”（Victim）主动将其回滚。

  - 判定标准通常是：**产生的 Undo Log 量最小、持有行级排他锁最少**的事务。

  - 被回滚的事务会收到经典报错：

    ```
    ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
    ```



**2. 超时回滚机制（兜底策略）**

- 参数：`innodb_lock_wait_timeout`（默认 50 秒）。
- 若在高并发极度极端场景下主动关闭了死锁检测（为了降低 CPU 锁图扫描开销），事务在等待锁超过该超时时间后会被强行打断回滚。



**四大经典死锁复现场景与底层剖析**

**场景 1：相反的加锁顺序（最常见的业务死锁）**

两个事务同时批量更新多行数据，但加锁顺序相反。

```
时刻   事务 1 (trx_id=100)                     事务 2 (trx_id=200)
─────────────────────────────────────────────────────────────────────────────
T1     BEGIN;
       UPDATE user SET age=20 WHERE id=1;
       -- 持有 id=1 的 X 锁

T2                                            BEGIN;
                                              UPDATE user SET age=30 WHERE id=2;
                                              -- 持有 id=2 的 X 锁

T3     UPDATE user SET age=21 WHERE id=2;
       -- 申请 id=2 的 X 锁，被事务 2 阻塞等待...

T4                                            UPDATE user SET age=31 WHERE id=1;
                                              -- 申请 id=1 的 X 锁，被事务 1 阻塞！
                                              💥 触发死锁！InnoDB 回滚其中一个事务。
```



**场景 2：间隙锁 + 插入意向锁冲突（并发 INSERT 必踩雷区）**

**间隙锁（Gap Lock）之间彼此兼容，但间隙锁与插入意向锁（Insert Intention Lock）互斥。**

假设表里只有 `id = 5` 和 `id = 10` 两条记录：

```
时刻   事务 1                                  事务 2
─────────────────────────────────────────────────────────────────────────────
T1     BEGIN;
       SELECT * FROM t WHERE id=7 FOR UPDATE;
       -- 记录不存在，成功获取 (5, 10) 的间隙锁

T2                                            BEGIN;
                                              SELECT * FROM t WHERE id=8 FOR UPDATE;
                                              -- 间隙锁彼此兼容，事务 2 也成功获取 (5, 10) 的间隙锁

T3     INSERT INTO t (id) VALUES (7);
       -- 插入需要 (5, 10) 的插入意向锁
       -- 被事务 2 持有的间隙锁阻塞等待...

T4                                            INSERT INTO t (id) VALUES (8);
                                              -- 同样申请 (5, 10) 的插入意向锁
                                              -- 被事务 1 持有的间隙锁阻塞！
                                              💥 双方互相阻塞，触发死锁！
```



**场景 3：共享锁升级为排他锁（Lock Upgrade Deadlock）**

两个事务先读后写，共同持有读锁（S 锁），随后同时尝试升级为写锁（X 锁）。

```
时刻   事务 1                                  事务 2
─────────────────────────────────────────────────────────────────────────────
T1     BEGIN;
       SELECT * FROM t WHERE id=1 FOR SHARE;
       -- 持有 id=1 的 S 读锁

T2                                            BEGIN;
                                              SELECT * FROM t WHERE id=1 FOR SHARE;
                                              -- S 锁兼容，事务 2 也持有 id=1 的 S 读锁

T3     UPDATE t SET name='A' WHERE id=1;
       -- 申请 id=1 的 X 锁（必须等所有 S 锁释放）
       -- 被事务 2 的 S 锁阻塞...

T4                                            UPDATE t SET name='B' WHERE id=1;
                                              -- 申请 id=1 的 X 锁
                                              -- 被事务 1 的 S 锁阻塞！
                                              💥 互相等待对方释放 S 锁，触发死锁！
```



场景 4：主键索引与二级索引交叉更新

- 事务 1 先通过主键索引更新行，随后更新关联的唯一二级索引。
- 事务 2 通过唯一二级索引查找并更新，回表加主键锁。
- 两事务在不同的 B+ 树上以相反方向申请锁，引发死锁。



**如何排查与定位死锁？**

**1. 查看最近一次死锁日志**

```sql
SHOW ENGINE INNODB STATUS\G
```

找到 `------------------------ LATEST DETECTED DEADLOCK ------------------------` 区域，关键字段解析：

- `(1) TRANSACTION` / `(2) TRANSACTION`：参与死锁的两个事务信息及正在执行的 SQL。
- `WAITING FOR THIS LOCK TO BE GRANTED`：该事务在等待什么锁。
- `HOLDS THE LOCK(S)`：该事务持有什么锁。
- `WE ROLL BACK TRANSACTION (1)`：被选为受害者并回滚的事务。



**2. 将所有死锁记录持久化输出到日志（生产推荐开启）**

```sql
-- 开启后，每次发生死锁都会完整打印到 MySQL error.log 中，便于历史追溯
SET GLOBAL innodb_print_all_deadlocks = ON;
```



**生产环境死锁预防与优化策略**

- **业务端统一加锁顺序（最有效）**：

  涉及批量操作或多行更新时，在业务代码中**按主键或唯一键升序排序后**再执行 SQL（例如批量更新 ID 列表 `[3, 1, 5]`，先排成 `[1, 3, 5]` 再循环更新）。

- **避免“先 S 锁后 X 锁”升级**：

  如果业务后续确定要更新该行，查询时直接使用 `SELECT ... FOR UPDATE` 加 X 锁，切忌使用 `FOR SHARE` 随后再 `UPDATE`。

- **控制事务粒度（短小精悍）**：

  事务内只做纯数据库交互，严禁在事务代码中包含外部 HTTP 调用、MQ 投递或复杂耗时计算，缩短锁持有时间。

- **降级隔离级别至 RC（Read Committed）**：

  在读已提交（RC）级别下，**间隙锁（Gap Lock）默认关闭**，可以规避绝大多数由间隙锁引发的并发死锁。

- **应用层设计重试机制**：

  死锁在并发系统中无法 100% 杜绝，上游业务捕获 `1213 (Deadlock)` 异常后，应配合指数退避（Jitter/Backoff）进行**自动重试**（通常重试 1~3 次即可成功）。
