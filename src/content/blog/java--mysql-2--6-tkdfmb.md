# 一. undo log

Undo Log（回滚日志）是 MySQL InnoDB 存储引擎层生成的逻辑日志，主要用于**保证事务的原子性（Atomicity）以及支持 MVCC（多版本并发控制）**。

### 核心作用

- **保障事务原子性**：记录数据的反向操作。当事务执行失败或主动触发 `ROLLBACK` 时，InnoDB 会读取 Undo Log 执行反向操作（如 `INSERT` 对应 `DELETE`，`DELETE` 对应 `INSERT`，`UPDATE` 对应更新回旧值），使数据恢复至事务开始前的状态。
- **支持MVCC（多版本并发控制）**：当一个事务修改了某行记录但尚未提交时，其他事务发起快照读（`SELECT`），InnoDB 会借助 Undo Log 读取该行在事务修改前的历史版本，实现读写互不阻塞的并发访问。



### 工作流程

- `insert`：把这条记录的主键值记下来，回滚时执行 `DELETE`
- `update`：把要被更新的列的旧值记下来，回滚时执行相反的 `UPDATE` 将数据改回
- `delete`：把这条记录的内容都记下来，回滚时执行 `INSERT` 将其恢复



**Undo Log 的类型**

- **Insert Undo Log**：记录 `INSERT` 操作。由于新插入的行在事务提交前对其他事务不可见，提交后其他事务无需读取历史版本，因此该日志在**事务提交后立即释放/删除**。
- **Update Undo Log**：记录 `UPDATE` 和 `DELETE` 操作。不仅回滚需要，MVCC 快照读也依赖该链条，因此**事务提交后不能立刻删除**，需交由后台线程统一清理。



### 生命周期与 Purge 机制

1. **写入**：事务对数据页修改前，先在 Undo 页面中写入旧值。
2. **提交**：事务提交后，Insert Undo Log 立即被移除；Update Undo Log 被放入 Undo Log 历史链表（History List）。
3. **Purge 清理**：后台 **Purge 线程**会持续检查系统中所有活跃事务的 `ReadView`。当确认某条 Undo Log 记录不再被任何活跃事务的快照读依赖时，Purge 线程才会将其彻底清理并回收磁盘空间。



为了更清晰地理解，可以将 undo log 与常常一同提及的 redo log 进行对比：

| 特性         | Undo Log (回滚日志)                  | Redo Log (重做日志)                  |
| :----------- | :----------------------------------- | :----------------------------------- |
| **主要目的** | 保障事务**原子性 (Atomicity)**       | 保障事务**持久性 (Durability)**      |
| **记录内容** | **逻辑日志**，记录“如何撤销”的逆操作 | **物理日志**，记录数据页的“物理修改” |
| **主要作用** | 事务**回滚**、**MVCC** 一致性读      | **崩溃恢复** (Crash Recovery)        |

>redo log 记录了此次事务「修改后」的数据状态，记录的是更新之后的值，主要⽤于事务崩溃恢复，保证事务的持久性。
>
>undo log 记录了此次事务「修改前」的数据状态，记录的是更新之前的值，主要⽤于事务回滚，保证事务的原⼦性。

# 二. Buffer pool

Buffer Pool（缓冲池）是 MySQL InnoDB 存储引擎在内存中开辟的一块核心内存区域，旨在**通过内存缓存磁盘数据页，减少磁盘随机 I/O**，以此大幅提升数据库的读写吞吐量。

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822103832352.png" alt="image-20260822103832352" style="zoom:67%;" />



### 缓存的核心内容

在mysql启动的时候，InnoDB会为Buffer Pool申请一片连续的内存空间（默认配置下 Buffer Poll 只有128MB，可以通过调整innodb_buffer_pool_size参数来调整Buffer Pool的大小，一般建议设置成可用物理内存的60-80%），然后按照默认的16KB划分出一个个的页，Buffer Pool中的页就叫做缓存页。此时这些缓存页都是空闲的，之后随着程序的运行，才会有磁盘上的页被缓存到Buffer Pool中

Buffer Pool 以 **页（Page，默认 16KB）** 为基本单位进行管理，其内部主要包含：

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822103942205.png" alt="image-20260822103942205" style="zoom:50%;" />

- **数据页（Data Pages）与索引页（Index Pages）**：最主要的缓存数据。
- **Undo 页（Undo Pages）**：事务回滚与 MVCC 所需的历史版本数据。
- **自适应哈希索引（Adaptive Hash Index, AHI）**：InnoDB 对热点索引自动构建的内存哈希表。
- **Change Buffer（写缓冲）**：缓存针对非唯一二级索引的增删改操作，延后合并。
- **锁信息（Lock Info）与数据字典信息**。

为了更好的管理这些在Buffer Pool中的缓存页，InnoDB为每一个缓存页都创建了一个控制块，控制块的信息包括：缓存页的表空间，页号，缓存页地址，链表节点，控制块也是占用内存空间的，它是放在Buffer Pool的最前面，然后才是缓存页

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822163530625.png" alt="image-20260822163530625" style="zoom:67%;" />

在控制块和缓存页之间的部分就称之为碎片空间



**undo页面记录的是什么**

>开启事务后，InnoDB 层更新记录前，⾸先要记录相应的 undo log，如果是更新操作，需要把被更新的列的旧值记下来，也就是要⽣成⼀条 undo log，undo log 会写⼊ Buffer Pool 中的 Undo 页⾯。

**查询⼀条记录，就只需要缓冲⼀条记录吗？**

>当我们查询⼀条记录时，InnoDB 是会把整个页的数据加载到 Buffer Pool 中，将页加载到 Buffer Pool 后，再通过页⾥的「页⽬录」去定位到某条具体的记录。



### 工作流程

- 当读取数据时，如果数据存在于 Buffer Pool 中，客户端就会直接读取 Buffer Pool 中的数据，否则再去磁盘中读取。
- 当修改数据时，如果数据存在于  Buffer Pool  中，那直接修改 Buffer Pool 中数据所在的页，然后将其页设置为脏页（该页的内存数据和磁盘上的数据已经不⼀致），为了减少磁盘I/O，不会⽴即将脏页写⼊磁盘，后续由后台线程选择⼀个合适的时机将脏页写⼊到磁盘。



### 内部架构

为了高效追踪每个缓存页的状态，InnoDB 为每个缓存页分配了一个**控制块（Control Block）**，并通过三条双向链表管理：

- **Free List（空闲链表）**：记录所有尚未装载数据的空闲页。当需要从磁盘读取新页到内存时，直接从 Free List 摘取空闲页分配。
- **Flush List（脏页链表）**：记录内存中已被修改但尚未刷回磁盘的**脏页（Dirty Pages）**。脏页按照修改先后顺序（根据 LSN）串联，后台线程据此顺序异步刷盘。
- **LRU List（淘汰链表）**：管理所有已加载的缓存页，决定内存不足时优先淘汰哪些冷数据。



**管理空闲页**

为了能够快速找到空闲的缓存页，使⽤链表结构，将空闲缓存页的「控制块」作为链表的节点，这个链表称为**Free** 链表（空闲链表）。

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822164207822.png" alt="image-20260822164207822" style="zoom:67%;" />

Free 链表上除了有控制块，还有⼀个头节点，该头节点包含链表的头节点地址，尾节点地址，以及当前链表中节点的数量等信息。

Free 链表节点是⼀个⼀个的控制块，⽽每个控制块包含着对应缓存页的地址，所以相当于 Free 链表节点都对应⼀个空闲的缓存页。

有了 Free 链表后，每当需要从磁盘中加载⼀个页到 Buffer Pool 中时，就从 Free链表中取⼀个空闲的缓存页，并且把该缓存页对应的控制块的信息填上，然后把该缓存页对应的控制块从 Free 链表中移除。



**管理脏页**

设计 Buffer Pool 除了能提⾼读性能，还能提⾼写性能，也就是更新数据的时候，不需要每次都要写⼊磁盘，⽽是将 Buffer Pool 对应的缓存页标记为脏页，然后再由后台线程将脏页写⼊到磁盘。

那为了能快速知道哪些缓存页是脏的，于是就设计出**Flush** 链表，它跟 Free 链表类似的，链表的节点也是控制块，区别在于 Flush 链表的元素都是脏页。

有了 Flush 链表后，后台线程就可以遍历 Flush 链表，将脏页写⼊到磁盘。

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822164555634.png" alt="image-20260822164555634" style="zoom:67%;" />



**提高缓存命中率**

Buffer Pool  的⼤⼩是有限的，对于⼀些频繁访问的数据我们希望可以⼀直留在 Buffer Pool 中，⽽⼀些很少访问的数据希望可以在某些时机可以淘汰掉，从⽽保证 Buffer Pool  不会因为满了⽽导致⽆法再缓存新的数据，同时还能保证常⽤数据留在 Buffer Pool 中。

**改良版 LRU 算法：防止缓存污染**

传统的朴素 LRU 算法在面对**全表扫描**或预读（Read-Ahead）时，会瞬间把真正的高频热点数据冲刷出内存。InnoDB 采用了分段式改良 LRU：

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822164850931.png" alt="image-20260822164850931" style="zoom:80%;" />

- **分区结构**：将 LRU 链表按比例分为 **Young 区（热数据区，约 63%）** 和 **Old 区（冷数据区，约 37%）**。
- **插入位置**：新从磁盘读取的数据页默认插入 **Old 区的头部**（即 Midpoint 点），而不是整个链表的最前端。
- **晋升机制（`innodb_old_blocks_time`）**：(用来解决Buffer Pool污染)
  - Old 区的数据页被访问时，不会立刻移入 Young 区。
  - 只有当该页在 Old 区的停留时间超过指定阈值（默认 **1000ms**）后再次被访问，才会被移入 Young 区头部。
  - 全表扫描时，同一个数据页在毫秒内被连续读取多次后便不再访问，因此会自然在 Old 区随链表推移被淘汰，避免冲垮 Young 区热点。



### 刷入磁盘的时机

引⼊了 Buffer Pool  后，当修改数据时，⾸先是修改  Buffer Pool  中数据所在的页，然后将其页设置为脏页，但是磁盘中还是原数据。

因此，脏页需要被刷⼊磁盘，保证缓存和磁盘数据⼀致，但是若每次修改数据都刷⼊磁盘，则性能会很差，因此⼀般都会在⼀定时机进⾏批量刷盘。

如果在脏页还没有来得及刷⼊到磁盘时，MySQL 宕机了，不就丢失数据了吗？

InnoDB 的更新操作采⽤的是 Write Ahead Log 策略，即先写⽇志，再写⼊磁盘，通过 redo log ⽇志让 MySQL 拥有了崩溃恢复能⼒。

下⾯⼏种情况会触发脏页的刷新：

- 当 redo log ⽇志满了的情况下，会主动触发脏页刷新到磁盘；
- Buffer Pool 空间不⾜时，需要将⼀部分数据页淘汰掉，如果淘汰的是脏页，需要先将脏页同步到磁盘；
- MySQL 认为空闲时，后台线程会定期将适量的脏页刷⼊到磁盘；
- MySQL 正常关闭之前，会把所有的脏页刷⼊到磁盘；

在我们开启了慢 SQL 监控后，如果你发现「偶尔」会出现⼀些⽤时稍长的 **SQL**，这可能是因为脏页在刷新到磁盘时可能会给数据库带来性能开销，导致数据库操作抖动。

如果间断出现这种现象，就需要调⼤ Buffer Pool 空间或 redo log ⽇志的⼤⼩。



### 关键配置参数

| 参数                               | 说明                                                         | 建议值                                                       |
| :--------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **`innodb_buffer_pool_size`**      | **最重要的参数**，Buffer Pool 的总大小。                     | 通常设置为服务器**物理内存的 60% ~ 80%**。                   |
| **`innodb_buffer_pool_instances`** | Buffer Pool 的实例个数。多实例可减少高并发下的锁竞争。       | 当 `size > 1GB` 时，建议设置为 1~8 个（如设置为 4 或 8）。   |
| **`innodb_old_blocks_pct`**        | Old 区占 LRU List 的比例。                                   | 默认 37。若经常有大表扫描，可适当调大（如 50），以延长缓存失效保护。 |
| **`innodb_old_blocks_time`**       | 数据页在 Old 区必须等待多少毫秒后，再次被访问才能进入 Young 区。 | 默认 1000（1秒）。对于 OLTP 业务，保持默认即可。             |



###  协同

它们在数据库中是这样配合的：

1. **写操作**：修改 **Buffer Pool** 中的数据页（产生脏页）→ 同时追加写入 **Redo Log**（保证崩溃恢复）。
2. **回滚/MVCC**：修改数据前，先在 **Buffer Pool** 中生成 **Undo Log** 页（它也缓存于 Buffer Pool 中），记录旧值。
3. **崩溃恢复**：MySQL 重启后，利用 **Redo Log** 重做所有已提交事务的修改（将 Buffer Pool 中的脏页恢复），再利用 **Undo Log** 回滚未提交事务。

**一句话总结**：**Buffer Pool 是 InnoDB 的性能心脏**，它负责在内存中完成几乎所有数据读写操作，而 Undo Log 和 Redo Log 则是它的守护者，确保内存中的数据在意外发生时依然安全、可撤回。绝大多数 MySQL 性能优化，归根结底都是对 Buffer Pool 命中率（通常应 > 95%）的优化。



# 三. redo log

**Redo Log（重做日志）是 MySQL InnoDB 存储引擎特有的物理日志**，记录的是“在某个数据页上做了什么物理修改”，核心职责是保证事务的持久性（Durability）并实现 **崩溃恢复（Crash Recovery）**。

### WAL

**WAL（预写式日志）** 技术指的是， **MySQL** 的写操作并不是⽴刻写到磁盘上，⽽是先写⽇志，然后在合适的时间再写到磁盘上。

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822110856731.png" alt="image-20260822110856731" style="zoom:67%;" />

直接将内存中修改过的脏页随机写入磁盘（Random I/O）性能极低。InnoDB 采用 **WAL（Write-Ahead Logging）** 机制优化写入性能：

- 事务修改数据时，先更新内存中的 **Buffer Pool**（产生脏页）。
- 事务提交时，只需将变更以顺序 I/O（Sequential I/O）的方式追加写入磁盘上的 Redo Log。
- 只要 Redo Log 成功持久化，事务即视为提交成功。内存中的脏页由后台线程异步刷新（Flush）到磁盘数据文件。



### redo

redo log 是物理⽇志，记录了某个数据页做了什么修改，⽐如对 **XXX** 表空间中的 **YYY** 数据页 **ZZZ** 偏移量的地⽅做了**AAA** 更新，每当执⾏⼀个事务就会产⽣这样的⼀条或者多条物理⽇志。

在事务提交时，只要先将 redo log 持久化到磁盘即可，可以不需要等到将缓存在  Buffer Pool  ⾥的脏页数据持久化到磁盘。

当系统崩溃时，虽然脏页数据没有持久化，但是 redo log 已经持久化，接着 MySQL 重启后，可以根据 redo log 的内容，将所有数据恢复到最新的状态。



**被修改的undo log页面，需要记录对应的redo log吗**

>开启事务后，InnoDB 层更新记录前，⾸先要记录相应的 undo log，如果是更新操作，需要把被更新的列的旧值记下来，也就是要⽣成⼀条 undo log，undo log 会写⼊ Buffer Pool 中的 Undo 页⾯。
>
>不过，在内存修改该 **Undo** 页⾯后，也是需要记录对应的 **redo log**，因为**undo log**也要实现持久性的保护。



事务提交之前发⽣了崩溃（这⾥的崩溃不是宕机崩溃，⽽是事务执⾏错误，mysql 还是正常运⾏的。如果是宕机崩溃的话，其实就不需要通过 undo log 回滚了，因为事务没有提交，事务的数据并不会持久化，还是在内存中，宕机崩溃了数据就丢失了，反正事务都没有提交成功，所以数据本⾝就⽆意义的，丢失了就丢失了），重启后会通过undo log 回滚事务。

事务提交之后发⽣了崩溃（这⾥的崩溃是宕机崩溃），重启后会通过 redo log 恢复事务，如下图：

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822170426023.png" alt="image-20260822170426023" style="zoom:67%;" />

所以有了 redo log，再通过 WAL 技术，InnoDB 就可以保证即使数据库发⽣异常重启，之前已提交的记录都不会丢失，这个能⼒称为**crash-safe**（崩溃恢复）。可以看出来，**redo log** 保证了事务四⼤特性中的持久性。



#### 作用

Redo Log 的核心设计目标，就是解决磁盘随机写（修改数据页）太慢的问题。

1. **保障持久性 (Durability)**：事务提交时，数据可能还在 Buffer Pool（内存）里没来得及刷盘。万一崩溃，Redo Log 就是唯一的救命稻草，它能重放所有已提交事务的修改，确保数据不丢失。
2. **提升写入性能 (WAL 技术)**：这是最关键的设计哲学。修改数据时，InnoDB **不再直接去磁盘修改数据页（随机I/O）**，而是将修改操作以**追加顺序写**的方式写入 Redo Log 文件。顺序写的速度比随机写快几个数量级，这就是 InnoDB 写入性能高的根本原因。



#### 格式

Redo Log 是一种 **物理逻辑 (Physical-Logical) 日志**，这比纯粹的物理日志或逻辑日志更高效。

- **物理层面**：它记录的是对哪个**表空间**、哪个**数据页号**、哪个**偏移量**进行了修改。
- **逻辑层面**：它记录的是修改的**具体操作**，比如“在这个页的偏移量 X 处，将值从 A 改为 B”，而不是整个页的完整镜像。

这种设计的优势在于：**它足够精简，用于恢复时重做速度极快；同时它又足够具体，能精确应用到物理页上**。



#### 刷盘策略

Redo Log 在写入磁盘前会暂存于内存中的 `Redo Log Buffer`。该参数控制何时将 Buffer 中的日志刷入磁盘：

![image-20260822171532991](/covers/java--mysql-2--6-tkdfmb/image-20260822171532991.png)

- **`0`**：事务提交时不主动刷盘；由后台主线程每秒将 Redo Log Buffer 写入操作系统缓存（OS Page Cache）并执行 `fsync` 落盘（性能最高，MySQL 进程崩溃最多丢失 1 秒数据）。
- **`1`（默认/推荐）**：每次事务提交都必须将 Redo Log Buffer 写入 OS Cache 并立即执行 `fsync` 刷盘（保证强持久性，安全性最高，但 I/O 成本最高）。
- **`2`**：每次事务提交只将 Redo Log Buffer 写入 OS Cache，后台主线程每秒执行一次 `fsync` 刷盘（MySQL 进程异常退出不丢数据，仅宿主机断电/操作系统宕机时丢失最多 1 秒数据）。

数据安全性：参数 1 > 参数 2 > 参数 0 

写⼊性能：参数 0 > 参数 2> 参数 1



**如何选择**

- 在⼀些对数据安全性要求⽐较⾼的场景中，显然innodb_flush_log_at_trx_commit参数需要设置为 1。
- 在⼀些可以容忍数据库崩溃时丢失 1s 数据的场景中，我们可以将该值设置为 0，这样可以明显地减少⽇志同步到磁盘的 I/O 操作。
- 安全性和性能折中的⽅案就是参数 2，虽然参数 2 没有参数 0 的性能⾼，但是数据安全性⽅⾯⽐参数 0 强，因为参数 2 只要操作系统不宕机，即使数据库崩溃了，也不会丢失数据，同时性能⽅便⽐参数 1 ⾼。



#### 循环写入与 Checkpoint 机制

Redo Log 在磁盘上以 **一组固定大小的文件** 存在（通常是 `ib_logfile0`, `ib_logfile1` 等），并采用 **循环写入** 的方式。

InnoDB 通过两个全局指针来管理这个循环缓冲区：

- **`write pos` (写入点)**：当前 Redo Log 写入的位置。随着事务不断提交，`write pos` 会不断向后推进（追加写入）。
- **`checkpoint` (检查点)**：当前可以覆盖（即已刷盘）的位置。表示 `checkpoint` 之前的所有数据页修改，都已经被安全地写入了磁盘上的数据文件。

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260822172116352.png" alt="image-20260822172116352" style="zoom:67%;" />

- write pos 和 checkpoint 的移动都是顺时针⽅向；
- write pos ～ checkpoint 之间的部分（图中的红⾊部分），⽤来记录新的更新操作；
- check point ～ write pos 之间的部分（图中蓝⾊部分）：待落盘的脏数据页记录；

 **生命周期流程**

1. **写入**：事务修改数据时，先写入 Redo Log Buffer（内存），提交时通过 `fsync` 强制刷到磁盘文件（`write pos` 推进）。
2. **推进**：后台线程异步将 Buffer Pool 中的脏页刷回磁盘。每刷完一个页，就更新 `checkpoint` 的进度。
3. **覆盖**：当 `write pos` 追上了 `checkpoint`，说明 Redo Log 文件写满了。此时 InnoDB 会**强制触发脏页刷盘**（这就是“刷脏”），推动 `checkpoint` 向前移动，从而腾出空间，让 `write pos` 可以继续循环写入覆盖旧日志。



#### 崩溃恢复

这是 Redo Log 最关键的表演时刻。MySQL 重启后，恢复过程分为三步：

1. **分析 (Analysis)**：从最后一个 Checkpoint 开始，扫描 Redo Log，找到所有未完成的事务（包括已提交但未刷脏的，和未提交的）。
2. **重做 (Redo / 前滚)**：**这是 Redo Log 的职责**。将所有已提交事务的修改记录，全部应用到 Buffer Pool 或磁盘数据页上。此时，所有已提交事务的修改都被恢复。
3. **回滚 (Undo / 后滚)**：这一步虽然叫 Undo，但它是为了完成 Redo 流程。InnoDB 会利用 Undo Log 将那些在崩溃时**未提交**的事务的修改**回滚掉**，保证原子性。

**核心原则**：**Redo 先于 Undo**。必须先用 Redo 把数据库“物理地”恢复到崩溃前的统一状态，再通过 Undo 把未完成的事务“逻辑地”撤销掉。



# 四. binlog

Binlog（Binary Log，二进制日志）是 MySQL Server 层维护的逻辑日志，以二进制格式记录所有引起或可能引起数据库数据变更的 DDL 与 DML 语句（不记录 `SELECT`、`SHOW` 等只读操作），是实现主从复制、数据恢复以及变更数据捕获（CDC）的核心底座。



### 作用

1. **主从复制 (Replication)**：这是 Binlog 最广为人知的作用。主库将数据变更写入 Binlog，从库通过 `I/O线程` 拉取并写入本地 `Relay Log`，再通过 `SQL线程` 重放，从而实现数据异地同步，构建读写分离和灾备架构。
2. **时间点恢复 (Point-in-Time Recovery, PITR)**：当数据被误删或误改时，仅靠全量备份无法恢复到出问题前的瞬间。结合全量备份和 Binlog，你可以“回放”从备份时间点到误操作前的所有变更，将数据恢复至任意一秒。
3. **数据审计与异构消费**：Binlog 是结构化的变更流，可以被 Canal、Debezium 等中间件消费，实时同步到 Kafka、Elasticsearch 或数据仓库，实现异构数据同步和离线分析。



### 日志格式

这是 Binlog 最核心的配置，直接决定日志的大小、主从一致性以及性能。

| 格式                                  | 记录内容                                                     | 优点                                                      | 致命缺点 / 风险                                              |
| :------------------------------------ | :----------------------------------------------------------- | :-------------------------------------------------------- | :----------------------------------------------------------- |
| **STATEMENT** (基于SQL语句)           | 记录执行的 SQL 语句原文（如 `UPDATE t SET a=a+1`）。         | 日志量极小，网络传输快，IO压力小。                        | **极易导致主从数据不一致**。如包含 `NOW()`、`UUID()` 或依赖索引顺序的 `LIMIT`，在从库重放时会得到不同的结果。 |
| **ROW** (基于行，**MySQL 5.7+ 默认**) | 记录**每一行数据**被修改前后的完整值（`before_image` 和 `after_image`）。 | **绝对安全**，能保证主从数据严格一致。支持所有 SQL 语句。 | 日志量**极大**。一条 `UPDATE` 更新 10万行，就会产生 10万条 Binlog 事件，可能导致磁盘暴涨和网络延迟。 |
| **MIXED** (混合模式)                  | 自动判断：SQL 语句“安全”就用 STATEMENT，包含不安全函数或 `UPDATE...LIMIT` 时自动切换为 ROW。 | 折中了日志量和安全性。                                    | 恢复和复制时仍需小心，且判断逻辑有极少数边界场景会出错。     |

> **生产环境铁律**：除非磁盘空间极度紧张，否则 **强制使用 `ROW` 格式**。并且建议开启 `binlog_row_image = FULL`（记录完整行），虽然空间占用多，但为数据恢复和消费提供了最大的灵活性。



### 写入流程与刷盘机制

每个事务执行期间，日志先写入线程独享的 **binlog cache**，事务提交时再集中写入全局 Binlog 文件中。

```
[事务开始] ──> 执行 DML ──> 写入线程独立的 binlog cache (内存)
                                │
[事务提交] ──> 调用 write() ────┘
                │
                ▼
         Page Cache (操作系统内核缓存)
                │
                ▼ 调用 fsync()
         Binlog 物理磁盘文件
```

1. **binlog cache**：由参数 `binlog_cache_size` 控制单个线程分配的内存大小。若事务产生的数据超过该值，会暂存到临时磁盘文件。
2. **刷盘控制（sync_binlog）**：
   - **`sync_binlog = 0`**：每次事务提交只调用系统的 `write()` 将缓存写入操作系统 Page Cache，由 OS 自行决定何时调用 `fsync()` 刷盘。性能最高，但 OS 宕机或掉电会丢失未落盘日志。
   - **`sync_binlog = 1`（生产推荐）**：每次事务提交都必须执行 `fsync()` 将 Page Cache 强刷到物理磁盘，确保即使服务器掉电也绝不丢失已提交的 Binlog。
   - **`sync_binlog = N (N > 1)`**：累计提交 N 个事务后执行一次 `fsync()`，折中吞吐量与数据安全性。



### 两阶段提交 (2PC)

这是保障 **Binlog 和 Redo Log 数据逻辑一致** 的生死协议。

**为什么必须有它？** 因为 MySQL 先用 Redo Log 保证崩溃恢复，再用 Binlog 保证主从复制，如果两者不一致，主库崩溃重启后和从库的数据就会发生“脑裂”。

**核心流程（内部 XA 事务）：**

1. **Prepare 阶段（Redo Log 落盘）**：
   - 事务修改数据，Redo Log 写入磁盘。
   - Redo Log 的事务状态标记为 **`PREPARE`**（准备提交）。
2. **Write & Sync Binlog 阶段（Binlog 落盘）**：
   - 将事务的变更内容写入 Binlog，并调用 `sync_binlog=1` 强制落盘。
3. **Commit 阶段（Redo Log 提交）**：
   - Binlog 写入成功后，Redo Log 的状态从 `PREPARE` 改为 **`COMMIT`**，事务正式提交成功。

<img src="/covers/java--mysql-2--6-tkdfmb/image-20260823105440413.png" alt="image-20260823105440413" style="zoom:67%;" />

**崩溃恢复的“裁判逻辑”**：
假设主库在第2步和第3步之间突然宕机，此时 Redo Log 状态是 `PREPARE`，但 Binlog 可能已写或未写。重启恢复时，InnoDB 会做如下“绝对理性”的判断：

- 检查处于 `PREPARE` 状态的事务。
- **去 Binlog 中查找该事务是否完整存在**：
  - 若 **Binlog 中有** 该事务记录 → **提交（Commit）**该事务（因为从库可能已通过 Binlog 同步了数据，主库必须补上）。
  - 若 **Binlog 中没有** 该事务记录 → **回滚（Rollback）**该事务（因为还没同步给从库，主库不能有这笔数据）。

**这就是 2PC 的精髓**：它以 Binlog 是否成功写入为最终“裁判员”，保证主库崩溃恢复后的数据和从库通过 Binlog 复制的数据**完全一致，绝不产生分歧**。



**问题**

- 磁盘 **I/O** 次数⾼：对于“双1”配置，每个事务提交都会进⾏两次 fsync（刷盘），⼀次是 redo log 刷盘，另⼀次是 binlog 刷盘。
- 锁竞争激烈：两阶段提交虽然能够保证「单事务」两个⽇志的内容⼀致，但在「多事务」的情况下，却不能保证两者的提交顺序⼀致，因此，在两阶段提交的流程基础上，还需要加⼀个锁来保证提交的原⼦性，从⽽保证多事务的情况下，两个⽇志的提交顺序⼀致。
