# Redis分片集群

Redis 分片集群（Redis Cluster）是 Redis 官方提供的一种分布式解决方案。它的核心思想是**将数据自动拆分（Sharding）到多个不同的 Redis 节点上**，从而突破单台物理机的内存和性能极限。

在引入分片集群之前，传统的“单机”或“主从+哨兵”模式主要面临以下瓶颈：

1. **单机内存受限**：一台服务器的内存是有限的，如果业务需要缓存数百 GB 甚至 TB 级别的数据，单台机器根本存不下。
2. **并发写性能瓶颈**：“主从架构”虽然能通过增加从节点来分担“读”请求，但所有的“写”操作依然只能由唯一的 Master 承担，无法应对百万级以上的并发写场景。
3. **网络带宽瓶颈**：极端高并发下，单台物理机的网卡吞吐量也会成为天花板。

分片集群通过**水平扩容**完美解决了这些问题：把数据和访问压力分散到多台服务器上。



## 1. 核心工作原理

Redis 分片集群的设计非常精巧，主要由以下几个核心机制构成：

### 1. 哈希槽机制 (Hash Slots)

这是 Redis 集群最核心的数据分布策略。Redis 并没有使用传统的一致性哈希，而是引入了**哈希槽 (Hash Slot)** 的概念。

- Redis 集群中内置了 **16384** 个哈希槽（从 0 到 16383）。
- 集群启动时，这 16384 个槽会被均匀（或根据你的配置）分配给集群中的各个 Master 节点。
- 当你要存入或读取一个键值对时，Redis 会对 Key 进行 `CRC16` 算法计算，然后再对 16384 取模，得到的值就是这个 Key 的“槽位”：`Slot = CRC16(key) % 16384`。
- 最终，这个 Key 就会被存储到负责该特定槽位的 Master 节点上。

> **举个例子**：假设集群有 3 个 Master（节点 A、B、C）。
>
> - 节点 A 负责槽位：0 ~ 5460
>
> - 节点 B 负责槽位：5461 ~ 10922
>
> - 节点 C 负责槽位：10923 ~ 16383
>
>   如果一个名为 `user:100` 的 Key 计算出的槽位是 6000，那么它就会被保存到节点 B 上。

### 2. 去中心化通信 (Gossip 协议)

许多分布式系统需要一个中心化的协调节点（比如 ZooKeeper 或独立代理层）来维护元数据，但 Redis Cluster 是**无中心架构**的。

集群中的各个节点通过 **Gossip 协议** 互相通信，就像在玩“传话游戏”一样，不断交换彼此的心跳、节点状态以及哈希槽的映射信息。任何一个节点都掌握着整个集群完整的路由视图。

### 3. 客户端路由与重定向 (MOVED 机制)

客户端在访问集群时，可以连接集群中的**任意一个节点**。

- 如果你要操作的 Key 正好属于当前连接的节点，该节点就会直接处理并返回结果。
- 如果该 Key 不属于当前节点，节点会返回一个 `MOVED` 错误，告诉客户端：“这个 Key 归节点 B 管，它的 IP 和端口在这里”。
- 客户端收到 `MOVED` 响应后，会自动重新连接到目标节点发起请求。

*(注：在实际开发中，现代的“智能客户端”如 JedisCluster 或 Lettuce 会在本地缓存一份完整的【槽位 -> 节点】映射表，直接精准命中目标节点，避免了频繁的重定向开销。)*

### 4. 高可用与故障转移 (Failover)

为了保证数据不丢失和服务不中断，集群中的每个分片（Master）通常会配置一个或多个从节点（Slave）。

- **数据同步**：Slave 会实时从 Master 复制数据。
- **故障检测**：节点之间相互 Ping，如果集群中大多数 Master 节点发现某个 Master 失去联系，就会将其判定为客观下线。
- **自动接管**：集群会自动从该下线 Master 的 Slave 中选举出一个新的 Master，接管它负责的哈希槽，整个过程无需人工干预。

## 优缺点总结

| **维度** | **表现**                                                     |
| -------- | ------------------------------------------------------------ |
| **优点** | 突破单机内存和网络限制；支持海量并发吞吐；无中心单点故障风险；支持在线动态扩容/缩容（迁移槽位无需停机）。 |
| **缺点** | 架构复杂，部署和运维成本变高；**受限于槽位机制，默认不支持跨节点的多键操作**（如 `MSET` 跨槽位会报错）；不支持跨节点的事务。 |

































## 4.1.搭建分片集群

主从和哨兵可以解决高可用、高并发读的问题。但是依然有两个问题没有解决：

- 海量数据存储问题

- 高并发写的问题

使用分片集群可以解决上述问题，如图:

![image-20210725155747294](/covers/java--redis-2--3-3k2g20/image-20210725155747294.webp)



分片集群特征：

- 集群中有多个master，每个master保存不同数据

- 每个master都可以有多个slave节点

- master之间通过ping监测彼此健康状态

- 客户端请求可以访问集群任意节点，最终都会被转发到正确节点

## 4.2.散列插槽

### 4.2.1.插槽原理

Redis会把每一个master节点映射到0~16383共16384个插槽（hash slot）上，查看集群信息时就能看到：

![image-20210725155820320](/covers/java--redis-2--3-3k2g20/image-20210725155820320.webp)



数据key不是与节点绑定，而是与插槽绑定。redis会根据key的有效部分计算插槽值，分两种情况：

- key中包含"{}"，且“{}”中至少包含1个字符，“{}”中的部分是有效部分
- key中不包含“{}”，整个key都是有效部分





例如：key是num，那么就根据num计算，如果是{itcast}num，则根据itcast计算。计算方式是利用CRC16算法得到一个hash值，然后对16384取余，得到的结果就是slot值。

![image-20210725155850200](/covers/java--redis-2--3-3k2g20/image-20210725155850200.webp) 

如图，在7001这个节点执行set a 1时，对a做hash运算，对16384取余，得到的结果是15495，因此要存储到103节点。

到了7003后，执行`get num`时，对num做hash运算，对16384取余，得到的结果是2765，因此需要切换到7001节点



### 4.2.1.小结

Redis如何判断某个key应该在哪个实例？

- 将16384个插槽分配到不同的实例
- 根据key的有效部分计算哈希值，对16384取余
- 余数作为插槽，寻找插槽所在实例即可

如何将同一类数据固定的保存在同一个Redis实例？

- 这一类数据使用相同的有效部分，例如key都以{typeId}为前缀

## 4.5.RedisTemplate访问分片集群

RedisTemplate底层同样基于lettuce实现了分片集群的支持，而使用的步骤与哨兵模式基本一致：

1）引入redis的starter依赖

2）配置分片集群地址

3）配置读写分离

与哨兵模式相比，其中只有分片集群的配置方式略有差异，如下：

```yaml
spring:
  redis:
    cluster:
      nodes:
        - 192.168.150.101:7001
        - 192.168.150.101:7002
        - 192.168.150.101:7003
        - 192.168.150.101:8001
        - 192.168.150.101:8002
        - 192.168.150.101:8003
```
