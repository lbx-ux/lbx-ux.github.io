# Redis持久化

Redis 作为一款基于**内存**的数据库，其最大的优势是极高的读写性能。但这也带来了一个致命问题：一旦服务器宕机或断电，内存中的数据就会全部丢失。

为了解决这个问题，Redis 提供了持久化机制，将内存中的数据落盘到硬盘上。Redis 主要有两大持久化武器：**RDB (Redis DataBase)** 和 **AOF (Append Only File)**，并在较新的版本中引入了**混合持久化**。



## 1. RDB持久

RDB 是一种**快照持久化**（Snapshotting）。它会在指定的时间间隔内，将 Redis 在内存中的全量数据集“拍”一张快照，并序列化保存到磁盘上，生成一个非常紧凑的二进制文件（默认名为 `dump.rdb`）。当 Redis 重启时，可以直接加载这个二进制文件来快速恢复数据。



### 1. 触发机制

RDB 快照的生成可以由手动触发或自动触发完成。

#### 1. 手动触发

- **`save` 命令：** 在主线程中执行，会**阻塞** Redis 服务器，直到 RDB 文件创建完毕。在此期间，Redis 无法处理任何客户端的请求。
- **`bgsave` 命令：** 在后台异步进行快照操作，生成快照的同时还可以响应客户端请求。

#### 2. 自动触发

在 `redis.conf` 配置文件中，可以通过 `save m n` 指令进行自动触发配置。意思是：**在 m 秒内，如果至少发生了 n 次修改**，就会自动触发 `bgsave`。

- `save 900 1` （15分钟内至少有1个 key 被修改）
- `save 300 10` （5分钟内至少有10个 key 被修改）
- `save 60 10000` （1分钟内至少有10000个 key 被修改）

除此之外，执行 `flushall`（清空数据）或主从同步时的全量复制阶段，Redis 也会自动触发 RDB。



### 2. 底层核心原理

执行 `bgsave` 时，Redis 既要保证主线程不被阻塞，又要保证在生成快照的过程中，新写入的数据不会破坏快照的一致性。这里巧妙地利用了操作系统的底层机制。

**执行流程：**

1. **Fork 子进程：** 主线程调用操作系统的 `fork()` 函数，创建一个子进程。这个 `fork` 动作本身会阻塞主线程一小瞬间，但时间极短。
2. **生成快照：** 子进程开始将内存中的数据写入一个临时的 RDB 文件中。
3. **替换旧文件：** 子进程写完后，用临时文件替换掉旧的 `dump.rdb` 文件，子进程退出。



**Copy-On-Write (写时复制) 机制：**

这是 RDB 底层最核心的技术点。

1. **内存共享（fork时刻）**：`fork()` 发生时，子进程并不会立刻复制父进程的所有物理内存，而是**共享父进程的内存页**。此时，父子进程指向同一块物理内存，内存并没有瞬间翻倍。
2. **和平共处（纯读阶段）**：如果在这期间，所有客户端只是做读操作，那大家相安无事，一起读这块内存。
3. **写时复制**：如果在子进程写 RDB 期间，主线程接收到了写操作（修改某个数据），操作系统才会将该数据所在的内存页复制一份副本出来，让主线程在这个副本上进行修改。

   - 主线程修改的这个“副本”，在 RDB 执行完成后，就顺理成章地变成了 Redis 主线程继续使用的“正式数据”。它不需要进行任何额外的“合并”或“回写”操作。
     
- 而随着子进程使命结束退出，曾经的“旧原配”因为无人引用，被操作系统默默当作垃圾回收掉了。


4. **快照保持**：子进程依然读取的是原来的那份数据。这就保证了子进程“拍”下的快照永远是 `fork` 发生那一刻的静态数据。



#### 细节：

**只是按需复制被修改数据所在的那个具体的“内存页”，绝对不是把所有物理数据都复制一份。**

**1. `fork()` 发生的瞬间：只复制“目录”，不复制“内容”**

当 Redis 主线程调用 `fork()` 创建子进程来生成 RDB 快照时，操作系统**只复制了主进程的“页表”（即虚拟内存映射表）**。 你可以把物理内存想象成一本书的正文，把页表想象成目录。`fork()` 只是复印了一份目录给子进程，父子进程的目录目前都指向同一本正文（同一块物理内存）。因此，这一瞬间是非常快的，物理内存也没有瞬间翻倍。

**2. 读操作期间：大家和平共处**

如果在这期间，Redis 只有读操作，没有写操作，那么父子进程就一直共享这块物理内存，相安无事。

**3. 写操作发生时：按“页”为单位精准复制**

操作系统的内存管理是以页（Page）为单位的（在 Linux 下，一个内存页通常是 **4KB**）。 当主线程（父进程）收到了一条写命令，想要修改某个 Key 的值时，会发生以下事情：

- **触发中断：** 操作系统发现主线程试图修改一个共享的、被标记为只读的内存页，会触发一个写保护中断。
- **复制单页：** 操作系统会在物理内存中新分配一个 4KB 的空白页，并将**旧页**里的 4KB 数据完整地拷贝到**新页**中。
- **指针重定向：** 操作系统将主线程的页表指针更新，指向这个新的 4KB 页，并允许主线程在上面进行修改。
- **子进程无感知：** 子进程的页表依然指向原来的那个旧页。这样，子进程读取到的永远是 `fork()` 发生那一刻的静态数据。



### 3. 配置

Redis内部有触发RDB的机制，可以在redis.conf文件中找到，格式如下：

```properties
# 900秒内，如果至少有1个key被修改，则执行bgsave ， 如果是save "" 则表示禁用RDB
save 900 1  
save 300 10  
save 60 10000 
```



RDB的其它配置也可以在redis.conf文件中设置：

```properties
禁用RDB
save ""

# 是否压缩 ,建议不开启，压缩也会消耗cpu，磁盘的话不值钱
rdbcompression yes

# RDB文件名称
dbfilename dump.rdb  

# 文件保存的路径目录
dir ./ 
```



### 4. 优缺点分析

**优点：**

- **体积小，恢复极快：** RDB 是经过压缩的二进制文件，非常适合做全量备份和灾难恢复。相比于 AOF（追加日志），重启时加载 RDB 文件的速度要快得多。
- **性能最大化：** 主进程只需要 `fork` 出子进程，所有的磁盘 I/O 都由子进程完成，主进程本身不执行任何底层的磁盘读写操作，保证了 Redis 的极高单线程吞吐量。

**缺点：**

- **数据丢失风险较高：** 因为 RDB 是间隔一段时间才执行一次，如果 Redis 意外宕机，你会丢失最后一次快照之后的所有修改。例如配置了5分钟保存一次，最坏情况可能丢失接近5分钟的数据。
- **Fork 时的阻塞与内存压力：** 虽然 `bgsave` 是异步的，但主线程在执行 `fork()` 的那一刻是阻塞的。如果 Redis 占用的内存非常大（比如几十GB），`fork` 耗时可能会达到百毫秒级别，导致业务卡顿。此外，如果 `bgsave` 期间发生大量的写操作，触发大量的 Copy-On-Write，会导致瞬时内存占用激增。



## 2. AOF持久化

AOF 是**以独立日志的方式，记录每次执行的写命令**（如 `SET`, `INCR` 等，读命令不记录），当 Redis 重启时，只需要重新执行一遍 AOF 文件中的所有写命令，就可以恢复数据。



### 1. AOF 的工作流程与三大刷盘策略

AOF 的执行流程并不是直接把命令写进磁盘，而是巧妙地利用了操作系统的缓冲区。完整流程分为三步：

1. **命令追加 (Append)：** Redis 每执行完一条写命令，都会把这条命令以 Redis 协议的格式追加到服务器内部的 **`aof_buf`（AOF 缓冲区）** 中。
2. **文件写入 (Write)：** 在每次事件循环结束时，Redis 会调用系统的 `write()` 函数，把 `aof_buf` 里的数据写入到操作系统的**内核缓存区 (Page Cache)** 中。
3. **文件同步 (Fsync)：** 这一步决定了数据什么时候真正从系统的 Page Cache 刷到物理磁盘上。（追加到已有文件）

Redis 在 `redis.conf` 中提供了三种刷盘策略：

- **`Always`（同步写回）：**
  - **机制：** 每次写入**内核缓冲区**后，立刻调用系统的 `fsync()` 将数据刷入磁盘。
  - **特点：** 数据最安全（最多丢失一条命令的数据），但性能最差。由于磁盘 I/O 非常慢，这会严重拖垮 Redis 的单线程性能，线上极少使用。
- **`Everysec`（每秒同步一次 - 默认策略）：**
  - **机制：** 将 `fsync()` 操作交由一个后台线程（BIO 线程）每秒执行一次。
  - **特点：** 性能与安全的完美折中。Redis 依然能保持极高的 QPS，极端宕机情况下，最多只会丢失这一秒内的数据。**这是线上最常用的配置。**
- **`No`（交由操作系统决定）：**
  - **机制：** Redis 只负责把数据写入内核的 Page Cache，至于何时刷入物理磁盘，完全由操作系统的机制决定（Linux 默认通常是 30 秒）。
  - **特点：** 性能最高，但数据安全性极低，如果机器意外宕机，可能会丢失大量数据。



### 2. AOF 重写机制

随着 Redis 运行时间的推移，AOF 文件只会追加记录，体积会越来越大。

比如你对一个 key 连续执行了 100 次 `INCR`，AOF 文件里会原封不动地记录 100 条命令。但实际上，我们只需要知道最后一次的值是多少就可以了。**AOF 重写（Rewrite）就是为了“瘦身”这个文件。**

**底层执行原理：**

1. **Fork 子进程：** 主进程调用 `fork()` 创建一个名为 `bgrewriteaof` 的子进程。和 RDB 一样，这里利用了操作系统的 **Copy-On-Write (写时复制)** 机制，子进程拥有主进程 `fork` 瞬间的内存快照。
2. **生成新 AOF 文件：** 子进程遍历此刻的内存快照数据（**Redis 根本不会去读取旧的 AOF 文件来做压缩或分析**。它完全不关心过去发生过什么，只关心**现在内存里是什么**，这就实现了重写），把每一对键值对转化为一条写命令，直接写入一个临时AOF 文件。
3. **处理重写期间的新写入（双写机制）：** 这子进程在写新文件的漫长过程中，主进程还在接收客户端的新请求，这部分数据怎么保证不丢失？
   - Redis 巧妙地引入了一个 **AOF 重写缓冲区 (`aof_rewrite_buf`)**。
   - 在子进程工作的这段时间里，主进程接收到的所有写命令，会**同时写入两个地方**：普通的 `aof_buf`（保证旧 AOF 文件的机制正常运行），以及 `aof_rewrite_buf`。
     - **写入普通的 `aof_buf` 缓冲区**：这是为了让旧的 AOF 文件继续按照原有的机制正常落盘，作为兜底方案，防止本次重写中途失败。
     - **写入专属的 `aof_rewrite_buf` 缓冲区**：这是专门为了保存从 `fork` 发生那一刻起，到子进程写完新文件期间产生的所有增量写命令。
4. **文件合并：** 当子进程把快照数据全部写完后，会发信号通知主进程。主进程会阻塞一下（此时不处理新请求），把 `aof_rewrite_buf` 里的增量命令追加到新的 AOF 文件末尾。
5. **替换：** 最后，主进程用新的 AOF 文件的替换掉旧的 AOF 文件，重写完成。



### 3. 配置

AOF默认是关闭的，需要修改redis.conf配置文件来开启AOF：

```properties
# 是否开启AOF功能，默认是no
appendonly yes
# AOF文件的名称
appendfilename "appendonly.aof"
```

AOF的命令记录的频率也可以通过redis.conf文件来配：

```properties
# 表示每执行一次写命令，立即记录到AOF文件
appendfsync always 
# 写命令执行完先放入AOF缓冲区，然后表示每隔1秒将缓冲区数据写到AOF文件，是默认方案
appendfsync everysec 
# 写命令执行完先放入AOF缓冲区，由操作系统决定何时将缓冲区内容写回磁盘
appendfsync no
```

Redis也会在触发阈值时自动去重写AOF文件。阈值也可以在redis.conf中配置：

```properties
# AOF文件比上次文件 增长超过多少百分比则触发重写
auto-aof-rewrite-percentage 100
# AOF文件体积最小多大以上才触发重写 
auto-aof-rewrite-min-size 64mb 
```





## 3. AOF 与 RDB 的对比

RDB 是定期给数据拍的一张“照片”，那么 AOF（Append Only File）就是一台一直在录像的“监控”。

| **维度**       | **RDB (快照)**                     | **AOF (日志)**                                 |
| -------------- | ---------------------------------- | ---------------------------------------------- |
| **文件大小**   | 较小（二进制压缩）                 | 较大（纯文本命令日志）                         |
| **恢复速度**   | **极快**（直接加载到内存）         | 较慢（需要重新执行一遍所有命令）               |
| **数据安全性** | 较低（会丢失上次快照后的数据）     | **极高**（`everysec` 策略最多丢 1 秒）         |
| **系统开销**   | 较重（大块内存的 I/O 和 CPU 压缩） | 较轻（仅在重写时有明显开销，平时只是日志追加） |



## 4. 混合持久化

从计算机组成原理和操作系统的角度来看，RDB 和 AOF 本质上是对**磁盘 I/O 效率**与**数据恢复速度**的博弈：

- **RDB** 恢复极快（直接将二进制序列化数据加载到内存），但存在丢失数据的风险。
- **AOF** 数据最安全（命令日志追加），但重启恢复时需要把海量命令重新由 CPU 执行一遍，耗时极长。 

为了解决这个“鱼与熊掌”的问题，Redis 4.0 引入了混合持久化（在 Redis 5.0 中默认开启）。它的核心思想很简单：**RDB记录基础数据，AOF记录增量数据**



### 1.  混合持久化的文件结构

在混合持久化模式下，Redis 依然生成的是一个 AOF 文件，但这个文件的内部结构发生了彻底的改变。它不再是纯文本的命令日志，而是变成了 **“前半部分是 RDB 格式的二进制数据，后半部分是 AOF 格式的文本数据”** 的混合体。

### 2. 工作流程

混合持久化的魔法发生在使用 `BGREWRITEAOF` 触发 **AOF 重写**的那一刻。具体工作流程如下：

1. **Fork 子进程（写时复制）：**

   主进程同样会调用操作系统的 `fork()` 产生一个子进程。此时子进程拥有了和主进程一模一样的内存页表。

2. **生成 RDB 数据：**

   **这是与传统 AOF 重写最大的不同。** 子进程不再是把内存数据遍历转换成一条条 `SET` 等文本命令，而是直接将此刻的内存状态以 **RDB 的二进制格式**写入到一个临时的 AOF 文件中。这大大降低了重写时的 CPU 开销和磁盘 I/O 压力。

3. **处理重写期间的增量数据：**

   在子进程吭哧吭哧写 RDB 数据的时候，主进程依然在接收新的外部请求。这些新的写命令会被放在 **AOF 重写缓冲区（aof_rewrite_buf）** 中。

4. **追加 AOF 日志：**

   当子进程把 RDB 数据写完后，主进程会把重写缓冲区里的这部分增量新命令，以传统的 **AOF 纯文本命令格式**，追加到这个临时文件的末尾。

5. **原子替换：**

   用这个全新的、包含“RDB 头部 + AOF 尾部”的文件，替换掉旧的 AOF 文件。



### 3. 恢复数据

当 Redis 发生宕机或重启时，加载数据的流程也非常巧妙：

1. Redis 打开 AOF 文件，首先读取文件开头的部分。
2. 它会检查开头的几个字节是不是 `REDIS` 这个魔数（Magic Number，这是 RDB 文件的标准开头）。
3. 如果是，说明开启了混合持久化。Redis 就会先以极快的速度，像加载普通 RDB 文件一样，把前面的二进制数据直接映射到内存中。
4. RDB 部分加载完毕后，Redis 继续往下读，把尾部的一小段 AOF 文本命令一条条重放执行。



### 4. 总结与配置

在 `redis.conf` 中通过以下参数开启：

```bash
aof-use-rdb-preamble yes
```

**总结它的优势：**

它完美融合了 RDB 和 AOF 的优点。在日常运行中，它通过追加 AOF 保证了数据的绝对安全（最多丢1秒）；在重写时，它利用 RDB 格式大幅缩小了文件体积；在灾难重启时，绝大部分数据通过 RDB 二进制直接加载，仅仅回放极少量的 AOF 增量日志，极大地缩短了系统的停机恢复时间。



## 5. 大key对持久化的影响

在 Redis 中，“大 Key”（Big Key）对持久化机制（RDB 和 AOF）有着非常显著的负面影响。大 Key 不仅会占用大量内存，还会在执行持久化操作时引发严重的性能瓶颈，甚至导致 Redis 主线程阻塞。

具体来说，大 Key 对持久化的影响主要体现在以下几个方面：



### 1. 对 RDB (快照持久化) 的影响

RDB 是通过 `bgsave` 命令 fork 出一个子进程来生成内存快照的。大 Key 会在这个过程中带来三大隐患：

- **`fork()` 耗时过长，阻塞主线程：**

  执行 `bgsave` 时，Redis 主进程需要 fork 一个子进程。虽然现代操作系统采用 Copy-On-Write (写时复制) 技术，不需要立即拷贝所有内存数据，但**必须拷贝内存页表**。大 Key 意味着 Redis 占用的内存空间极大，页表也会相应变大。`fork()` 拷贝大页表的过程是同步的，会直接阻塞 Redis 主线程，导致这段时间内 Redis 无法响应任何客户端请求。

- **Copy-On-Write (COW) 引发内存突增：**

  在子进程生成 RDB 文件的过程中，如果主进程对这个大 Key 进行了修改操作（例如修改了一个包含上万元素的 Hash），就会触发 Copy-On-Write。此时，操作系统需要为这个大 Key 所在的内存页重新分配物理内存。由于 Key 的体积庞大，这会导致 Redis 瞬间申请大量内存，极易引发内存碎片化，甚至在内存紧张时触发 OOM（Out of Memory）。

- **磁盘 I/O 耗时：**

  将庞大的大 Key 序列化并写入 RDB 文件需要消耗大量的时间和磁盘 I/O 带宽。这会拖慢整个 RDB 快照的生成速度。



### 2. 对 AOF (追加日志持久化) 的影响

AOF 是将每一条写命令追加到日志文件中。大 Key 对 AOF 的影响同样集中在阻塞和资源消耗上：

- **AOF 缓冲区写入及 `fsync` 阻塞：**

  当对大 Key 执行写操作时（例如存入一个巨大的 String，或者向 Set 中批量添加大量元素），生成的单条 AOF 命令也会非常大。

  - 如果 AOF 刷盘策略配置为 `Always`，主线程在执行完命令后需要立刻将这么大的数据同步到磁盘，这会直接引发严重的磁盘 I/O 阻塞，拖垮主线程。
  - 如果配置为 `Everysec`，虽然由后台线程执行刷盘，但如果磁盘 I/O 处理不过来，导致 AOF 缓冲区堆积，依然可能反向拖慢甚至阻塞主线程。

- **AOF 文件体积膨胀过快：**

  频繁操作大 Key 会导致 AOF 文件体积急剧膨胀，这会更快地触发 AOF 重写（Rewrite）机制。

- **AOF Rewrite (`bgrewriteaof`) 的双重打击：**

  AOF 重写的过程与 RDB 类似，同样需要 fork 子进程。因此，它会**重复遭遇与 RDB 完全相同的 `fork()` 阻塞和 COW 内存突增问题**。此外，在重写期间，子进程需要遍历整个大 Key 并将其转化为多条写入命令写入新的 AOF 文件中，这不仅极其消耗 CPU，还会给磁盘带来持续的高负载。



大 Key 对持久化的核心影响可以概括为：**主线程阻塞风险极高（因 `fork` 和大 I/O）、内存存在突增 OOM 风险、磁盘 I/O 压力大。**

**应对与排查策略：**

1. **拆分大 Key：** 治本的方法。将一个巨大的 Hash/List 拆分成多个小的 Hash/List（例如通过一致性哈希或分片取模的方式打散）。
2. **异步删除：** 当需要删除大 Key 时，绝对不要使用 `DEL`（会阻塞主线程），而应该使用 `UNLINK`，交由后台异步线程去释放内存。
3. **合理配置持久化：** 在从节点（Slave）上进行 RDB 备份，主节点（Master）尽量避免进行繁重的持久化操作；或者调整 AOF 的 rewrite 触发阈值。
4. **监控工具：** 定期使用 `redis-cli --bigkeys` 命令扫描集群，或者通过 RDB 离线分析工具（如 `redis-rdb-tools`）来提前发现并处理大 Key。
