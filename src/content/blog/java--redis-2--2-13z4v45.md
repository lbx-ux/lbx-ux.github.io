# 一. Redis主从架构

Redis 的主从复制（Master-Slave / Master-Replica）是 Redis 实现高可用架构的最基本方式。它的核心思想很简单：**一台主节点负责写数据，一台或多台从节点负责读数据，主节点会将数据单向实时同步给从节点。**

<img src="/covers/java--redis-2--2-13z4v45/image-20260811153332803.webp" alt="image-20260811153332803" style="zoom:80%;" />

**主从架构的主要作用**：

- **读写分离：** 在实际的业务场景中，绝大多数操作都是“读多写少”。让主节点（Master）专职处理写请求，多台从节点（Slave）分担读请求，可以大幅提高系统的整体并发吞吐量。
- **数据冗余与备份：** 从节点不仅分担读压力，还充当着主节点的数据热备。即使主节点发生灾难性故障（如磁盘损坏），数据也不会完全丢失。
- **高可用的基石：** 单纯的主从架构并不具备自动容错能力，但它是 Redis 进阶高可用方案（哨兵模式 Sentinel 和集群模式 Cluster）的底层基础。



## 1. 主从同步过程

### 1. 全量复制时机（拜师学艺）

- **发生时机：** 从节点**第一次**接入主节点时，或者断线太久导致增量复制条件不满足时。
- **特点：** 极其耗费资源（生成 RDB、传输 RDB、清空内存、加载数据）。

### 2. 命令传播时机（正常上课）

- **发生时机：** 全量复制（或增量复制）完成之后，主从节点处于**正常连接、健康运行**的整个阶段。
- **特点：** 这是一个**持续且实时**的过程。主节点一接收到写命令，就立刻以数据流的形式通过长连接推给从节点，从节点实时回放。这被称为“命令传播”（Command Propagation）

### 3. 增量复制时机（请假后补笔记）

- **发生时机：**只发生在**异常断开后的重连时刻**。
- **典型场景：**
  - **网络闪断/抖动：** 主机房和备用机房之间的网络突然断开几秒钟，导致 TCP 长连接断裂。
  - **单点阻塞：** 主节点或从节点因为执行了某些耗时操作（如删除了一个超级大 Key，或者 `bgsave` 时发生严重的 swap），导致心跳超时，连接被系统强制判定为断开。
- **执行瞬间：** 当网络恢复，从节点重新向主节点建立起 TCP 连接，并发出 `psync {runID} {offset}` 命令的那一刻，主节点开始执行增量复制，把断开这段时间内的“笔记”（缓冲区里的写命令）一股脑补发给从节点。



一个典型的增量复制发生的时间线是这样的：

正常命令传播 `->` **突发网络故障导致断开** `->` 产生未同步的数据堆积在缓冲区 `->` 网络恢复 `->` 从节点发起重连 `->` **【此时触发并执行增量复制补齐数据】** `->` 恢复正常命令传播。

所以，增量复制本质上是一种**轻量级的故障恢复机制**，它的登场时机永远是在“短时间掉线并重连”的时候。



## 2. 核心同步机制

Redis 主从节点之间的数据同步主要分为两种场景：**全量复制**和**增量复制**。

### 1. 全量复制（Full Synchronization）

全量复制是 Redis 主从同步中最核心，同时也是非常消耗资源的一个过程。它通常发生在**从节点第一次连接主节点**，或者**从节点断开时间过长导致增量复制失败**被迫降级时。

你可以把全量复制理解为一次“彻底的拜师学艺”，从节点需要完全清空自己的记忆，把主节点当前的全部功力（数据）完整拷贝一份。

<img src="/covers/java--redis-2--2-13z4v45/image-20260811154225037.webp" alt="image-20260811154225037" style="zoom:80%;" />

全量复制是一个严格按顺序执行的网络交互与底层数据处理过程：

**1.发起同步请求:**psync ? -1.

从节点向主节点发送 `psync ? -1` 命令。`?` 代表从节点还不知道主节点的 runID，`-1` 代表它还没有复制偏移量（offset），即请求进行首次全量同步。主节点收到后回复 `+FULLRESYNC {runid} {offset}` 确认全量复制。

**2.主节点生成 RDB 快照:**BGSAVE.

主节点会在后台执行 `bgsave` 命令，通过 `fork` 创建一个子进程，将当前的内存数据生成为一个 RDB 快照文件。**此时主节点依然可以接收新的写请求**，这些新命令会被暂存到**复制缓冲区（repl_backlog_buffer）**中。

**3.传输 RDB 文件:**

主节点将生成的 RDB 文件通过网络发送给从节点。这是一个比较耗时的网络 I/O 过程，耗时取决于 RDB 文件的大小和主从节点之间的网络带宽。

**4.从节点清空旧数据并加载 RDB:**

从节点接收完 RDB 文件后，会**先清空自己内存中的所有旧数据**（`flush old data`），然后将 RDB 文件加载到内存中。这一步完成后，从节点的数据状态就恢复到了主节点执行 `bgsave` 那个时刻的状态。

**5.发送并执行增量命令:**

在主节点生成和传输 RDB 的这段时间里，新产生的写命令都堆积在 `replication buffer` 中。主节点此时会将这些堆积的命令发送给从节点。从节点执行完这些命令后，主从节点的数据就达到了完全一致的最终态。



**全量复制的潜在风险点**

因为全量复制涉及到磁盘 I/O（生成 RDB）、网络 I/O（传输 RDB）和 CPU 消耗（加载 RDB），在生产环境中如果频繁触发，会带来严重的性能隐患：

- **主节点阻塞：** `bgsave` 过程中的 `fork` 操作如果主节点内存非常大，可能会导致主节点发生毫秒甚至秒级的阻塞。
- **复制风暴：** 如果一台主节点下面挂了非常多的从节点，且这些从节点同时断线重连触发全量复制，主节点需要同时向多个从节点发送庞大的 RDB 文件，极易耗尽主节点的网络带宽，这被称为“主从复制风暴”。（通常通过引入“主-从-从”的级联架构来缓解）。
- **复制缓冲区溢出：** 如果 RDB 文件很大或者网络很慢，导致从节点加载数据的时间过长，主节点的 `repl_backlog_buffer` 可能会被新的写命令撑爆。一旦溢出，主节点会断开复制连接，导致全量同步失败并陷入死循环。



### 2. 增量复制（Partial Synchronization）

增量复制（Partial Synchronization）是 Redis 2.8 之后引入的一项极其关键的优化机制。它的出现，主要是为了解决**从节点在遭遇网络闪断或短时间掉线后，重连时依然需要进行昂贵的全量复制**这一痛点。

可以把增量复制理解为“断点续传”，它的核心依赖于三个关键要素：**主节点运行 ID (runID)**、**复制偏移量 (offset)** 和 **复制积压缓冲区 (repl_backlog_buffer)**。



#### 1. 三大核心组件

- **主节点运行 ID (runID)：**

  每个 Redis 节点启动时，都会自动生成一个由 40 个随机十六进制字符组成的唯一 ID。从节点初次复制时，会保存主节点的 `runID`。断线重连后，从节点会把这个 `runID` 发给主节点，主节点借此判断：“你之前是不是一直跟着我混的？”

- **复制偏移量 (offset)：**

  主节点和从节点都会各自维护一个 `offset`。主节点每向从节点发送 N 个字节的数据，自己的 `offset` 就会加 N；从节点每收到 N 个字节的数据，自己的 `offset` 也会加 N。正常情况下，主从的 `offset` 是完全一致的。

- **复制积压缓冲区 (repl_backlog_buffer)：**

  这是主节点上的一个**固定大小的环形队列**（默认大小通常是 1MB）。当主节点响应写命令时，不仅会把命令发给从节点，还会同时写入这个环形缓冲区。由于它是环形的，当数据写满后，新的数据就会覆盖掉最老的数据。



#### 2. 交互流程

假设主从集群正在正常运行，突然发生了网络抖动，从节点掉线了几十秒。以下是它重连后的完整动作：

<img src="/covers/java--redis-2--2-13z4v45/image-20260811155912659.webp" alt="image-20260811155912659" style="zoom:80%;" />

1. **发起续传请求：**

   从节点重新连上主节点，发送 `psync {runID} {offset}` 命令。这里的 `runID` 是它掉线前保存的主节点 ID，`offset` 是它掉线前同步到的最新偏移量。

2. **主节点核对身份 (runID)：**

   主节点收到请求后，首先比对 `runID`。如果发现 `runID` 和自己当前的不一致（说明主节点可能重启过，或者当前的主节点是刚被 Sentinel 提拔上来的），那么主节点直接拒绝增量复制，强制降级为**全量复制**。

3. **主节点核对进度 (offset)：**

   如果 `runID` 匹配，主节点会去自己的**复制积压缓冲区**中查找从节点传过来的 `offset`。

   - **场景 A（命中）：** 如果这个 `offset` 之后的数据依然完整地保存在环形缓冲区内（没有被新数据覆盖），主节点会回复 `+CONTINUE`，然后把缺失的这部分数据直接发送给从节点，瞬间完成同步。
   - **场景 B（未命中）：** 如果从节点掉线时间太长，或者主节点在这期间接收了极其海量的写请求，导致缓冲区的数据已经被覆盖了一圈以上（`offset` 找不到了），主节点只能回复 `+FULLRESYNC`，被迫降级为代价高昂的**全量复制**。



#### 3. 生产环境的避坑指南

增量复制虽然美好，但在高并发的业务场景下，非常容易因为配置不当而失效，导致频繁触发全量复制，进而引发系统雪崩。

核心的瓶颈就在于那个**固定大小的环形缓冲区**。如果缓冲区太小，稍微断开几秒钟，数据就被覆盖了。因此，合理配置 `repl-backlog-size`（缓冲区大小）至关重要。合理的估算公式通常是：`缓冲空间大小 = 主库写入命令速度 * 从库重连需要的平均时间 * 2`。

在梳理清楚了增量复制的边界条件后，你是否想探讨一下，在实际的生产环境部署中，我们该如何根据具体的业务写入吞吐量来动态计算并调整 `repl-backlog-size` 这个参数？



## 3. 主从架构的局限性

尽管主从模式解决了单机并发读取和数据备份的问题，但它并不完美：

| **局限性**           | **说明**                                                     |
| -------------------- | ------------------------------------------------------------ |
| **无法自动故障转移** | 一旦主节点（Master）宕机，系统就彻底失去了写能力。必须由运维人员手动将某个从节点提升为主节点，并修改应用程序的配置，期间服务会中断。 |
| **写能力受限**       | 无论挂载多少个从节点，所有的写请求依然只能由单台主节点承担，单机的 CPU 性能成为了写入并发的瓶颈。 |
| **存储容量受限**     | 从节点是主节点的完整副本，这意味着整个 Redis 系统的最大存储容量依然受限于单台主节点的内存大小。 |





## 4. 主从同步优化

主从同步可以保证主从数据的一致性，非常重要。

可以从以下几个方面来优化Redis主从就集群：

- 在master中配置repl-diskless-sync yes启用无磁盘复制，避免全量同步时的磁盘IO。
- Redis单节点上的内存占用不要太大，减少RDB导致的过多磁盘IO
- 适当提高repl_baklog的大小，发现slave宕机时尽快实现故障恢复，尽可能避免全量同步
- 限制一个master上的slave节点数量，如果实在是太多slave，则可以采用主-从-从链式结构，减少master压力

# 二. Redis哨兵

## RedisTemplate

**1. 引入依赖**

在项目的pom文件中引入依赖：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```



**2. 配置Redis地址**

然后在配置文件application.yml中指定redis的sentinel相关信息：

```java
spring:
  redis:
    sentinel:
      master: mymaster
      nodes:
        - 192.168.150.101:27001
        - 192.168.150.101:27002
        - 192.168.150.101:27003
```



**3. 配置读写分离**

在项目的启动类中，添加一个新的bean：

```java
@Bean
public LettuceClientConfigurationBuilderCustomizer clientConfigurationBuilderCustomizer(){
    return clientConfigurationBuilder -> clientConfigurationBuilder.readFrom(ReadFrom.REPLICA_PREFERRED);
}
```

这个bean中配置的就是读写策略，包括四种：

- MASTER：从主节点读取
- MASTER_PREFERRED：优先从master节点读取，master不可用才读取replica
- REPLICA：从slave（replica）节点读取
- REPLICA _PREFERRED：优先从slave（replica）节点读取，所有的slave都不可用才读取master





# 三. 面试

在技术面试中，面试官考察 **Redis 高可用架构** 通常围绕 **主从复制**、**哨兵模式（Sentinel）**、**分片集群（Redis Cluster）** 三层演进体系展开，并重点深挖**故障转移细节**与**数据一致性陷阱**。

**一、 主从复制（数据冗余与读写分离）**

主从复制是所有高可用架构的基础，面试重点考察数据同步的底层机制：

- **全量同步与增量同步流程**：
  - **首次同步（全量）**：Slave 发送 `psync ? -1` $\rightarrow$ Master 执行 `bgsave` 生成 RDB 发送给 Slave $\rightarrow$ Master 发送快照期间积累的 `replication_buffer` 写入命令 $\rightarrow$ Slave 加载 RDB 并回放缓冲命令。
  - **断线重连（增量）**：基于 `repl_backlog_buffer`（环形复制积压缓冲区）和 `master_repl_offset`。若 Slave 的偏移量还在环形缓冲区内则进行增量同步；若被覆写覆盖，则强制退化为全量同步。
- **高频追问点**：
  - *主从复制风暴*：多个 Slave 同时全量同步导致 Master 频繁 `fork` 阻塞主线程并打满网络带宽（优化方案：树状主从架构或调大积压缓冲区）。
  - *读写分离的坑*：异步复制导致的**主从延迟与脏读**、从节点过期键未及时物理删除导致的读取问题。

**二、 哨兵模式（Sentinel，自动故障转移）**

哨兵主要解决主从架构下 Master 宕机需人工介入切换的问题。

- **监控与故障判定**：

  - **主观下线（sdown）**：单个 Sentinel 节点向 Master 发送 PING 超过 `down-after-milliseconds` 未收到有效回复。
  - **客观下线（odown）**：Sentinel 向其他节点发送 `SENTINEL is-master-down-by-addr` 询问，当超过 `quorum` 配置数量的 Sentinel 认为其下线时，判定客观下线（仅针对 Master）。

- **故障转移（Failover）完整流程**：

  1. **选举 Leader 哨兵**：基于简化版 Raft 共识算法，获得超半数（$\ge n/2 + 1$ 且 $\ge quorum$）投票的 Sentinel 当选 Leader 执行切换。

  2. **选出新 Master 规则**：

     $$\text{过滤不健康/断连节点} \rightarrow \text{优先级 (slave-priority)} \rightarrow \text{复制偏移量 (offset 最大)} \rightarrow \text{运行 ID (runid 最小)}$$

  3. **角色切换与通知**：向选出的 Slave 发送 `slaveof no one`，向其他 Slave 发送 `slaveof <new_master_ip>`，并通知客户端新主节点地址。

**三、 分片集群（Redis Cluster，海量数据与横向扩展）**

Cluster 解决了单机内存容量上限和单点写瓶颈，实现了分布式存储与内置高可用。

- **哈希槽（Hash Slot）机制**：
  - 整个集群固定分配 **16384** 个槽位，通过 $\text{CRC16}(key) \pmod{16384}$ 计算 Key 所属槽位。
  - **Hash Tag**：使用 `{user_id}:order` 强制将相同大括号内的键映射到同一个 Slot，以支持多键事务或 Pipeline 操作。
  - *经典追问*：为什么是 16384 个槽位？（心跳包体积考量：16384 占 2KB 位图，65535 占 8KB；集群建议规模通常在 1000 节点以内，16384 足够均匀分布）。
- **集群通信与路由**：
  - **Gossip 协议**：节点间通过 PING/PONG/MEET/FAIL 报文交换状态，属于去中心化架构。
  - **重定向机制**：
    - `MOVED`：Key 对应的槽位已固定在目标节点，客户端接收后需更新本地 Slot 缓存。
    - `ASK`：Slot 正在迁移中，客户端需先向目标节点发送 `ASKING` 命令再执行请求，不更新本地路由缓存。

**四、 高频压轴深挖题（必背陷阱）**

| **考察场景**                          | **核心原因**                                                 | **解决方案 / 回答要点**                                      |
| ------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **网络分区导致的脑裂（Split-Brain）** | 原 Master 发生网络分区被孤立，Sentinel 选举了新 Master，但旧 Master 仍在接收客户端写入。分区恢复后旧 Master 降为 Slave 并清空本地数据，导致期间写入丢失。 | 配置参数防护：  • `min-replicas-to-write 1`（至少 1 个 Slave 连接）  • `min-replicas-max-lag 10`（Slave 延迟不超过 10 秒），否则 Master 拒绝写入。 |
| **异步复制丢失数据**                  | Master 写入成功并响应客户端，但在异步同步给 Slave 之前 Master 宕机，新晋 Master 缺失该部分数据。 | 无法做到 100% 强一致性；若需强可靠可结合业务端补偿、Binlog 双写校验或引入消息队列削峰落盘。 |
| **分布式锁的主从安全性**              | 在 Master 上获取锁后，Master 宕机未同步至 Slave，Slave 升主导致同一把锁被重复获取。 | 说明 Redisson / Redlock 算法原理（向 $N$ 个独立 Master 申请锁），并能客观分析 Redlock 对时钟漂移敏感的争议与权衡。 |
