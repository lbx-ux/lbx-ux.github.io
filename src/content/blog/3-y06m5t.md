## 一. PO,VO,DTO,QO

区分它们的根本意义在于**解耦**和**数据安全**——避免把数据库底层结构直接暴露给外部，同时也让不同代码层之间的职责更加清晰。

**核心概念解析**

| **对象类型** | **全称**                            | **层级定位**                           | **核心作用**                                                 | **典型应用场景**                                             |
| ------------ | ----------------------------------- | -------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **PO**       | Persistent Object (持久化对象)      | 数据访问层 (DAO/Mapper)                | 直接与数据库表结构一一对应，属性和数据库表的字段基本一致。   | MyBatis/MyBatis-Plus 中带有 `@TableName` 注解的实体类，代表 MySQL 里的一行真实数据。 |
| **DTO**      | Data Transfer Object (数据传输对象) | 服务层 (Service) ↔ 控制层 (Controller) | 在不同逻辑层之间传输数据，或者在微服务之间进行 RPC 调用时打包聚合数据。 | 业务逻辑处理后，从 Service 层返回包含多张表关联信息的 `UserOrderDTO` 给 Controller 层。 |
| **VO**       | View Object (表现层对象)            | 控制层 (Controller) ↔ 前端             | 专为前端展示定制的数据结构，隐藏后端实现细节，主要用于数据格式化。 | 返回给前端的视图数据，例如把后端的枚举状态 `1` 映射为 `已发货`，并严格屏蔽掉密码等敏感字段。 |
| **QO**       | Query Object (查询对象)             | 前端 ↔ 控制层 (Controller)             | 封装前端传来的查询条件，通常包含特定的查询逻辑字段。         | 前端发起的列表请求，将 `keyword` (模糊搜索关键字), `page`, `size` 封装进 `UserQO` 中供后端接收。 |

**数据在架构中的流转**

在标准的三层架构中，这些对象的边界非常明确，通常按以下流程流转：

1. **接收请求：** 前端发起数据检索请求，Controller 层通过 **QO**（如 `UserQO`）接收参数。
2. **处理业务：** Controller 将 QO 传递给 Service 层。
3. **查询底层：** Service 层调用 Mapper 层，Mapper 层查询 MySQL 数据库，返回与表结构强绑定的 **PO**（如 `UserPO`）。
4. **数据聚合：** Service 层将 `UserPO` 的基础数据提取出来，可能还会调用其他服务获取补充数据，将它们组装成 **DTO**（如 `UserDetailDTO`）返回给 Controller。
5. **响应视图：** Controller 拿到 DTO 后，将其转换为前端所需的最终形态 **VO**（如 `UserVO`，处理时间格式，剔除无关字段），最终返回给客户端。



## 二. copyProperties

copyProperties是一个非常常用的工具方法，主要用于**将一个对象的属性值复制到另一个对象中**。它最常见的使用场景是在分层架构中，进行数据传输对象（DTO）、视图对象（VO）和实体类（Entity）之间的相互转换。

不过，在使用它之前，你必须先搞清楚你引入的是哪个包下的 `copyProperties`，因为这是 Java 开发中**最容易踩坑**的地方。

目前主流的有两个版本：**Spring 提供**的和 **Apache 提供的**。它们的**参数顺序是完全相反的**！我们要使用Spring版的



**Spring 版**：

**包名**：`org.springframework.beans.BeanUtilsuser`

**方法签名**：`copyProperties(Object source, Object target)`

**记忆口诀**：**先源后目标**（把前面的复制给后面的）

```java
BeanUtils.copyProperties(user, UserDTO.class);
```



**Spring 版的高级用法（忽略某些属性）：**

如果你不想拷贝某些特定的属性（比如密码），可以传入第三个参数：

```java
// 拷贝时，忽略 "password" 和 "createTime" 字段
BeanUtils.copyProperties(entity, dto, "password", "createTime");
```



**三大避坑指南**

1. **字段名称和类型必须严格一致**

- **名称必须相同**：只有源对象和目标对象中**名字完全一样**的字段才会被拷贝。比如 `userName` 和 `username` 无法映射。
- **类型最好一致**：虽然某些工具类会自动进行基础类型转换，但为了安全，建议字段类型保持一致（比如不能一个是 `String`，一个是自定义对象）。如果是包装类（`Integer`）和基本类型（`int`）之间，通常可以自动装箱/拆箱，但要注意源属性为 `null` 时可能会引发空指针异常。

2. **它是“浅拷贝” (Shallow Copy)**

`copyProperties` 仅仅是把属性的引用拷贝过去。

- 如果你的对象里嵌套了另一个自定义对象（比如 `User` 里面包含一个 `Address` 对象），拷贝后的 `UserDTO` 和 `UserEntity` 会**共享同一个 `Address` 内存地址**。
- 如果你修改了 `UserDTO` 里的 `Address`，`UserEntity` 里的 `Address` 也会跟着变！如果需要深拷贝，建议手动 `set` 或者使用序列化方案。

3. **性能问题**

`copyProperties` 底层使用的是**反射机制**。

- **Spring 版** 内部做了大量的缓存优化，性能尚可，日常业务开发完全够用。
- **Apache 版** 性能非常差，高并发场景下容易成为系统瓶颈。
- **极致性能**：如果你对性能要求极高（比如大批量数据导入导出），**千万不要用反射类的拷贝工具**。建议直接手写 `get/set` 方法，或者使用在编译期自动生成 `get/set` 代码的映射框架，例如 **MapStruct**。

## 三. builder

 **Lombok 提供的 `@Builder` 注解**（底层是经典的设计模式：建造者模式）,提供了一种**更优雅、更清晰的“链式调用”方式**来创建对象并赋值。

### 1.对比

假设我们要创建一个用户对象并赋值：

**❌ 传统方式（又臭又长，容易漏看）：**

```java
User user = new User();
user.setUsername("张三");
user.setEmail("zhangsan@example.com");
user.setPassword("加密后的密码");
user.setStatus(1);
```

用全参数构造函数 `new User(xxx, xxx, ...)`，一旦参数多了，根本分不清哪个值对应哪个字段。

**✅ Builder 方式（链式调用，清晰明了）：**

```java
User user = User.builder()
        .username("张三")
        .email("zhangsan@example.com")
        .password("加密后的密码")
        .status(1)
        .build(); // 最后调用 build() 生成最终对象
```



### 2.使用

你只需要在你的实体类（Entity 或 DTO）上加一个 `@Builder` 注解即可（前提是你已经引入了 Lombok 依赖）。

**第一步：改造实体类**

```java
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.Data;
import lombok.NoArgsConstructor;

@Data
@Builder // 👈 加上这个注解
@NoArgsConstructor // ⚠️ 避坑必加（原因见下文）
@AllArgsConstructor // ⚠️ 避坑必加
public class User {
    private Long id;
    private String username;
    private String email;
    private String password;
    private Integer status;
}
```

**第二步：在业务代码中使用**

```java
// 3. 密码加密
String encodedPassword = passwordEncoder.encode(userDTO.getPassword());

// 4. 使用 Builder 构建新用户对象 (代替 new User() 和 copyProperties)
User newUser = User.builder()
        .email(userDTO.getEmail())
        .password(encodedPassword) // 直接把加密后的密码塞进去
        // 其他不需要初始化的字段不用写，默认就是 null
        .build();

// 5. 插入数据库
userMapper.insert(newUser);
```

### 3.Builder 和 copyProperties 怎么选？

- **用 `copyProperties` 的场景**：DTO 和 Entity 字段**几乎完全一样**，且有十几二十个字段需要拷贝。图省事，一行代码搞定。
- **用 `Builder` 的场景**：只需要针对性地给**部分字段**赋值，或者字段名对不上，又或者需要在赋值时做一些数据转换（比如密码加密）。此时用 Builder 语义更清晰，可读性极强。

### 4.核心避坑指南

只要你在类上加了 `@Builder`，**请务必同时加上 `@NoArgsConstructor` 和 `@AllArgsConstructor`**！

**为什么？**

因为 `@Builder` 的底层逻辑是为你生成一个包含所有参数的私有构造函数。一旦有了全参构造函数，Java 就会**吃掉**默认的无参构造函数（`public User()`）。

而你的 MyBatis（查数据库映射时）和 Jackson（接收前端 JSON 数据时），底层都必须依赖无参构造函数来反射创建对象。如果不加 `@NoArgsConstructor`，你的接口大概率会报反序列化失败的错误！
